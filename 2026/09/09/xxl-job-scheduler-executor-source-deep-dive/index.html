【任务调度源码】XXL-Job 深度解析：调度中心触发机制、执行器注册发现与路由分片策略源码级剖析

面试官：你们的定时任务为什么不用 @Scheduled？XXL-Job 的调度中心和执行器是怎么通信的？分片广播怎么实现？

@Scheduled 在单机时代够用，一旦任务要多实例执行、动态扩容、失败重试、分片处理千万级数据，就需要分布式任务调度平台。XXL-Job 是国产开源里使用最广的（没有之一）：调度中心（admin）+ 执行器（executor） 的架构简单清晰，文档完善，面试也爱考。

但大多数人的理解停留在”会用 @XxlJob 注解”。本文扒开它的调度触发、注册发现、RPC 通信、路由策略、分片广播，讲清楚它到底怎么工作的。

一、整体架构：两个进程，各自职责

核心思想：调度与执行解耦——调度中心只负责”什么时候触发、触发谁”，真正干活的是业务应用内的执行器。所以执行器天然支持多实例，任务可以水平扩展。

二、调度中心：Quartz 触发的真相

很多人以为 XXL-Job 自己实现了 cron 解析，其实调度中心内部用的是 Quartz 做粗粒度触发（XxlJobScheduler 启动时初始化 Quartz Scheduler）：

  1. 新增/编辑任务时，把 cron 注册成 Quartz JobDetail（JobInfo → Quartz）；
  2. 到了触发时间点，Quartz 回调 XxlJobDynamicScheduler 的 Trigger 逻辑——这一步只是”到点了”的闹钟；
  3. 真正触发时，调度中心从 DB 加载 JobInfo，走 TriggerParam 组装 → 路由 → RPC 下发。

关键点：Quartz 在这里只是触发器，任务的执行模型完全是 XXL-Job 自己的（路由、阻塞、重试都是它实现的）。Quartz 集群（基于 DB 行锁的集群模式）保证了调度中心多节点部署时 cron 不会重复触发——这也是调度中心可以做集群的原因。

三、执行器注册发现：30 秒心跳的玄机

执行器启动后（XxlJobExecutor.start()）：

  • 注册信息存调度中心 DB 的 xxl_job_registry 表（appname + 实例地址 + 更新时间）；
  • 调度中心的 JobRegistryMonitorHelper 每 30s 扫描一次，把超过 90s 未更新的实例标记为下线并清理；
  • 执行器侧还有 TriggerCallbackThread：任务执行完，把结果异步批量回调调度中心（失败会重试补交）。

所以执行器优雅停机时要调 XxlJobExecutor.destroy() 主动摘除注册，否则要等 90s 超时才被清理——发布时旧实例可能继续被调度，这就是为什么建议执行器配置优雅停机 + 注册摘除钩子。

四、调度中心 → 执行器的 RPC 调用

XXL-Job 自研了一套轻量 RPC（xxl-rpc），默认 Netty 实现，也可切换 Http 实现：

  1. 调度中心根据路由策略选出一个执行器地址（http://ip:9999/）；
  2. 序列化触发参数（TriggerParam：jobId、executorHandler、executorParams、分片参数、超时时间等）走 Netty 发出；
  3. 执行器收到请求 → JobThread（每个 JobId 一个常驻线程）入队 → 执行 @XxlJob 方法；
  4. 执行完成，执行器把结果（成功/失败、执行日志地址）回调调度中心落库。

这里有个高频考点：JobThread 是每个任务 ID 一个常驻线程 + 阻塞队列，配合”阻塞处理策略”实现单机串行——同一任务在同一实例上不会并发执行。

五、路由策略：10 种策略源码级解读

触发时由 ExecutorRouter 路由，常见策略：

策略 行为 适用场景
第一个 固定选注册列表第一个 指定单机执行
轮询 依次分发 负载均衡执行
随机 随机选一台 无状态任务
一致性 HASH 按 JobId hash 选固定实例 需要”同一任务固定机器”（本地缓存型任务）
最不经常使用 / 最近最久未使用 按实例被调度次数/时间选 冷热不均场景
故障转移 逐个尝试，失败换下一台 高可用关键任务
忙碌转移 实例忙（执行中）就换一台 避免排队
分片广播 发给所有实例，携带分片参数 大数据量分批处理

分片广播是 XXL-Job 最亮的功能，看它的参数传递：

10 个执行器各处理 1/10 的数据，百万级订单批处理从”一台跑 2 小时”变成”10 台跑 12 分钟”，这就是分片广播的价值——比 Quartz 单机不知道高到哪里去了。

六、阻塞处理与失败重试

阻塞处理策略（任务还没跑完又到触发点怎么办）：

策略 行为
单机串行 排队等上一个跑完（默认，推荐）
丢弃后续调度 直接丢弃本次触发
覆盖之前调度 终止旧线程，跑新的（慎用，可能产生脏数据）

失败重试：JobInfo 上配”失败重试次数”，执行失败会自动重试（注意重试是整任务重跑，任务要做好幂等）；超过重试次数 → 触发告警（邮件/钉钉/企业微信）。

七、高可用与生产实践

  1. 调度中心集群：多节点 + 共用 MySQL（Quartz 集群表），任意节点挂掉不影响调度；
  2. 执行器多实例：同一 appname 部署多份，注册表里就有多个地址，路由/分片才有意义；
  3. 任务幂等：分布式调度没有”恰好一次”，失败重试/超时重发都可能导致重复执行，业务侧必须幂等（唯一键、状态机）；
  4. 超时控制：配任务超时时间，超时执行器会中断并标记失败，防止任务卡死占着 JobThread；
  5. 日志：执行日志分片存储，调度中心可在线查看——排查问题利器。

八、面试高频追问

  • 调度中心为什么用 Quartz？→ 只借它的 cron 触发 + 集群去重，执行模型自研
  • 执行器怎么被发现？→ 30s 心跳注册，90s 未更新摘除
  • 任务怎么到执行器的？→ 自研 RPC（Netty/Http），路由策略选实例
  • 分片广播参数哪来的？→ 调度中心下发 shardIndex/shardTotal，业务按模取数
  • 同一实例上同一任务会并发吗？→ 不会，JobThread 单线程 + 阻塞队列
  • 和 Quartz 单机部署比优势？→ 动态管理、路由、分片、重试告警、日志可视化

一句话总结：XXL-Job = Quartz 做闹钟 + 注册中心做发现 + 自研 RPC 做下发 + 路由分片做分发 + JobThread 做隔离执行。理解这五层，分布式定时任务的架构题就稳了。

【Redis 原理】Redis 键过期删除策略深度解析：惰性删除、定期删除与主从复制下的过期之谜

面试官：给 Key 设置了过期时间，Redis 是怎么把它删掉的？过期键会立刻消失吗？

这是 Redis 面试的经典高频题，几乎必问。很多同学知道”惰性删除 + 定期删除”两个词，但说不清底层数据结构、删除时机、内存淘汰的关系，更答不上”主从复制下过期键怎么处理”这种进阶追问。今天一次讲透。

一、过期键是怎么存的？

1.1 过期字典（expires dict）

每个 Redis 数据库（db）里有两张哈希表：

  • dict：键空间，存所有键值对
  • expires：过期字典，key 相同，value 是过期时间戳（毫秒）

设置过期时间时（EXPIRE、SETEX、SET ... EX），Redis 会在 expires 字典里写入到期时间；PERSIST 则从 expires 字典移除该键。

1.2 过期时间的判定

二、三种删除策略对比（先讲理论）

策略 原理 优点 缺点
定时删除 到期立刻删，设置定时器 内存友好，及时释放 大量过期键时 CPU 开销巨大，Redis 未采用
惰性删除 访问时发现过期才删 CPU 友好 过期键长期驻留内存，浪费内存
定期删除 周期性抽查删除 CPU/内存折中 删除不及时，需与惰性删除配合

Redis 实际采用的是：惰性删除 + 定期删除 配合使用。

三、惰性删除（Lazy Delete）原理

3.1 触发时机

所有读写命令入口都会先调用 expireIfNeeded() 检查键是否过期：

  • 读命令：GET、HGET、MGET 等
  • 写命令：SET、INCR、LPUSH 等（对已过期键写入相当于覆盖）
  • 管理命令：EXISTS、TTL 等

3.2 关键特性

  • 过期键被访问到的那一刻才删除，删除动作和命令执行是原子的
  • 从未被访问的过期键会一直占着内存（这就是为什么要配合定期删除）
  • 注意：EXISTS 命令对过期键也返回 0，因为它在执行前就做了过期检查

4.2 设计要点

  • 随机采样而非全表扫描：避免大 keyspace 下单次耗时过长
  • 时间预算控制：activeExpireCycle 有耗时上限（默认约 25% 的 CPU 时间片），防止影响正常命令
  • 自适应：过期键多就多删几轮，少就提前退出

五、惰性删除 + 定期删除 还有漏网之鱼吗？

有！大量 Key 同时过期且长时间不被访问，定期删除一轮处理不完：

  • 1000 万个 Key 同一秒过期
  • 定期删除 16 轮 × 每轮 20 个 ≈ 每次最多处理几百个
  • 剩下的过期键继续占内存，直到被访问或下一轮定期删除

这就是”缓存雪崩”的内存侧成因：大批 Key 同时过期时，Redis 内存不会立刻释放，期间新写入可能触发内存淘汰，也可能出现短暂的命令延迟升高。

实战启示：给 Key 的过期时间加随机偏移（EXPIRE k1 3600 + random(0, 300)），既防雪崩，也避免过期键集中堆积。

6.1 主库：真实删除

6.2 从库：逻辑过期，不主动删

从库不会主动删除过期键（避免主从删除时机不一致），而是在读请求时做逻辑判断：

也就是：从库读到已过期的键时，返回空，但键本身还留在内存里，等待主库的 DEL 命令到来后才物理删除。

6.3 两种模式的差异

场景 主库 从库（默认异步复制）
键过期 立即物理删除 读时逻辑过滤，等主库 DEL
读请求 返回 nil 返回 nil（逻辑过期判断）
内存占用 及时释放 可能短暂残留（等 DEL 同步）
主从切换后 — 若从库升主，残留键由新主继续执行过期逻辑

6.4 追问：从库能读到已过期的数据吗？

不能读到（读命令会做逻辑过期判断返回 nil），但内存会短暂残留。唯一例外：如果主库 DEL 命令还没同步到从库，从库内存里有这个键，但读时依然返回 nil，所以业务上不会读到过期数据。

补充：Redis 5.0 之前从库读过期键返回 nil 但不删除；Redis 5.0 之后有 replica-read-only 等演进，但”从库不主动物理删除”的设计核心没变。

七、过期删除 vs 内存淘汰（易混淆点）

维度 过期删除 内存淘汰（Eviction）
触发条件 键设置了 TTL 且到期 内存达到 maxmemory 上限
处理对象 仅限有过期时间的键 所有键（取决于策略）
策略 惰性 + 定期 LRU / LFU / TTL / random / noeviction
目的 释放过期数据 保证 Redis 不 OOM

区别一句话：过期删除是”该删的删掉”，内存淘汰是”内存不够了挑着删”。

八、面试高频追问

Q1：为什么不只用惰性删除？
只用惰性删除，大量不被访问的过期键会永久占内存，极端情况下内存耗尽触发淘汰甚至 OOM。定期删除就是补这个洞的。

Q2：为什么不只用定期删除？
定期删除是抽样，无法保证”所有过期键都被及时删除”；且为控制耗时不能扫全表。两者配合：定期删除控制总量，惰性删除兜底单个键的时效性。

Q3：SET 一个已过期但未删除的键会发生什么？
expireIfNeeded 先删除旧键，再执行 SET，表现如同普通的覆盖写，数据不会错乱。

Q4：大量 Key 同时过期会卡 Redis 吗？
会。定期删除在”过期键比例高”时会连续多轮执行，虽然有时间预算，但删除 10 万个键的释放动作仍可能造成毫秒级延迟。所以生产上过期时间要加随机偏移。

Q5：主从切换后，新主库会有残留过期键吗？
可能有（原从库内存里逻辑过期的键）。但新主库继续执行惰性 + 定期删除逻辑，这些键被访问或抽查到时会被真正删除，不会长期残留。

总结

  • 存储：expires 过期字典记录每个键的到期时间
  • 删除策略：惰性删除（访问时删）+ 定期删除（随机采样 + 时间预算），Redis 未采用定时删除
  • 主从场景：主库真删并广播 DEL，从库逻辑过期、读返回 nil、等主库 DEL 才物理删
  • 易混淆：过期删除（TTL 到期）≠ 内存淘汰（maxmemory 触发）
  • 工程建议：过期时间加随机偏移，监控 expired_keys，避免批量同时过期引发雪崩

【MySQL 索引】B+ 树深度解析：从数据结构原理到 InnoDB 索引实现

面试官：为什么 MySQL 的索引要用 B+ 树，而不是二叉树、红黑树或者哈希表？

这是一道几乎必问的数据库面试题。要答好它，需要从”磁盘 IO 模型”这个底层约束出发，一层层推演。先给出结论：B+ 树是在”磁盘访问”场景下，读写性能、范围查询、稳定性三者综合最优的数据结构。

一、为什么不是这些结构？

1. 为什么不选哈希索引？

哈希索引查找单个 key 是 O(1)，无敌快，但有两个致命缺陷：

  • 不支持范围查询：WHERE age > 20 这种条件，哈希表只能全表扫描
  • 不支持排序：哈希是无序的，ORDER BY 无从谈起

所以哈希索引只适合等值查询的特定场景（如 Memory 引擎、自适应哈希索引 AHI）。

2. 为什么不选二叉搜索树（BST）？

最坏情况下 BST 会退化成链表（插入有序数据时），查找退化成 O(n)。就算平衡了（AVL/红黑树），还有更大的问题——树太高。

假设数据量是 1000 万条，红黑树高度约 log₂(1000万) ≈ 24 层。每查一个节点就是一次磁盘 IO（节点可能不在内存），24 次磁盘 IO，每次约 10ms，光寻道就要 240ms，完全不可接受。

3. 为什么不选红黑树？

红黑树是内存数据结构（Java 的 TreeMap、C++ 的 map），它优化的目标是减少旋转次数。但在磁盘场景下，树的高度（即磁盘 IO 次数）才是瓶颈。红黑树高度依然是 log₂N 级别，和 AVL 没有本质区别。

4. 为什么不选 B 树？

B 树已经是多路平衡树了，每个节点可以存多个 key，高度大幅降低。但它有个问题：key 和 data 存在一起，每个节点的容量有限。

B+ 树相比 B 树的改进（核心考点！）：

对比项 B 树 B+ 树
数据存储 每个节点都存数据 只有叶子节点存数据，非叶子节点只存 key
叶子节点 相互独立 通过链表相连（双向）
查找复杂度 不稳定，可能在中途节点命中 稳定，必须走到叶子节点
范围查询 需要中序遍历，多次回溯 找到起点后顺着链表扫，效率极高
单节点容纳 key 数 少（key+data 占空间） 多（只存 key，页能塞更多 key）→ 树更矮，IO 更少
数据冗余 无 key 在非叶子节点冗余，但换来稳定性和范围查询

关键量化：InnoDB 默认页大小 16KB，假设 bigint 主键 8 字节 + 指针 6 字节，一个非叶子节点能存约 16KB/14B ≈ 1170 个 key。三层 B+ 树能存：1170 × 1170 × 16（每叶子节点约 16 行）= 约 2190 万行数据。也就是说，2000 万行数据，查询最多 3 次磁盘 IO，根节点常驻内存的话实际只要 2 次 IO。

二、B+ 树的结构详解

B+ 树是一棵满足以下性质的 m 阶多路平衡树：

  1. 每个节点最多有 m 个子节点
  2. 除根节点外，每个节点至少有 ⌈m/2⌉ 个子节点
  3. 所有叶子节点在同一层（绝对平衡）
  4. 非叶子节点只存 key 和指针，不存数据
  5. 叶子节点存全部 key 和对应数据，且按 key 有序排列，通过双向链表连接

在 InnoDB 中，树的节点对应一个数据页（Page，16KB），节点分裂/合并就是页的分裂/合并，页之间通过指针关联。

三、InnoDB 的索引实现：聚簇索引与二级索引

InnoDB 是索引组织表，数据本身就存在主键索引（聚簇索引）的叶子节点上。

1. 聚簇索引（主键索引）

  • 叶子节点存的是整行数据（row data）
  • 表数据物理上按主键顺序存储
  • 主键查询极快，一次 B+ 树查找直接拿全行

2. 二级索引（普通索引）

  • 叶子节点存的不是数据行，而是主键值
  • 通过二级索引查到主键后，还要回聚簇索引再查一次 → 这叫回表（Bookmark Lookup）

注意：如果二级索引的叶子节点存的是主键而不是行指针，为什么不用行指针？因为行移动（页分裂、碎片整理）会导致行指针失效，而主键值不会变。这也是”InnoDB 建议用自增主键”的原因之一——用 UUID 做主键会让二级索引更大（UUID 16 字节 vs bigint 8 字节），且聚簇索引插入时频繁页分裂。

四、页的内部结构：数据在页里怎么放？

叶子节点的数据页内部结构（简化）：

  • 页内记录通过单向链表按主键顺序连接
  • 页目录采用**二分查找的槽（Slot）**结构，先二分定位到槽，再在槽内顺序扫描，所以页内查找是 O(log n) + 少量线性扫描
  • 记录采用变长格式，NULL 值列表 + 变长字段长度列表优化存储

这些细节解释了为什么 InnoDB 的行要”顺序插入快”：随机插入（如 UUID 主键）会频繁触发页分裂，产生碎片，写放大严重。

五、B+ 树的维护：插入、删除、分裂与合并

插入

  1. 定位到目标叶子节点
  2. 如果节点未满（页内还有空间），直接插入并维持有序
  3. 如果节点已满 → 节点分裂：把一半记录分裂到新页，key 上提到父节点
  4. 父节点如果也满，继续向上分裂，直到根。根分裂时树长高一层

分裂是成本最高的操作，涉及新页分配 + 数据搬移 + 父节点更新，所以：

  • 自增主键顺序插入 → 永远往最右叶子节点追加，几乎不触发中间分裂
  • 随机主键 → 频繁分裂 + 页碎片化 → 性能下降

删除

  1. 定位并删除记录
  2. 如果节点太”空”（低于一半），尝试与相邻兄弟节点合并或从兄弟节点借记录（重新分配）
  3. 合并可能导致父节点 key 减少，极端情况树变矮

页合并与空洞

频繁删除会产生空洞，OPTIMIZE TABLE 可以重建表、整理碎片。

六、B+ 树与查询优化器的配合

  • 范围查询：优化器选择 idx_age 索引，在 B+ 树中找到 age=20 的位置，然后顺着叶子链表向右扫描直到 age=30，一次 IO 连续读多页（预读机制 Prefetch）
  • 最左前缀原则：联合索引 (a, b, c)，查询条件 WHERE a=1 AND b=2 能用到索引，WHERE b=2 用不到。因为 B+ 树先按 a 排，再按 b 排，再按 c 排，跳过了 a 就无法利用有序性
  • 索引下推（ICP）：MySQL 5.6+，把 WHERE 中二级索引能过滤的条件下推到存储引擎层，在索引遍历时就过滤，减少回表次数

七、面试高频追问

Q1：B+ 树一个节点能存多少数据？
默认页 16KB。非叶子节点存 key+指针（约 14B），约 1170 个；叶子节点假设行均 1KB，约 16 行。三层树 ≈ 1170×1170×16 ≈ 2190 万行。

Q2：为什么 B+ 树适合范围查询而 B 树不适合？
B+ 树叶子节点有序且链表相连，范围查询定位起点后顺序扫描即可；B 树的 key 分散在各层节点，范围查询需要反复在树中上下回溯，IO 次数多。

Q3：为什么 InnoDB 推荐自增主键？
① 顺序插入避免页分裂和碎片；② 二级索引叶子存主键，自增主键 8 字节比 UUID 16 字节省空间，索引更小；③ 主键是聚簇索引的排序键，有序性对插入友好。

Q4：辅助索引为什么不直接存行地址？
行地址会随页分裂、合并、行移动而变化，失效后需要更新所有索引；存主键值则永不变化，但代价是回表一次。

Q5：千万级数据为什么还能”快”？
三层 B+ 树即可覆盖千万级数据，根节点常驻 Buffer Pool，实际磁盘 IO 仅 2~3 次；加上页预读、Buffer Pool 缓存，热点查询基本在内存完成。

总结

B+ 树的选择不是偶然：矮（少 IO）、有序（支持范围/排序）、稳定（查找路径恒定）、高扇出（内存友好），完美契合磁盘存储模型。回答这道题时，从”为什么排除二叉树/哈希”切入，再讲清 B+ 树结构 + InnoDB 聚簇/二级索引 + 页分裂维护，最后落到自增主键和覆盖索引等工程实践，就是一个完整且有深度的答案。

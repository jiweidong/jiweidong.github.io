【ES 底层】Elasticsearch 倒排索引与写入原理深度解析：从分词、索引结构到 Lucene 段合并

面试官：ES 为什么搜索那么快？它和 MySQL 的索引有什么区别？

一上来就答「ES 用了倒排索引」只能拿及格分。面试官真正想听的是：倒排索引长什么样、为什么对搜索友好、写入为什么是近实时的、段合并又是怎么回事。本文从 Lucene 底层把这些一次讲透。

一、正排 vs 倒排：搜索为什么必须用倒排？

正排索引（MySQL InnoDB 主键索引）

以文档 ID 为 key，存文档内容。查「包含 Java 的文档」时，只能全表扫描：逐行读内容、逐词匹配，复杂度 O(N)。

倒排索引（ES/Lucene）

反过来，以**词（Term）**为 key，存「哪些文档包含这个词」：

查询「包含 java 的文档」直接定位到 java → [1, 3]，一次哈希/二分查找就拿到结果，复杂度 O(log n) 甚至 O(1)，和数据总量无关 —— 这就是搜索引擎快的本质。

一句话总结：MySQL 索引是「文档 → 词」，适合等值/范围查询；倒排索引是「词 → 文档」，适合包含式检索。两者是互补关系，没有谁取代谁。

二、倒排索引的物理结构：Term Dictionary + Posting List + Term Index

一个 Lucene 倒排索引由三部分组成：

2.1 Posting List：核心数据

每个词对应一个倒排列表，记录：

  • docId：文档 ID（段内自增，非全局）
  • freq：词频（这个词在该文档出现几次，用于相关性打分）
  • position：出现位置（支持短语查询 "java 面试"）
  • offset：字符偏移（支持高亮显示）

2.2 Term Dictionary 与跳表

词典按字典序排列，支持二分查找。Posting List 内部用 Frame of Reference（FOR） 压缩：docId 差值（delta）后按块存储，块内用最小字节数编码 —— 压缩率极高，一个百万级 posting list 可能只有几十 KB。

多词查询（如 java AND spring）时，Lucene 对多个 posting list 做跳表（Skip List）合并：从最小 docId 开始，跳过不可能匹配的区间，交集操作非常快。

2.3 Term Index：FST（Finite State Transducer）

词典本身可能很大（几百万词），全放内存不现实。Lucene 用 FST 构建词的前缀索引：

  • 把「前缀相同的词」合并共享节点，如 java、javascript、javanese 共享 java 前缀；
  • FST 是一种有序的、共享前缀的确定性有限状态机，可以用极少内存表达整个词典的前缀结构；
  • 查询时先在内存 FST 中找到词在词典文件中的近似位置，再落盘做一次精确查找，内存占用小 + 查询快。

这也是 ES 启动时 JVM 堆「不大但很快」的秘诀之一 —— 主要词典结构都在磁盘 + 操作系统的页缓存里，FST 只占很小一部分内存。

三、分词器：倒排索引的「原料车间」

同样是「Java面试」，分词器不同，倒排结果完全不同。分析器（Analyzer）由三部分流水线组成：

以标准分词器分析 "Java & Spring 微服务"：

阶段 输入 输出
Character Filter Java & Spring 微服务 Java & Spring 微服务
Tokenizer Java & Spring 微服务 [java] [&] [spring] [微] [服务]
Token Filter … [java] [spring] [微] [服务]（& 被去停用词，大写转小写）

中文分词是重灾区：ES 默认的 standard 分词器把中文按字切（微/服务 分开），搜「微服务」匹配不上。生产环境必须装 IK 分词器：

  • ik_max_word：最细粒度切分（中华人民共和国 → 中华人民共和国/中华人民/中华/华人/人民共和国/人民/共和国…），适合索引；
  • ik_smart：最粗粒度切分（→ 中华人民共和国），适合搜索。

面试追问：分词器不一致会导致什么问题？
索引分词和查询分词必须一致（或查询词是索引词的子集），否则搜不到。经典案例：索引用 ik_max_word，查询用 standard，搜「微服务」查不到任何结果。ES 默认会复用字段的 analyzer 来分词查询串，自定义 mapping 时务必测试。

四、写入链路：为什么 ES 是「近实时」的？

ES 一次写入请求的完整路径：

关键在「内存段 → 可见」这一步，这就是 refresh：

  • refresh（默认 1s）：把内存 Buffer 中的文档生成一个新的内存段，并打开倒排索引，从此可被搜索。所以 ES 的写入是**近实时（NRT）**的，默认最多延迟 1s；
  • flush（默认 30s 或 translog 满）：把内存段 fsync 落盘、提交 translog 并清空 —— 生成真正的磁盘文件；
  • translog：写入的兜底。节点宕机时，内存段丢失，但 translog 还在，重启后可以重放恢复。

面试追问：为什么 ES 不像 MySQL 一样实时可见？
这是吞吐与实时性的权衡。Lucene 的段是不可变的，每次 refresh 都要新建一个段并打开倒排索引（加载 FST、预热页缓存），如果每条写入都立即 refresh，写放大和 IO 压力巨大。1s 刷新 + 批量写入（bulk）是工程上的最优解。需要秒级可见的搜索（如日志检索）用默认值，追求极致写入吞吐的（如离线导入）可以把 refresh_interval 调到 30s 甚至 -1，导入完再手动 refresh。

五、段（Segment）与段合并：不可变性的代价

Lucene 索引 = 多个不可变段的集合。不可变性带来了巨大好处：

  • 无需加锁，天然并发安全；
  • 可被操作系统页缓存充分缓存，读性能稳定；
  • 崩溃恢复简单（段要么完整存在，要么不存在）。

但代价是更新和删除不是真的改：

  • 更新 = 标记旧文档删除 + 写入新文档；
  • 删除 = 写入一条 tombstone（墓碑）标记，文档暂时还在段里；
  • 查询时被标记的文档会被过滤掉，但磁盘空间不会立即释放。

所以必须段合并（Merge）：后台线程把多个小段合并成大段，物理剔除被删除的文档，真正释放空间。合并策略（merge.policy）默认 tiered：

  • 段大小按层级翻倍（如 1MB、2MB、4MB…），优先合并大小相近的段；
  • 合并过程会占用 IO 和 CPU，indices.store.throttle.type=merge 可限流；
  • 极端情况下合并跟不上写入（段数量爆炸 → 文件句柄过多 → 集群变慢），这是 ES 集群「写多删多」场景的经典故障。

生产建议：大量删除/更新后，对索引执行 POST /my-index/_forcemerge?max_num_segments=1 强制合并（务必在低峰期），可以显著提升查询性能并释放磁盘。

相关性打分默认 BM25：综合词频（TF）、逆文档频率（IDF）和文档长度归一化，本质是「词越稀有、出现越频繁、文档越短 → 分越高」。这也是为什么 ES 能给出「相关度排序」而 MySQL LIKE 只能给「匹配即返回」。

  1. 倒排索引和 B+ 树索引的本质区别是什么？各自适合什么场景？

  8. force merge 有什么风险？为什么要在低峰期做？

小结

ES 快，快在倒排索引的数据结构（词 → 文档、跳表合并、FST 加速）；ES 准，准在分词器的精细控制；ES 稳，稳在段 + translog + 合并这套写入架构。把「写入 → refresh → flush → merge」和「分词 → 倒排 → 打分 → 排序」两条链路讲清楚，ES 的面试基本就稳了。

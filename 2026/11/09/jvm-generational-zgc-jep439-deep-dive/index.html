【JVM 前沿】分代 ZGC（JEP 439）深度解析

前言：ZGC 当年为什么”看起来很美，用起来犹豫”

ZGC 在 JDK 11 实验性引入时就立下了 flag：停顿时间不超过 1ms，且与堆大小、存活对象数量无关。靠的是染色指针（Colored Pointer）+ 读屏障（Load Barrier）+ 并发整理，全部工作都在应用线程运行的同时完成。

但真正把它推上生产的主力服务并不多，原因很实在：吞吐量比 G1 低 5%~15%。

根因只有一个：单代 ZGC 每次 GC 都要考虑整个堆。它没有分代，所有对象混在一起，一次并发标记要遍历全部存活对象；而那些”朝生夕死”的临时对象（Java 服务里 90% 以上都是），会被反复标记、反复参与整理。ZGC 用极低的延迟换来了额外的 CPU 与内存带宽开销，这笔账在 CPU 紧张的容器里往往不划算。

JEP 439（Generational ZGC）就是来还这笔债的：JDK 21 交付，JDK 23 起成为默认模式（JEP 474），JDK 24 直接移除了非分代模式（JEP 490）。也就是说，从 JDK 24 开始，“ZGC”就等于”分代 ZGC”，没有第二个选项。

本文讲清楚四件事：分代 ZGC 在指针与屏障上做了什么改动、Remembered Set 是怎么在没有卡表的情况下维护的、JDK 21 到 24 的参数与默认值演进、以及从 G1 迁移过来的真实调优经验。

一、从单代到分代：改的不只是”分两块内存”

1.1 单代 ZGC 的四色指针

单代 ZGC 的指针里塞了 4 个元数据位：

位 含义
Marked0 本轮标记位 0
Marked1 本轮标记位 1（与 Marked0 交替使用，用于区分不同 GC 周期）
Remapped 该指针已指向对象的最新地址
Finalizable 仅可被 finalize 访问

这四个位加上”多视图映射”（同一份物理内存映射到多个虚拟地址区间），让 ZGC 能在不移动对象的前提下”改变对象的地址”——只需切换指针的颜色位，再让读屏障在访问时把指针”自愈”（self-healing）成新地址。

代价是：ZGC 不能用压缩指针（Compressed Oops），必须 64 位、堆地址对齐，且虚拟地址空间要预留数倍于堆的容量。

1.2 分代 ZGC 只留两个颜色位

分代之后只需要区分”这个引用指向年轻代还是老年代”，于是颜色位从 4 个压缩到 2 个：一个表示年轻代标记，一个表示老年代标记。Remapped 语义被并入”未标记”状态的编码里，Finalizable 位不再需要。

省下来的位不是重点，重点是语义变了：

  • 单代时，颜色位描述的是”这个对象在本轮 GC 里的标记状态”；
  • 分代时，颜色位还要承担”这个引用跨代了吗”的信息，这是维护 Remembered Set 的基础。

1.3 新增写屏障：分代的真正代价

单代 ZGC 只有读屏障，没有写屏障。这是它相比 G1 的一个巨大优势——G1 的写屏障（post-write barrier）要在每次引用赋值时更新卡表，开销不小。

分代 ZGC 必须引入写屏障，原因和所有分代收集器一样：做 Young GC 时只扫年轻代，但老年代对象可能引用年轻代对象，如果不记录这些”跨代引用”，年轻代里那些只被老年代引用的对象就会被误判为垃圾。

ZGC 的选择是：写屏障只做一件极轻的事——判断被写入的引用是否指向年轻代对象，是则把”字段位置”记录到 Remembered Set。快速路径通常只有几条指令（比较 + 条件跳转），慢路径才真正写入。

所以分代 ZGC 的成本结构是：读屏障（每次引用读）+ 写屏障（每次引用写）+ 更小的扫描范围。前三项是纯开销，最后一项是收益。JEP 439 的结论是收益更大——因为年轻代回收极其频繁且存活率极低，扫描范围的缩小幅度远超屏障开销的增加。

二、Remembered Set：没有卡表的方案

G1 用卡表（Card Table）+ RSet 的经典组合：堆按 512 字节切成卡页，写屏障把卡标脏，GC 时扫脏卡。问题是卡表精度低（512 字节一粒）、RSet 内存开销可达堆的 5%~10%，且 RSet 的维护本身需要并发线程。

ZGC 的做法不一样，它用的是基于字段位置的 Remembered Set：

维度 G1 RSet 分代 ZGC RSet
记录粒度 卡页（512B）→ region 字段地址
数据结构 Per-region 稀疏/粗粒度位图 按年轻代 region 组织的位图 + 溢出哈希表
更新时机 写屏障标脏卡，并发线程扫描 写屏障直接记录字段
扫描成本 需先扫脏卡再过滤 直接按字段读取
内存开销 较明显（大堆可达 GB 级） 更紧凑，且只对”指向年轻代”的引用记录

关键点在于：只有指向年轻代的引用才被记录。因为只有 Young GC 需要它，而老年代回收是并发全堆标记，不需要 RSet。这让 Remembered Set 的规模天然受限——它的大小取决于”有多少老年代对象引用年轻代对象”，而不是堆大小。

三、三类回收周期

分代 ZGC 有三种回收动作，全部是并发执行的，STW 只发生在极短的初始标记/最终标记阶段：

3.1 Young Collection（最频繁，收益最大）

  • 只处理年轻代 region；
  • 根集合 = 线程栈 + 静态变量 + RSet 记录的老年代字段；
  • 存活对象晋升到老年代（超过年龄阈值或 region 空间紧张的）；
  • 停顿通常在 0.1~0.5ms 量级。

这是分代带来的核心收益：绝大多数对象的生命周期在几十毫秒内结束，一次 Young Collection 就能清掉，永远不会进入老年代，也就永远不会被全堆标记碰到。

3.2 Old Collection（频率低，成本高）

  • 并发标记整个老年代（含年轻代作为根）；
  • 并发重定位（Relocation）；
  • 停顿同样在亚毫秒级，但总 CPU 时间与堆大小成正比，所以频率必须控制。

3.3 Full GC（最后手段）

只剩一种触发场景：分配速率超过回收速率，堆真的满了。这时 ZGC 会退化为 STW 的全堆压缩——这正是你绝对不想看到的场景，因为分代 ZGC 的 Full GC 是单线程/少线程的保守实现，可能长达数秒。

判断标准：分代 ZGC 的调优目标不是”减少 Full GC 次数”，而是让它一次都不要发生。只要发生一次，就说明堆太小或分配速率失控。

四、JDK 21 → 24 的参数与默认值演进

JDK 启用方式 说明
21 -XX:+UseZGC -XX:+ZGenerational 分代模式需显式开启，单代仍是默认
22 同上 分代 ZGC 持续打磨，单代仍默认
23 -XX:+UseZGC 分代成为默认（JEP 474），-XX:-ZGenerational 可退回（已废弃）
24 -XX:+UseZGC 非分代模式被移除（JEP 490），ZGenerational 相关参数成历史

常用参数（分代模式）：

逐个说人话：

  • -Xms = -Xmx：ZGC 的堆管理依赖连续地址与多视图映射，动态伸缩收益极小，固定堆能避免页分配抖动。
  • -XX:SoftMaxHeapSize：软上限，GC 会努力把堆控制在这个值以下，但允许短时冲高。这是容器里最值得设的参数——比硬 -Xmx 提前触发回收，避免撞上 cgroup limit 被 OOMKill。
  • -XX:ConcGCThreads：并发 GC 线程数，默认约为 CPU 核数的 1/4。容器里一定要显式设置：JVM 看到的是节点核数还是 cgroup quota，取决于 UseContainerSupport 与内核版本，设错会出现”GC 线程和业务线程抢 CPU”或”GC 跟不上分配”。
  • -XX:ZUncommitDelay：空闲内存归还操作系统的延迟，默认 300s。容器里可以调小让 RSS 降下来，但太激进会导致反复 mmap/munmap。
  • 不要设 -Xmn / -XX:NewRatio：ZGC 的分代比例由 GC 自适应，这两个参数对它没有意义。

单代时代的 -XX:ZAllocationSpikeTolerance、-XX:ZProactive 等旋钮在分代模式下已经不适用，网上老文章里的调优建议要打折扣看。

五、从 G1 迁移：一份可执行的清单

我们一个 40 万 QPS 的网关服务，JDK 17 + G1 → JDK 21 + 分代 ZGC，整个过程分五步。

第一步：确认容器与指针压缩

第三步：打开正确的日志与 JFR

ZGC 的 JFR 事件很关键：

JFR 事件 用途
ZYoungGarbageCollection 年轻代回收次数、耗时、回收量
ZOldGarbageCollection 老年代回收次数，频率异常升高是危险信号
ZAllocationStall 分配停顿（堆满），出现即事故
ZPageAllocation 页分配/归还，判断是否有内存碎片或频繁伸缩
ZUncommit 内存归还，容器 RSS 曲线解释

⚠️ jstat -gcutil 对 ZGC 参考价值很低（S0/S1/E 列的语义与分代收集器不同），别拿它判断 ZGC 健康度，以 -Xlog:gc 和 JFR 为准。

第四步：压测对比

我们的实测数据（同机同流量，P99 与吞吐）：

指标 G1（JDK 17, 16G） 分代 ZGC（JDK 21, 20G）
吞吐（QPS） 38.2 万 40.1 万
P50 延迟 4.1ms 3.6ms
P99 延迟 62ms 21ms
P999 延迟 380ms 34ms
最大 STW 210ms 0.4ms
CPU 使用率 62% 68%
RSS 18.2GB 22.6GB

结论和官方口径一致：吞吐略升（因为扫的少了），延迟大幅改善，代价是 CPU +6% 和内存 +20%。如果你的服务是 CPU 瓶颈型（比如大量计算、序列化），迁移前务必确认还有 CPU 余量。

第五步：灰度与回滚

  • 按 5% → 25% → 50% → 100% 灰度，每档至少观察一个完整流量高峰；
  • 回滚方案就是换 JVM 参数 + 重启（ZGC 与 G1 的堆布局不兼容，不能热切）；
  • 重点盯三个指标：P999、ZAllocationStall 次数、容器 RSS。

六、五个真实踩过的坑

坑 1：容器 CPU limit 掐住了并发 GC。
把 ConcGCThreads 留在默认值，8 核节点上 JVM 开了 2 个并发 GC 线程，但容器 quota 只有 2 核，GC 线程和业务线程抢 CPU，结果 GC 永远追不上分配，出现 ZAllocationStall。解决：ConcGCThreads 按 quota 核数 设置（比如 quota 2 核就设 1），并把 -XX:ActiveProcessorCount 显式对齐。

坑 2：-Xmx 贴着 cgroup limit 设。
-Xmx16g 而容器 limit 是 16Gi，JVM 自身的元空间、线程栈、DirectBuffer、代码缓存还要几个 GB，必然 OOMKilled。经验值：-Xmx ≤ limit × 0.75，且用 SoftMaxHeapSize 做软刹车。

坑 3：把 -XX:+AlwaysPreTouch 和 ZGC 一起用在小容器里。
PreTouch 会在启动时把整个堆的物理页都摸一遍，容器里会导致启动慢 + 内存瞬时冲高被 OOMKill。只在内存充足的宿主机部署时开。

坑 4：以为 ZGC 不需要关心分配速率。
ZGC 的暂停与堆大小无关，但吞吐与分配速率强相关。一个每秒产生 3GB 垃圾的服务，无论用什么 GC 都在做无用功。用 JFR 的 ObjectAllocationSample 找出分配热点，往往能省掉一半的 GC 压力。

坑 5：忽略虚拟地址空间。
ZGC 的多视图映射会预留数倍于堆的虚拟地址空间。在 32 位受限环境、或设置了 ulimit -v 的容器里，会出现”内存够但 mmap 失败”。检查 ulimit -v 与 vm.max_map_count。

七、面试追问

Q1：分代 ZGC 为什么比单代 ZGC 吞吐高，明明多了写屏障？
因为扫描工作量下降的幅度远大于屏障开销。单代每次 GC 都要并发标记全堆存活对象；分代后 Young Collection 只扫年轻代（存活集小、频率高），老年代回收频率大幅降低。写屏障的快速路径只有几条指令，而节省的是整堆标记的 CPU 与内存带宽。

Q2：ZGC 的读屏障到底做了什么？为什么叫”自愈”？
读屏障在每次从堆里加载引用时执行：检查指针的颜色位，如果指向对象已被移动（颜色为”旧”），就用转发信息把指针修正为新地址并写回原字段（self-healing），然后返回正确引用。这样”修正”只需要做一次，后续读都是快路径。

Q3：为什么 ZGC 不支持压缩指针？
压缩指针依赖”对象地址 = 基址 + 32 位偏移”，而 ZGC 需要指针里空出多位存放颜色标记，且要求堆可以被映射到多个虚拟地址区间。两者在地址编码上直接冲突。

Q4：分代 ZGC 的 RSet 会不会像 G1 一样吃内存？
不会到那个量级。G1 的 RSet 记录的是”哪个 region 指向我”，粒度是 region，大堆下累积可达 GB 级；ZGC 只记录”指向年轻代的字段地址”，且只服务 Young GC，规模只与跨代引用数量相关，与堆总大小弱相关。

Q5：什么场景不该用 ZGC？

  • 极致吞吐优先的离线批处理（Parallel GC 更合适）；
  • CPU 极度受限（quota < 2 核）且延迟要求不高的服务；
  • 堆很小（< 2GB）且延迟本就达标——ZGC 的复杂度换不来收益，G1 更省心；
  • 依赖大量 JNI/Unsafe 直接操作对象地址的老代码（染色指针会让裸地址失效）。

Q6：ZGC 能消除所有停顿吗？
不能。仍有：初始标记/最终标记的 STW（亚毫秒）、safepoint 同步、ZAllocationStall（堆满时的分配阻塞，可能几十毫秒）。ZGC 承诺的是”停顿与堆大小无关”，不是”零停顿”。

八、总结

分代 ZGC 是 JVM 近几年最重要的工程成果之一，它的意义不在于”延迟又低了一点”，而在于把 ZGC 从”演示级低延迟”变成了”可以无脑默认的生产级 GC”：

  1. JDK 21 起步：-XX:+UseZGC -XX:+ZGenerational，值得在延迟敏感服务上试点；
  2. JDK 23/24 之后：分代是唯一模式，迁移成本从”要不要”变成”什么时候”；
  3. 迁移三件事：堆 ×1.3 起步、CPU 留 10% 余量、ConcGCThreads 按 quota 设；
  4. 三个红灯：ZAllocationStall 出现、ZOldGarbageCollection 频率飙升、Full GC 发生；
  5. 别迷信参数：ZGC 的设计哲学是”少调参”，真正有效的优化永远是减少分配。

下一次有人问你”ZGC 能不能上生产”，你可以这么回答：JDK 21 可以试，JDK 23 之后可以默认上；但要先确认你的 CPU 有 10% 余量、内存有 30% 余量，并且你愿意为 P999 从 380ms 降到 34ms 付这笔钱。

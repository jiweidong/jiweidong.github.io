【系统设计】A/B 实验平台架构设计：流量分桶、指标计算与显著性检验全解析

面试官：设计一个 A/B 实验平台，让产品经理能自己配置实验

这是一道考工程架构 + 数据统计 + 业务理解的综合题。它不像”设计秒杀”那样有标准答案，面试官真正在观察的是：

  • 你知不知道实验平台的核心是分流而不是”配置界面”？
  • 你分得清 AA 实验、样本量、显著性 这些统计概念吗？
  • 你能不能说出”同一用户必须稳定命中同一个实验组”这种工程约束？

下面按面试节奏，从需求澄清到落地细节，完整推一遍。

一、需求澄清：先问清楚再设计

Q1：实验的粒度是什么？ 用户级、设备级、请求级、还是租户级？绝大多数是用户级（同一用户在一次实验周期内体验一致）。

Q2：一个用户能同时参与几个实验？ 通常分层（Layer）后可以几十个，但同一层内的多个实验必须互斥。

Q3：指标谁来定义？ 产品定义业务指标（点击率、转化率、GMV），平台提供指标计算框架。

Q4：QPS 和延迟要求？ 分流是在线链路，必须做到毫秒级、高可用——实验系统挂了不能影响主站。

Q5：谁能看到什么？ 实验数据权限隔离，避免”产品看到别组的中间结果去干预实验”（这是实验泄露）。

二、整体架构

核心思想：在线分流与离线计算彻底解耦。

  • 在线：只做”一锤定音”的分流，越简单越快越好；
  • 离线：采集曝光、关联行为、算指标、跑统计。

三、分流设计：这是实验平台的灵魂

3.1 哈希分桶

核心公式：

  • salt：每个实验独立的盐，保证同一用户在实验 A 和实验 B 的分布相互独立（避免实验间相关性）；
  • 10000：分桶精度，即支持 0.01% 的最小流量粒度；
  • userId：分桶主体，必须稳定（登录用户用 uid，未登录用设备 ID）。

为什么用 MurmurHash 而不是 hashCode()？ Java 的 String.hashCode() 分布不够均匀，且不同 JVM 版本实现可能变化（虽然实际稳定），更重要的是容易被构造出碰撞。生产用 MurmurHash3 或 xxHash。

3.2 分层（Layer）与互斥（Domain）

实验平台必须支持两种正交关系：

机制 解决的问题 实现
分层 Layer 让多个实验可以同时跑在同一个用户身上 不同层用不同 salt，哈希独立
互斥 Domain 让同域内的实验不能同时命中 同域共用一个 salt，按流量区间切分

面试加分点：能说出”不同层之间必须相互独立，同一层内必须互斥“，并用”正交分层 / 互斥域”这两个词，立刻拉开差距。

3.3 流量扩大：慎之又慎

实验从 1% 扩到 10% 时，绝不能改变已命中用户的组别。正确做法是：扩流只把”原先未命中的用户”纳入，已命中的保持原组。这就要求变体的流量区间是”前缀式”扩展：

3.4 在线分流的可用性设计

分流是主链路，必须做到：

  1. SDK 本地缓存：实验配置全量缓存在应用内存，分流不上网，纯本地计算；
  2. 配置推送：通过配置中心长轮询（Apollo/Nacos）或推送，秒级生效；
  3. 兜底策略：配置拉取失败时走对照/默认值，绝不阻塞业务；
  4. 降级开关：实验平台故障时一键全量回滚到原始逻辑；
  5. 防超时：任何远程调用都设 50ms 超时，宁可降级不可拖慢。

四、数据采集：曝光与行为要能关联

分流之后必须回答：”这个用户到底看到了什么，然后做了什么？“

4.1 两类数据

  • 曝光日志（Exposure）：user_id, experiment_key, variant, timestamp, page, ...
  • 行为日志（Action）：user_id, action_type, value, timestamp, ...（点击、下单、支付）

4.2 采集原则

  1. 异步上报：业务线程只写本地队列/Dispatchers，后台批量发送到 Kafka；
  2. 不阻塞：采样率可调（如 10% 抽样），但实验组和对照组采样率必须一致，否则数据有偏；
  3. 幂等：同一用户同一实验重复曝光要去重（按 userId + expKey + variant + 天）；
  4. 不丢：本地落盘兜底，进程重启后补传。

五、指标计算：从明细到结论

5.1 实验指标分层

层级 指标 说明
北极星指标 GMV、留存 实验最终要看的目标
核心指标 转化率、人均订单数 直接反映实验效果
护栏指标 崩溃率、P99 延迟、负反馈率 必须不劣化，防止”提升转化但搞崩性能”
探索指标 点击分布、停留时长 辅助归因

面试必说：护栏指标（Guardrail Metrics） 是很多候选人的盲区。没有护栏指标，实验可能”赢了指标输了体验”。

5.2 SQL 计算示例（ClickHouse）

指标计算的三个正确姿势：

  1. 分母用 UV 不是 PV：转化率的分母必须是”曝光去重用户数”；
  2. 归因窗口：定义”曝光后多久内的行为算数”（如 7 天内下单），窗口不一致没法比；
  3. 实验中新增用户剔除：只统计实验开始前就存在的用户，避免样本污染。

六、显著性检验：A/B 测试的科学性

6.1 假设检验框架

  • 原假设 H₀：实验组与对照组无差异；
  • 备择假设 H₁：存在差异；
  • p 值：在 H₀ 成立时，观测到当前（或更极端）结果的概率；
  • 显著性水平 α = 0.05：p < 0.05 时拒绝 H₀，认为差异显著。

6.4 样本量：实验开始前必须算

这是面试的关键分点。样本量不够就跑实验，等于抛硬币。

  • Δ：最小可检测效应（MDE），如”能检测出 2% 的提升”；
  • σ：指标标准差（历史数据估算）；
  • β：第二类错误概率，通常取 0.2（统计功效 = 80%）。

经验值：日活 10 万、转化率 5%、想检测 5% 的相对提升，大约需要 1~2 周。产品经理总想”跑三天看结果”，你要能拿公式怼回去。

6.5 常见统计陷阱

陷阱 后果 规避
多次偷看（Peeking） 显著性被人为放大，假阳性飙升 固定实验周期，或用序贯检验
多重比较 测 20 个指标必有一个”显著” Bonferroni 校正 / FDR
Simpson 悖论 整体看 A 好，分层看 B 好 分层分析、检验分流均衡性
AA 实验失败 分流有偏，一切结论无效 实验前跑 AA 实验验证
幸存者偏差 只看完成实验的用户 用 ITT（意向性分析）

6.6 AA 实验：上线的准入门槛

任何实验平台上线前，必须能跑通 AA 实验：把流量随机分成两组，施加完全相同的策略，结果应该不显著（p > 0.05）。如果 AA 实验就显著，说明分流不均匀或埋点有问题。

AA 实验是对整个平台的体检：哈希算法、分桶、埋点、指标计算、统计方法，任何一个环节有偏都会暴露。

七、实验生命周期管理

工程要点：

  1. 审批流：高风险实验（改动核心链路）需要评审；
  2. 一键回滚：发现护栏指标劣化，秒级停止实验；
  3. 实验互斥检查：创建时自动检测是否与运行中的同域实验冲突；
  4. 实验快照：记录每个实验的配置、时间、参与人，可复现；
  5. 元数据版本：配置改动要留历史，否则报表口径会漂。

八、面试高频追问

追问一：分流为什么不放在服务端统一做？

可以，但服务端统一分流会引入网络调用到主链路，延迟与可用性都是问题。业界主流是SDK 本地分流 + 配置下发，把决策成本降到纳秒级。

追问二：用户 ID 不稳定怎么办（未登录）？

用设备 ID（deviceId）；若 deviceId 也没有，用 IP + UA 哈希（不推荐，分布会偏）。关键原则：同一次实验周期内，分桶主体必须稳定。

追问三：如何避免实验相互干扰？

正交分层（Layer）。不同层用不同 salt，使各层分桶独立；需要互斥的实验放同一域（Domain）。

追问四：实时报表还是离线报表？

都要。实时报表（Flink + OLAP）给产品看趋势、及时止损；离线报表（T+1）做精确统计与显著性检验。实时数据做决策要慎重，易被短期波动误导。

追问五：实验平台的 QPS 有多大？

按 DAU 1 亿、人均 100 次曝光估算，曝光上报约 10 万 QPS，必须走 Kafka 削峰 + 采样；而分流本身是本地内存计算，QPS 等同于业务 QPS，不构成瓶颈。

追问六：怎么防止实验数据被”选择性汇报”？

① 平台强制展示所有预设指标，不允许只挑显著的；② 实验注册时冻结指标口径；③ 审批流 + 只读报表，杜绝”看到好结果才上报”。

九、总结

A/B 实验平台的本质是四件事：

  1. 分流要稳：哈希分桶 + 正交分层 + 互斥域 + 前缀扩流，保证同一用户稳定命中；
  2. 采集要准：曝光与行为异步上报、幂等去重、实验组与对照组采样一致；
  3. 计算要对：UV 作分母、定义归因窗口、剔除新增用户、护栏指标兜底；
  4. 结论要科学：先算样本量、跑 AA 实验、防偷看与多重比较。

一句话收尾：实验平台不是”配置页面 + 报表”，而是一套”从分桶到统计”的因果推断基础设施。 在线分流决定谁看到什么，离线计算决定能不能下结论，两者缺一，实验就是在自欺欺人。

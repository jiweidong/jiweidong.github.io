【系统设计】实时风控系统架构设计：规则引擎、名单体系、滑动窗口与流式特征计算

面试官：你们的交易/登录/营销活动怎么防刷？设计一个实时风控系统

风控系统是很多后端工程师”知道很重要但没系统做过”的领域。它的难点不在于单个技术点，而在于架构分层、规则的可扩展性、以及实时性与准确性的平衡。

这篇文章从零搭建一个可落地的实时风控系统。

一、风控的本质：在 100ms 内判断”这个请求是不是坏人”

风控系统的基本形态是一个同步决策接口：

它的输入通常是：

  • 主体：用户 ID、设备指纹、IP、手机号、身份证哈希
  • 行为：登录、下单、支付、领券、抽奖、发帖、改密码
  • 上下文：时间、地理位置、网络环境、历史行为

核心挑战：

  1. 低延迟：风控挂在主链路上，超时就等于业务不可用。
  2. 高召回：宁可错杀，不可放过（但要控制误杀率）。
  3. 可解释：被拒的用户要能说清楚为什么被拒。
  4. 可演进：黑产每天都在变，规则必须能小时级上线。

二、整体架构

关键设计原则：

  • 决策服务无状态，可以水平扩容。
  • 多数据源并行获取，用超时控制（比如 30ms 拿不到特征就用默认值）。
  • 超时降级为放行（fail-open），但异步记录，事后补偿。这是风控与业务可用性的取舍：登录接口因为风控超时而拒绝所有用户，损失远大于漏过几个黑产。

三、名单体系：最便宜也最有效的第一道防线

名单是风控里性价比最高的部分：O(1) 判断，效果立竿见影。

3.1 名单类型

名单 用途 存储
黑名单 直接拒绝 Redis Set / 布隆过滤器
白名单 直接放行（内部员工、测试账号） Redis Set
灰名单 静默拦截（不告知用户） Redis Set
设备名单 设备维度封禁 Redis Set + 布隆过滤器

3.2 布隆过滤器：亿级名单的内存神器

黑名单可能有上亿条，全放 Redis Set 内存扛不住。布隆过滤器用极小空间换”可能存在”的判断：

特点：

  • 可能有假阳性，不会有假阴性。所以布隆过滤器命中后还要查一次 Redis/DB 二次确认。
  • 不支持删除。要删除元素，用 Counting Bloom Filter 或 Redis 的 BF.DEL（RedisBloom 模块）。

实践中的组合是：

用布隆过滤器做前置，可以把 99% 的正常请求挡在廉价判断上，只有少量请求需要查精确存储。

四、规则引擎：让规则可配置、可热更新

风控规则如果写死在代码里，每次调整都要发版，黑产早就跑完了。所以需要一个规则引擎。

4.1 方案对比

方案 优点 缺点 适用
硬编码 if-else 性能最好 不可配置 极少数核心规则
SpEL / Aviator 表达式 轻量、易用 复杂逻辑难维护 简单规则
Drools 功能强、DRL DSL 重、学习成本高 复杂规则集
自研 DSL + 决策树 完全可控 开发成本高 大厂常见

4.2 规则模型

一条规则通常包含：条件 + 动作 + 优先级 + 生效时间：

执行流程：按优先级顺序求值，命中即返回（first-match），或全部执行累加风险分（score-based）。

4.3 规则热更新

  • 规则存在 DB / 配置中心，决策服务本地缓存 + 长轮询/推送刷新。
  • 规则变更要有灰度：先对 1% 流量生效，观察误杀率再全量。
  • 每次决策记录 ruleId + ruleVersion，便于回溯。

五、特征计算：滑动窗口是核心

风控规则大多依赖”最近一段时间内的行为统计”，例如：

  • 最近 1 分钟登录次数
  • 最近 1 小时下单金额
  • 最近 24 小时不同设备数
  • 最近 10 分钟同 IP 注册数

5.1 Redis ZSet 实现滑动窗口

用 ZSet 存事件时间戳，ZREMRANGEBYSCORE 清理过期，ZCARD 统计数量：

为什么 member 要用 now + 随机后缀？因为 ZSet 的 member 唯一，同一毫秒的多条事件如果 member 相同会被覆盖，导致计数偏小。

5.2 高效变体：分桶计数

ZSet 存全量事件在超高频场景内存消耗大。更好的做法是时间分桶：

统计最近 5 分钟 = 当前桶（部分）+ 前 4 个完整桶。用 Redis Pipeline 一次取回，或者用 MGET。

分桶法的误差最多是”一个桶的时间粒度”，对风控来说完全可以接受，但内存和 CPU 成本远低于 ZSet。

5.3 流式特征：Flink 窗口聚合

流式计算负责离线/近线产出宽表特征，在线决策只做读取，这样在线链路始终是 O(1) 查询。

6.2 后置闭环：异步归因与模型迭代

风控不能只看当下。用户被放行后，行为可能在一段时间后才被确认为恶意（比如拒付、投诉、投诉成功）。所以要有：

  1. 异步回填：把决策结果和后续真实标签关联，形成训练样本。
  2. 离线评估：每天跑一次”如果新规则上线，历史流量会误杀多少、拦截多少”。
  3. 对抗演进：黑产绕过规则后，及时补充特征和规则。

这也是黑名单”动态化”的来源：今天放行的设备明天可能进黑名单。

七、高频追问

追问 1：风控超时了怎么办？

  • 主链路用超时 + fail-open：拿不到决策就放行，异步补记。
  • 对高风险操作（如大额支付）可以 fail-close（拒绝并要求二次验证）。
  • 关键是区分业务，不能一刀切。

追问 2：如何降低误杀？

  • 分层决策：低风险直接放行，中风险挑战（验证码），高风险拒绝。
  • 白名单与”老用户信任”机制。
  • 规则灰度 + A/B 测试，用数据说话。
  • 人工审核兜底 + 申诉通道。

追问 3：规则冲突怎么办？

  • 优先级（priority）决定执行顺序。
  • 明确”first-match”还是”score 累加”语义，不要混用。
  • 规则上线前做冲突检测（比如同一条件下两个规则给出相反结论）。

追问 4：怎么保证风控不影响主链路性能？

  • 决策服务独立部署，与业务服务物理隔离。
  • 特征本地缓存 + Redis 二级缓存。
  • 全链路超时预算：网关 500ms → 业务 200ms → 风控 50ms。
  • 熔断降级：风控不可用时，业务侧自动放行并告警。

追问 5：设备指纹怎么做？

服务端可以采集 UA、屏幕分辨率、时区、字体、Canvas/WebGL 指纹、IP、TLS 指纹等，组合生成设备 ID。注意合规：需要用户授权，且不能过度采集个人敏感信息。

八、总结

实时风控系统的骨架可以记成四句话：

  1. 名单先行：布隆过滤器 + 精确存储，O(1) 拦截大量风险。
  2. 规则可配：DSL/引擎 + 热更新 + 灰度，让风控跟得上黑产。
  3. 特征实时：滑动窗口（Redis）负责在线，Flink 负责近线宽表。
  4. 闭环演进：异步归因 + 离线评估，让系统越用越准。

风控的本质是在有限的延迟预算里，用最便宜的手段做最优决策。理解了这个 trade-off，架构自然就清晰了。

【系统设计】推荐系统架构设计：召回、粗排、精排、重排与实时特征全解析

面试官：如果让你设计一个推荐系统，你会怎么架构？

很多人对推荐系统的第一反应是「算法问题」，于是开始背协同过滤、双塔模型、Transformer……但面试官真正想考的，是一个 Java 后端工程师能不能把算法模型工程化成一个高可用、低延迟、可迭代的系统。

推荐系统的本质是一个漏斗（funnel）：从千万级物品里，用越来越复杂的模型，逐层筛到几十个最终展示结果。系统设计的核心矛盾是：

候选集越大，效果越好；但延迟预算只有 100~200ms。

这篇文章按「分层漏斗 + 工程实现」两条线，把推荐系统的架构讲透。算法只讲「工程上必须知道的接口」，重点放在架构、存储、缓存、降级和一致性上。

一、整体架构：四阶段漏斗

每一层的目标都可以用一句工程话概括：

阶段 输入规模 输出规模 延迟预算 核心诉求
召回 千万~亿 1k~5k 20~50ms 高吞吐、全量覆盖
粗排 1k~5k 100~500 10~20ms 低成本、快速裁剪
精排 100~500 10~50 20~50ms 精度优先
重排 10~50 N <5ms 业务规则、多样性

延迟预算是硬约束：所有阶段的耗时加起来必须小于整体的 SLA。实践中通常给整条链路设 200ms 超时，各阶段再分配子预算。

二、召回层：从海量到千级

召回的目标是在保证不遗漏高价值候选的前提下，把量级压到后面能处理的范围。常见召回通路：

召回类型 原理 工程实现 特点
热门召回 全局/分时段 Top-N Redis ZSet 新用户兜底、高时效
协同过滤 i2i 看过 A 的人也看 B 离线产出 i2i 倒排 效果好、覆盖广
协同过滤 u2i 相似用户喜欢的物品 用户向量 + ANN 个性化强
内容召回 标签/类目匹配 倒排索引 / ES 冷启动友好
向量召回 双塔 embedding + 近邻检索 Faiss/Milvus/HNSW 主流、可学习
规则召回 运营配置 配置中心 + 规则引擎 可控、可解释
新品/探索召回 给新内容曝光 时间窗口过滤 解决马太效应

多路召回的并行编排

多路召回天然适合并行。工程上有两种实现：

方案 A：CompletableFuture 并行 + 超时

关键设计：

  • 线程池隔离：每路召回一个独立线程池，避免一路慢拖垮全部（参考 microservice-bulkhead-isolation）。
  • 超时降级：单路超时返回空，整体不受影响。
  • 单路熔断：某路持续失败时熔断，直接跳过（Sentinel/Resilience4j）。

方案 B：异步回调 / 响应式，适合超高 QPS 场景。

去重与截断

多路召回结果需要：

  1. 去重：用 itemId 做去重，通常用 LongOpenHashSet 或布隆过滤器（注意布隆有误判，召回场景要慎用——误判会丢失候选）。
  2. 分路配额：不能一路召回量过大把其他路「挤掉」，需要按路限制条数。
  3. 粗筛：过滤下架、无库存、重复、已读、屏蔽等。

三、特征工程：实时特征是成败关键

推荐系统的效果，特征 > 模型结构。特征分为三类：

特征类型 举例 存储 更新频率
用户特征 性别、年龄、长期兴趣向量 KV（Redis/HBase） 天级/小时级
物品特征 类目、标签、统计值（CTR/CVR） KV + 本地缓存 小时级
上下文特征 时间、位置、设备、网络 请求内计算 实时
实时行为特征 最近点击序列、实时偏好 流式计算 + KV 秒级

实时特征链路

工程要点：

  1. 特征一致性（online-offline consistency）：离线训练用的特征和在线推理用的特征必须口径一致，否则模型效果暴跌。常见做法是统一的特征仓库（Feature Store），离线/在线共用同一套特征计算逻辑。
  2. 特征回填：新模型上线需要历史样本，特征要能按时间点回放（point-in-time correctness），避免特征穿越（data leakage）——用了未来的数据训练。
  3. 特征版本化：特征定义变更要有版本，模型与特征版本绑定。
  4. 实时特征降级：Redis 挂了怎么办？必须有兜底（用离线特征/默认值），否则整个推荐服务不可用。

特征读取的性能优化

精排阶段几百个候选 × 几百维特征，如果每个候选都回一次 Redis，延迟立刻爆炸。工程做法：

  • 批量读取：MGET / Pipeline 批量拉取用户和物品特征；
  • 本地缓存 + 广播：物品特征变化慢，用 Caffeine 本地缓存，配合 Redis Pub/Sub 广播失效（参考 caffeine-multi-level-cache-practice）；
  • 特征预取与复用：用户特征一次拉取，全候选复用；物品特征按 itemId 批量拉。

四、排序层：粗排与精排

粗排（Coarse Ranking）

目标：用极低的成本把几百上千候选裁到百级。

  • 模型：双塔（用户塔 + 物品塔，向量点积即分数）、GBDT、线性模型；
  • 特点：可以离线预计算物品向量，在线只需算用户向量 + 点积，延迟极低；
  • 实现：向量检索（Faiss/HNSW）或直接矩阵运算。

精排（Fine Ranking）

目标：多目标预估（CTR、CVR、时长、点赞、收藏……）。

  • 模型：DeepFM / DIN / MMoE 等多任务模型；

  • 工程：模型服务化（TF Serving / Triton / 自研推理服务），特征拼接在 Java 侧完成，模型只做前向计算。

Java 侧与模型服务的边界

这是面试里很容易被追问的点：Java 工程师在推荐系统里做什么？

  1. 特征组装：从 Redis/HBase 拉取特征，拼成模型输入的 tensor（通常用 protobuf/Arrow 序列化）；
  2. 模型服务调用：gRPC 调用推理服务，带超时和降级；
  3. 打分编排：并发调用、结果合并、异常兜底；
  4. 打分缓存：热门用户/物品的组合分数可缓存；
  5. 降级策略：模型服务挂了，退化为规则排序或热门排序。

五、重排：业务价值集中地

重排是唯一能快速上线、见效明显的层，因为它不需要训练模型：

策略 作用 实现
去重 同一物品/同一作者不重复 滑动窗口 + 作者计数
打散 避免同类目连续出现 类目间隔控制
多样性 提升整体点击率 MMR / DPP 算法
强插 运营/广告指定位置 位置插槽
保量 保证某些内容曝光 配额控制
新鲜度 提升新内容曝光 时间衰减
冷启动 新用户探索 ε-greedy / 汤普森采样

六、可用性与一致性设计

推荐系统是**「有损可接受」**的系统：推荐降级为用户看到热门内容，体验下降但服务不能挂。这决定了它的高可用策略和交易系统完全不同。

分级降级

每一级都必须有兜底数据，且兜底数据要预热在本地缓存里（不能依赖可能已挂的 Redis）。

缓存策略

数据 缓存位置 说明
热门榜单 本地缓存 + Redis 变化慢，多级缓存
用户画像 Redis 用户维度，TTL + 主动更新
物品特征 本地缓存 + Redis Pub/Sub 失效 读多写少
召回结果 （谨慎）不强缓存 高度个性化，命中率低
最终结果 短 TTL 缓存（秒级） 缓解热点用户 QPS

热点问题：头部用户/明星物品会产生热 Key（参考 redis-big-key-hot-key-deep-dive）。治理手段：本地缓存、Key 打散（多副本 + 随机后缀）、请求合并。

容灾

  • 多机房部署：推荐服务无状态，可多机房部署 + 就近路由；
  • 兜底开关：配置中心一键「关闭个性化，全部走热门」，用于算法出问题时的紧急止血；
  • 模型灰度：新模型按用户/流量比例灰度，效果不达标自动回滚。

七、可观测性与效果闭环

推荐系统必须能被「看懂」，否则无法迭代。

指标体系

层次 指标
系统指标 QPS、P99 延迟、错误率、各阶段耗时分布、线程池队列长度
业务指标 CTR、CVR、人均时长、曝光量、多样性
算法指标 各召回通路命中率、模型打分分布、特征缺失率
数据指标 特征覆盖率、样本延迟、特征一致性校验

埋点与反馈

归因：点击要能追溯到「哪次请求、哪条推荐、哪个实验」，这要求推荐结果带上 traceId + experimentId + rankInfo。

AB 实验

任何排序/策略变更都要经过 AB 实验（参考 ab-testing-experiment-platform-architecture-design）。工程上需要：

  • 流量分桶（用户级哈希，保证同一用户分桶稳定）；
  • 分层实验（召回层、排序层、重排层可独立实验，互不干扰）；
  • 实验指标实时看板 + 显著性检验。

八、数据存储选型

用途 选型 理由
用户画像 / 特征 Redis（热）+ HBase/Redis 集群（全量） 低延迟 KV
倒排索引（i2i） Redis / 本地内存 / LevelDB 高吞吐读取
向量检索 Milvus / Faiss / Elasticsearch kNN ANN 近邻
行为日志 Kafka + HDFS/S3 高吞吐写入
离线特征 Hive / Spark 数仓 批量计算
正排（物品信息） MySQL + 本地缓存 强一致、低频变更
实时特征 Kafka + Flink + Redis 秒级更新

核心设计原则：在线读走内存型存储，离线算走批量计算，中间用 Kafka 解耦。

九、面试常见追问

Q1：召回为什么不用精排模型直接打全量？

因为延迟和算力。千万级候选 × 深度模型 = 秒级甚至分钟级延迟，完全不可接受。漏斗的本质是「算力预算的分配」。

Q2：冷启动怎么解决？

新用户：热门召回 + 上下文召回（地理位置、时间）+ 快速试探（ε-greedy/汤普森采样）快速积累兴趣；新物品：内容召回（标签匹配）+ 探索流量池 + 保证曝光配额。

Q3：如何保证推荐结果的多样性？

重排层做打散（类目/作者间隔）、MMR/DPP 做多样性优化、控制相似物品的曝光上限。

Q4：实时特征和离线特征不一致怎么办？

统一的 Feature Store，在线用同一套逻辑计算，离线用同一套逻辑回放；加上一致性校验任务（对比同一时刻在线/离线特征值）。

Q5：推荐服务挂了会怎样？

分级降级到热门/兜底内容。这是设计时就要内置的能力，不是事后补的。

Q6：怎么衡量推荐系统做得好不好？

短期看在线指标（CTR/CVR/时长），长期看生态健康（多样性、创作者生态、用户留存）。过度优化短期指标会导致「信息茧房」和内容同质化。

十、总结

推荐系统架构可以浓缩成一张图：

作为 Java 后端工程师，你需要牢牢抓住三点：

  1. 漏斗思维：每层的规模、延迟预算、成本要清晰；
  2. 特征工程：在线离线一致性、实时特征链路、读取性能优化；
  3. 降级与可观测：有损可接受，但必须分级降级 + 全链路可观测 + 能灰度回滚。

算法决定效果上限，但工程决定你能不能稳定地跑到这个上限——而后者，正是面试官想从你这里听到的。

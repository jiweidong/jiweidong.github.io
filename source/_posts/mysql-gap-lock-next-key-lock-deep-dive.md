# 【MySQL 锁】间隙锁与临键锁深度解析：InnoDB 加锁规则、幻读与死锁实战

## 面试官：说说 InnoDB 的间隙锁（Gap Lock）和临键锁（Next-Key Lock）？

这道题是 MySQL 锁机制的"天花板"题目。先明确前提：**间隙锁和临键锁只在 RR（可重复读）隔离级别下生效**，RC 级别为了减少锁冲突，只保留记录锁。

## 一、为什么要引入间隙锁？——幻读问题

先回顾三种读异常的级别：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | ❌可能 | 可能 | 可能 |
| READ COMMITTED | 不会 | 可能 | 可能 |
| REPEATABLE READ | 不会 | 不会 | **可能（InnoDB 已解决）** |
| SERIALIZABLE | 不会 | 不会 | 不会 |

**幻读定义**：在同一个事务里，两次相同条件的查询，第二次多出了第一次没有的行（插入型问题）。

注意区分：
- **不可重复读**：同一行数据内容变了（UPDATE 造成）→ 用 MVCC 版本链 + 快照读解决
- **幻读**：查询结果**行数变多**（INSERT 造成）→ 快照读靠 MVCC 解决，**当前读要靠间隙锁解决**

```sql
-- 事务 A
BEGIN;
SELECT * FROM t WHERE id > 10 FOR UPDATE;  -- 当前读，返回 2 行
-- 事务 B 此时执行：INSERT INTO t(id) VALUES (11); -- 会被阻塞！
SELECT * FROM t WHERE id > 10 FOR UPDATE;  -- 依然是 2 行，没有幻读
COMMIT;
```

如果不加间隙锁，事务 B 插入 id=11 成功后，事务 A 第二次当前读会读到 11 这一行——**幻读**。间隙锁锁住的就是 `(10, +∞)` 这个"空隙"，让 B 的插入无法完成。

## 二、InnoDB 三种锁的递进关系

### 1. 记录锁（Record Lock）

单条索引记录上的锁，锁的是**索引记录**（不是行数据本身）。即使表没有索引，InnoDB 也会用隐藏的聚簇索引来锁。

```sql
SELECT * FROM t WHERE id = 10 FOR UPDATE;  -- 锁住 id=10 这条索引记录
```

### 2. 间隙锁（Gap Lock）

锁的是**两条索引记录之间的空隙**，或者第一条记录之前、最后一条记录之后的空隙。间隙锁**只阻止插入，不阻止更新和删除已存在的记录**。间隙锁之间**不互斥**（两个事务可以同时持有同一个间隙锁，因为各自都不能插入，互不冲突——这也是间隙锁死锁的一个根源）。

```sql
-- 表 t 现有 id: 5, 10, 15
SELECT * FROM t WHERE id BETWEEN 6 AND 9 FOR UPDATE;
-- 会锁住 (5, 10) 这个间隙，其他事务无法插入 id 6~9 的记录
```

### 3. 临键锁（Next-Key Lock）= 记录锁 + 间隙锁

锁的是**左开右闭区间** `(a, b]`：包含前一个间隙 + 当前记录。这是 InnoDB RR 级别默认的加锁单位，既防幻读又防更新冲突。

```sql
-- 表 t 现有 id: 5, 10, 15
SELECT * FROM t WHERE id >= 8 AND id <= 12 FOR UPDATE;
-- 临键锁范围：(5,10] 和 (10,15]
-- 即：间隙(5,10) + 记录10 + 间隙(10,15) + 记录15
-- 其他事务：不能插入 id ∈ (5,15] 的任意记录，不能更新/删除 id=10、15
```

### 4. 插入意向锁（Insert Intention Lock）

插入操作在**等待间隙锁释放**时，会先申请一个插入意向锁。它表达的是"我打算往这个间隙插入，但还没插入"。插入意向锁之间互不冲突（不同位置可以并行插入），但**插入意向锁和间隙锁冲突**。这个锁是理解"为什么间隙锁能阻塞插入"的关键。

## 三、加锁规则（MySQL 8.0 官方 + 丁奇《45 讲》总结版）

锁是加在**索引记录**上的，规则如下（以 RR 级别为例）：

1. **等值查询命中唯一索引（主键/唯一键）**：退化为**记录锁**，不锁间隙
2. **等值查询命中普通索引**：锁住该记录 + 其前后间隙（临键锁 + 右侧间隙锁）
3. **等值查询未命中**：锁住**相邻记录之间的整个间隙**（只锁间隙，不锁记录）
4. **范围查询**：对范围内的每条记录加临键锁，**并锁住范围末尾的间隙**（范围查询不会像等值查询那样优化掉间隙锁）
5. **锁是加在索引上的**：如果 WHERE 条件没走索引（全表扫描），InnoDB 会对**所有记录**加锁，等效于锁表；间隙锁也会覆盖所有间隙
6. **两阶段锁协议**：加锁在语句执行时进行，**所有锁在事务提交/回滚时统一释放**（所以事务里锁持有越久，阻塞面越大）

```sql
-- 场景：id 主键，现有 5, 10, 15
SELECT * FROM t WHERE id = 5 FOR UPDATE;   -- 只锁记录 5（唯一索引等值）
SELECT * FROM t WHERE id = 7 FOR UPDATE;   -- 锁间隙 (5, 10)，不锁记录
SELECT * FROM t WHERE id >= 10 FOR UPDATE; -- 锁 (5,10]、(10,15]、(15, +∞) 直到 supremum 伪记录
```

**supremum 伪记录**：InnoDB 在每页的头部和尾部各有一个虚拟记录 Infimum 和 Supremum。`id > 15` 的范围查询会锁到 Supremum 上的临键锁 `(15, +∞)`，表示"锁住最大记录之后的所有空间"，所以 `INSERT INTO t(id) VALUES(100)` 也会被阻塞。

## 四、MVCC 快照读为什么不需要间隙锁？

面试官常问：RR 级别下普通 `SELECT`（快照读）不是有 MVCC 保证一致性读吗，为什么还需要锁？

因为 **MVCC 只对快照读生效**，`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT ... ON DUPLICATE KEY UPDATE` 属于**当前读**（读最新版本），无法靠版本链保证"结果集不变"，必须用临键锁物理上锁住范围。

一句话总结：**快照读防幻读靠 MVCC 版本控制，当前读防幻读靠 Next-Key Lock。**

## 五、死锁案例分析（面试最爱考）

### 案例 1：间隙锁互不排斥导致的死锁

```sql
-- 表 t 现有 id: 5, 10，间隙 (5,10)
-- 事务 A
BEGIN;
SELECT * FROM t WHERE id = 8 FOR UPDATE;  -- 持有间隙锁 (5,10)
-- 事务 B
BEGIN;
SELECT * FROM t WHERE id = 9 FOR UPDATE;  -- 也持有间隙锁 (5,10)（间隙锁不互斥）
-- 事务 A
INSERT INTO t(id) VALUES (8);  -- 需要插入意向锁，与 B 的间隙锁冲突 → A 等待 B
-- 事务 B
INSERT INTO t(id) VALUES (9);  -- 与 A 的间隙锁冲突 → B 等待 A
-- 💥 死锁！InnoDB 检测到后回滚其中一个事务
```

### 案例 2：主键顺序颠倒导致的死锁

```sql
-- 事务 A：UPDATE t SET v=1 WHERE id=1; 然后 UPDATE t SET v=1 WHERE id=2;
-- 事务 B：UPDATE t SET v=1 WHERE id=2; 然后 UPDATE t SET v=1 WHERE id=1;
-- 互相持有对方需要的记录锁 → 死锁
```

**预防与处理**：
1. 按**固定顺序**访问资源（先 id 小后 id 大）
2. 事务尽量**短**，减少锁持有时间
3. 合理利用**唯一索引**等值查询，减少间隙锁范围
4. 死锁发生后：`SHOW ENGINE INNODB STATUS\G` 查看 `LATEST DETECTED DEADLOCK`，分析锁等待链
5. InnoDB 死锁检测默认开启，检测到就回滚**代价更小**的事务；高并发下可用 `innodb_deadlock_detect=OFF` + 锁等待超时兜底（`innodb_lock_wait_timeout`，默认 50s）

## 六、RC 级别下的锁

RC 级别**没有间隙锁**，只有记录锁。那 RC 怎么避免不可重复读？——RC 的 MVCC 是**每次读都生成新快照**（RR 是第一次读时生成快照并复用），所以 RC 下两次读可能读到不同版本，即不可重复读。RC 锁更少、并发更高，是很多互联网公司选择 RC 的原因（配合业务层补偿解决幻读/重复问题）。

| 维度 | RC | RR（默认） |
|------|----|-----------|
| 间隙锁/临键锁 | 无 | 有 |
| 幻读防护 | 无 | 有 |
| 并发度 | 更高 | 较低 |
| 死锁概率 | 较低 | 较高 |
| 日志/主从 | 支持 statement 复制有限制 | 兼容性更好 |

## 七、面试高频追问

**Q1：间隙锁会锁住不存在的记录吗？**
会。间隙锁正是锁"不存在记录的区间"，阻止其他事务往这个空隙插入。`SELECT ... WHERE id = 7`（7 不存在）会锁住 (5,10) 间隙。

**Q2：为什么间隙锁之间不互斥？**
两个事务同时持有同一间隙锁是允许的，因为间隙锁的目的是"防止别人插入"，两个持有者谁都无法插入，互不影响。只有当**插入意向锁**来竞争时才会冲突。这也是间隙锁死锁的常见成因。

**Q3：唯一索引等值查询为什么不锁间隙？**
因为唯一索引等值查询要么命中唯一一条记录，要么查询的记录不存在（此时会锁间隙）。命中时不会有其他事务插入相同值（唯一约束保证），所以不需要间隙锁来防幻读，只加记录锁即可。

**Q4：UPDATE 没走索引会怎样？**
全表扫描时 InnoDB 会对**所有扫描过的记录**加临键锁，间隙锁覆盖全表空隙，等效于把整张表锁住，其他事务的插入、更新全部阻塞。所以**写操作务必保证走索引**。

**Q5：如何用 EXPLAIN 判断加锁范围？**
看 `type`（range/ref 说明走索引，ALL 说明全表扫描会锁全表）、`key`（实际用的索引）、`rows`（预估扫描行数，范围越大锁越多）。

## 总结

间隙锁解决的是**当前读下的幻读**：临键锁 = 记录锁 + 间隙锁，默认锁左开右闭区间，唯一索引等值命中时退化为记录锁。理解加锁规则、两阶段锁协议、插入意向锁的冲突关系，再配合死锁案例分析，这道 MySQL 压轴题就能答出深度。

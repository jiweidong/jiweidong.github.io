# 【系统设计】IM 即时通讯系统架构设计：从单机到分布式百万在线

## 面试官：让你设计一个支持百万在线的 IM 系统，你怎么设计？

IM（Instant Messaging）是系统设计面试的"压轴题"之一：它集齐了**长连接、消息可靠性、顺序性、在线状态、群聊扩散、历史消息存储**几乎所有分布式难点。微信、钉钉、Slack 的架构都能在这套骨架里找到影子。

本文按"需求分析 → 单机原型 → 分布式演进 → 核心难点逐个击破"的顺序，给你一套可以直接背诵+扩展的完整方案。

---

## 一、需求分析：先搞清楚要做什么

### 1.1 核心功能

| 功能 | 说明 | 难点 |
|---|---|---|
| 单聊 | 点对点消息 | 路由、可靠性 |
| 群聊 | 一对多广播 | 扩散模型选择 |
| 在线状态 | 上下线感知 | 一致性、实时性 |
| 消息可靠性 | 不丢不重 | ACK + 重传 + 幂等 |
| 消息顺序 | 单会话内有序 | seq 机制 |
| 历史消息 | 离线拉取、漫游 | 海量存储、分页 |
| 已读回执 | 已读未读 | 状态同步 |

### 1.2 非功能需求

- **规模**：100 万在线，峰值 QPS 10 万+，单聊消息峰值 5 万/秒
- **延迟**：消息端到端 < 200ms
- **可靠性**：消息不丢（至少一次），尽量不重（幂等去重）
- **可用性**：99.99%，单点故障不影响核心链路

## 二、单机原型：一切从长连接开始

### 2.1 最朴素的模型

```
客户端 ──TCP/WebSocket 长连接──> 单机 IM Server ──> 内存中维护: uid -> Channel
```

- 客户端与服务器建立**长连接**（WebSocket 或自研二进制协议）
- 服务器内存维护 `Map<uid, Channel>`
- 发消息：查收件人 Channel，直接写入

**瓶颈立刻出现**：

1. 单机连接数上限（一台 4C8G 机器约支撑 5~10 万长连接）
2. 单点故障：机器挂了所有连接断开
3. 内存 Map 无法扩展
4. 没有消息持久化，离线消息全丢

于是必须走向分布式。

## 三、分布式演进：四层架构

```
客户端
  │  (长连接)
  ▼
┌─────────────┐
│ 接入层 Gateway │  ← 负载均衡: 四层(LVS/ELB) + 七层(Nginx/自研), WebSocket 粘滞会话
└──────┬──────┘
       │ (内部 RPC / gRPC)
┌──────▼──────┐   ┌──────────────┐   ┌──────────────┐
│ 路由层 Router │   │  在线状态服务  │   │  消息队列 MQ   │
│ (uid → 网关) │   │ (Redis 存储)  │   │ (削峰/异步)    │
└──────┬──────┘   └──────────────┘   └──────┬───────┘
       │                                    │
┌──────▼────────────────────────────────────▼───────┐
│              存储层: 消息存储 + 历史消息               │
│   MySQL(分库分表) / TiDB / HBase / 对象存储           │
└───────────────────────────────────────────────────┘
```

### 3.1 接入层（Gateway）：连接是命根子

- **职责**：维护海量长连接、心跳保活、协议编解码、鉴权、流量控制
- **无状态化**：Gateway 自身不存业务状态，只做"连接管道"，业务逻辑下沉
- **连接与业务分离**：Gateway 收到消息后转发给 Router 处理，自己只负责把响应写回对应连接
- **路由粘滞**：长连接建立后，同一客户端的连接尽量固定在一个 Gateway（或通过连接级路由表寻址），避免消息到了别的节点找不到连接
- **横向扩展**：加机器即可扩容连接容量，通过 Nginx stream 或自研网关做四层转发

### 3.2 路由层（Router）：uid → Gateway 的映射

核心数据结构：**在线路由表** `uid -> gatewayId`，存储在 **Redis**（或内存 + 一致性哈希）。

```java
// 伪代码：消息路由流程
public void route(Message msg) {
    // 1. 查收件人在线路由
    String gatewayId = onlineService.getGatewayId(msg.toUid);
    if (gatewayId != null) {
        // 2. 在线：推送到对应 Gateway
        gatewayClient.send(gatewayId, msg);
    } else {
        // 3. 离线：写入离线消息存储
        offlineStore.append(msg.toUid, msg);
    }
}
```

### 3.3 在线状态服务：Redis 是天然选择

- **在线集合**：`SET online:uid`，登录时写入、断开时删除
- **上下线广播**：好友上下线通知走 MQ 广播给相关会话
- **心跳机制**：Gateway 与客户端约定心跳（如 30s），N 次未收到则判定离线，同时更新路由表
- **注意脑裂**：客户端与 Gateway 断连但 TCP 未感知时，需靠"心跳超时 + 对端主动断开"双通道确认

## 四、核心难点逐个击破

### 4.1 难点一：消息可靠性（不丢不重）

**方案：ACK + 重传 + 幂等 + 序号去重**

```
客户端 A ──发送(seq=100)──> 服务端
服务端 ──ACK(seq=100)──> 客户端 A      # 服务端确认收到
服务端 ──下发(seq=100)──> 客户端 B
客户端 B ──ACK(seq=100)──> 服务端      # B 确认收到
```

- **客户端重传**：超时未收到 ACK 就重发，配合递增 seq
- **服务端幂等**：收到重复 seq 的消息直接丢弃（用 Redis `SETNX msg:{uid}:{seq}` 去重）
- **至少一次 + 幂等去重** = 最终"不重不丢"
- **消息落库**：服务端收到消息先持久化（MQ + 存储）再下发，避免"确认了但没存"的丢失

### 4.2 难点二：消息顺序性（单会话内有序）

**方案：每个会话独立 seq**

- 每个会话（单聊或群聊）维护一个单调递增的 **seq 号**
- 场景：同一发送方连续发两条消息，若走不同 MQ 分区可能乱序
- 解法：**按会话维度 hash 到同一个 MQ 分区**（`partition = hash(conversationId) % N`），保证同一会话消息有序消费
- 客户端侧：**按 seq 排序后再展示**（网络乱序兜底），gap 检测触发补拉

```java
// 会话消息序号（伪代码）
long seq = conversationSeqService.next(conversationId);  // Redis INCR 或发号器
msg.setSeq(seq);
```

### 4.3 难点三：群聊扩散模型

| 模型 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| 写扩散（拉模式） | 发一条，群成员各自拉取 | 存储小、群大也不怕 | 延迟高、读放大 |
| 读扩散（推模式） | 发一条，给每个成员写一份 | 实时性好 | 存储放大，万人大群写放大 |
| **混合（推荐）** | 小群(<500)推模式，大群拉模式 + 在线成员实时推送 | 平衡 | 模型复杂 |

**微信的经典做法**：在线成员实时推送（不走存储），离线成员上线后拉取群消息；群规模大时只给活跃成员建索引。

### 4.4 难点四：离线消息与历史消息存储

- **离线消息**：Redis List 暂存（如 7 天），上线后拉取并清理
- **历史消息**：按会话分表 `msg_{conversationId_hash}`，或直接上 **TiDB/HBase** 这类分布式存储
- **分页**：以 seq 为游标翻页（`WHERE seq < cursor ORDER BY seq DESC LIMIT 20`），避免深分页
- **消息体与索引分离**：正文存对象存储，DB 只存索引（类似"大字段拆表"思路）

### 4.5 难点五：已读回执

- 每个会话记录 `lastReadSeq`（每个成员一个）
- 展示已读/未读：`我的 lastReadSeq vs 对方最后一条消息 seq`
- 群聊已读：只统计"最近活跃 N 人"已读，避免全量统计爆炸（微信的群已读也是近似实现）

## 五、协议选型：WebSocket 还是自研？

| 维度 | WebSocket | 自研二进制（如微信 mmtls） |
|---|---|---|
| 开发成本 | 低，浏览器天然支持 | 高，需自研编解码 |
| 性能 | HTTP 升级后全双工，够用 | 更紧凑，头部极小 |
| 多端/Web | ✅ 直接支持 | ❌ 需 Web 端适配层 |
| 适用 | 绝大多数业务 IM | 亿级用户、极致性能 |

**推荐**：业务 IM 用 WebSocket + JSON（或 Protobuf 压缩消息体）；追求极致性能再上自研协议。MQTT 也是 IoT 场景的成熟选择（QoS 0/1/2 内置可靠性语义）。

## 六、关键技术选型清单

| 组件 | 选型 | 理由 |
|---|---|---|
| 长连接 | WebSocket / Netty | Netty 支撑百万连接，业界标配 |
| 在线状态/路由 | Redis Cluster | 高并发读写，天然支持过期与原子操作 |
| 消息削峰异步 | Kafka / RocketMQ | 分区有序、持久化、削峰 |
| 消息存储 | TiDB / HBase / MySQL 分表 | 海量写入 + 水平扩展 |
| 历史消息 | 对象存储 + 索引 | 冷热分离 |
| 服务发现 | Nacos / K8s | 网关动态感知节点 |
| 监控 | Prometheus + 自定义指标 | 连接数、消息延迟、丢消息率 |

## 七、压测与容量估算（面试常考）

**粗算 100 万在线的资源需求**：

- 单 Gateway 支撑 5 万连接 → 需要 **20+ 台 Gateway**（留冗余 25 台）
- 在线路由表：100 万条 KV，Redis 轻松承载
- 消息峰值 5 万/秒，单条 1KB → 50MB/s 写入，Kafka 3 节点集群可扛
- 历史消息：假设 100 万日活每人每天 200 条 = 2 亿条/天，按月存 60 亿条 → 必须分表 + 冷热分离 + 定期归档

## 面试官常见追问

**Q：Gateway 怎么做到水平扩展？连接会不会"漂移"？**
A：连接建立时通过负载均衡分发到某个 Gateway，路由表记录 uid→gatewayId。消息路由先查路由表找到目标 Gateway 再投递，连接不漂移。Gateway 宕机时，其上的连接断开，客户端自动重连到其他 Gateway 并重新上报在线状态，路由表更新。关键点：**业务逻辑无状态化**，状态全部外置到 Redis/存储。

**Q：消息顺序和可靠性怎么同时保证？**
A：可靠性靠"服务端落库 + ACK + 客户端超时重传 + seq 幂等去重"；顺序靠"同一会话 hash 到同一 MQ 分区串行消费 + 会话级 seq 递增"。注意：**可靠性里的重传可能产生乱序**（前一条丢了后一条先到），所以客户端必须按 seq 排序 + gap 检测补拉，两者是配合关系。

**Q：为什么在线状态用 Redis 而不用数据库？**
A：在线状态是"高频写、低价值、可丢失"数据：上下线、心跳更新可能每秒几十万次写，DB 扛不住且没必要持久化；Redis 内存读写十万级 QPS、天然 TTL 过期（心跳超时自动清理）、原子操作方便。这是典型"缓存优先"的场景。

**Q：群聊 10 万人，消息怎么发？**
A：用混合模型：① 在线成员走推模式，Gateway 定向推送（内存连接表查一遍，不落库）；② 离线成员上线后按 seq 拉取；③ 群消息本身只落一份存储 + 群成员索引。避免"每人写一份"的写放大。如果是全员在线的大群，还可以用"扇出到 Gateway 再广播"的方式减少重复序列化。

**Q：怎么防止消息风暴打垮系统？**
A：分层防护：① 接入层限流（令牌桶按 uid/会话限速）；② MQ 削峰，消费端按会话并发控制；③ 群消息合并（同一群高频消息聚合下发）；④ 优先级队列：系统通知 > 单聊 > 群聊；⑤ 降级预案：高峰期已读回执、在线状态可降级为"近似"。

## 总结

IM 架构设计题的标准答题框架：

1. **需求**：功能（单聊/群聊/状态/回执）+ 非功能（百万在线、低延迟、不丢消息）
2. **分层架构**：接入层（长连接）→ 路由层（uid→gateway）→ 业务层 → 存储层
3. **核心难点**：可靠性（ACK+重传+幂等）、顺序（会话 seq + MQ 分区）、群聊（混合扩散）、离线/历史（分表+冷热分离）
4. **技术选型**：Netty + Redis + Kafka + TiDB/分表 MySQL
5. **扩展性**：无状态接入层横向扩容，状态外置

按这个框架答，深度和广度都覆盖到了，面试官想继续深挖也有足够的抓手。

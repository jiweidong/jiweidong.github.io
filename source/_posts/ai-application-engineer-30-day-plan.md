# 【AI 转型】30 天 AI 应用开发速成计划：每日任务与检验标准

## 前言

先泼冷水：**30 天不可能让你成为 AI 专家**。但 30 天足够让一个 3 年经验的 Java 后端，从「只会调 API」变成「能独立交付一个 RAG 问答 + 一个工具调用 Agent，并且能说清楚每个技术取舍」——这已经够拿到 AI 应用开发岗的面试机会。

这份计划有三个设计原则：

1. **不做知识收藏家**。每天必须有可运行产出，没有产出的一天等于没学。
2. **Java 技术栈为主**。你已有的 Spring、并发、数据库经验是资产，不要从零学 Python 生态，那是自我降维。
3. **每天有检验标准**。标准要可验证（能跑、能测、能讲），不是「了解了」「大概懂了」。

时间预算：**每天 2.5~3 小时**（工作日），周末 5 小时。总计约 100 小时。如果每天只有 1 小时，把计划拉长到 60 天，不要压缩内容。

## 一、30 天后你应该达到什么

| 能力 | 达标标准 |
|---|---|
| LLM 调用 | 能写健壮的调用层：重试、超时、流式、结构化输出、成本统计 |
| Prompt | 能写出稳定可复现的 Prompt，会用 few-shot、CoT、输出约束 |
| RAG | 能独立搭一条检索链路，并用黄金集测出 Recall |
| Agent | 能实现 ReAct 循环 + 3 个以上工具 + 权限控制 |
| 工程化 | 有日志 Trace、有缓存、有限流、有评测 |
| 表达 | 能把项目讲成「问题-方案-取舍-指标」四段式 |

**不要求**：模型训练、微调、分布式推理、CUDA。这些是算法岗/平台岗的事，应用开发不需要。

## 二、四周结构总览

| 周 | 主题 | 核心产出 |
|---|---|---|
| 第 1 周 | LLM 基础与调用工程 | 一个生产级 LLM 调用层 + Prompt 实验台 |
| 第 2 周 | RAG 全链路 | 一个可用的知识库问答 + 评测报告 |
| 第 3 周 | Agent 与工具调用 | 一个多工具 Agent + 审批流 |
| 第 4 周 | 工程化与作品集 | 可观测/成本/评测 + 简历与面试 |

## 三、第 1 周：LLM 基础与调用工程（Day 1-7）

### Day 1 · 建立正确认知

**任务**
- 搞清 Token、上下文窗口、temperature、top_p、presence_penalty 的实际影响。
- 用 curl 或 Java 各调一次 chat completions，打印 usage。
- 记录：同样问题在 temperature 0 / 0.7 / 1.2 下的输出差异。

**产出**：一篇 500 字的笔记，含 3 组对比输出。

**检验标准**：能解释「为什么 temperature=0 仍可能不完全确定」（浮点、批处理、模型版本）。

### Day 2 · Spring AI 接入

**任务**
- 新建 Spring Boot 3.3 项目，接入 Spring AI + 一个模型（OpenAI 兼容接口即可，DeepSeek/通义都行）。
- 实现同步对话、流式对话（SSE）两个端点。

**产出**：`/chat` 和 `/chat/stream` 两个接口，用 curl 能看到逐字输出。

**检验标准**：流式接口在浏览器里能实时看到 token；断连后服务端不报错堆积。

### Day 3 · 调用层健壮性

**任务**
- 加重试（指数退避 + 抖动）、超时（连接/读分开）、降级（备用模型）。
- 用 Resilience4j 或 Spring Retry 实现。
- 加 token 统计与单次成本计算。

**产出**：`LlmClient` 封装类 + 单元测试（模拟超时、429、500）。

**检验标准**：用 WireMock 模拟 429，验证重试 3 次后降级成功；成本统计误差 < 1%。

### Day 4 · Prompt 工程

**任务**
- 学四种技巧：角色设定、few-shot、CoT、输出格式约束。
- 做一个「结构化信息抽取」Prompt：输入一段招聘 JD，输出 JSON（公司、岗位、薪资、技能列表）。

**产出**：Prompt 模板 + 20 条测试样本的抽取结果。

**检验标准**：20 条里至少 18 条 JSON 可解析，字段完整率 > 90%。

### Day 5 · 结构化输出

**任务**
- 用 JSON Schema 约束输出（Spring AI 的 `BeanOutputConverter` 或原生 `response_format`）。
- 实现「解析失败 → 带错误信息重试一次 → 仍失败降级为宽松解析」。

**产出**：`StructuredExtractor<T>` 泛型工具类。

**检验标准**：故意让模型输出多余文本，验证重试链路生效，最终成功率 > 95%。

### Day 6 · 上下文与 Token 管理

**任务**
- 实现对话历史的滑动窗口 + 摘要压缩。
- 统计多轮对话的 token 增长曲线。

**产出**：`ConversationMemory`，支持窗口大小配置与摘要触发阈值。

**检验标准**：20 轮对话后输入 token 不超过设定上限；摘要后仍能正确回答第 1 轮提到的关键信息（人工验 5 条）。

### Day 7 · 复盘 + 小项目

**任务**
- 把 Day 2-6 串成一个「命令行/网页版通用助手」：支持流式、历史、结构化抽取、成本显示。
- 写复盘：哪一步最耗时，为什么。

**产出**：可运行 demo + 复盘笔记。

**检验标准**：能对陌生人 5 分钟讲清架构；代码有 README 和启动说明。

## 四、第 2 周：RAG 全链路（Day 8-14）

### Day 8 · Embedding 与向量基础

**任务**
- 理解 embedding 维度、相似度度量（cosine/dot/L2）、归一化。
- 用 Java 调 embedding API，算 10 组句子的相似度，人工验证合理性。

**产出**：相似度实验表格。

**检验标准**：能解释「为什么 cosine 更适合文本」「归一化后 dot 等价于 cosine」。

### Day 9 · 向量库落地

**任务**
- Docker 起 pgvector（或 Qdrant），建表、建索引（HNSW/IVFFlat）。
- 写入 1000 条数据，做 TopK 查询，测延迟。

**产出**：可运行的向量读写 DAO + 延迟数据。

**检验标准**：1000 条数据下 Top10 查询 P95 < 20ms；能说出 HNSW 的 `m`、`ef_construction` 作用。

### Day 10 · 文档解析与切分

**任务**
- 解析 PDF/Word/Markdown（PDFBox / POI / 直接读 md）。
- 实现两种切分：固定长度、按标题层级结构化切分。
- 对比同一问题的检索结果差异。

**产出**：`DocumentLoader` + `Chunker` 两个接口及实现。

**检验标准**：结构化切分下，检索到的块「语义完整」（人工看 20 条，完整率 > 80%）。

### Day 11 · 混合检索

**任务**
- 加 BM25（pgvector 用 `tsvector`，或 ES）与向量检索并行。
- 用 RRF 融合两路结果。

**产出**：`HybridRetriever`。

**检验标准**：对 20 条含专有名词的 query，混合检索命中率高于单路向量 ≥ 15%。

### Day 12 · 重排

**任务**
- 接入一个 rerank 模型（BGE-reranker / Cohere Rerank / 商用 API）。
- 对比「不重排 / 重排」的 Top3 相关性。

**产出**：重排前后对比表。

**检验标准**：Top3 相关性人工打分平均提升 ≥ 0.8 分（5 分制）。

### Day 13 · 生成与引用

**任务**
- 上下文组装：控制总 token、加分隔符、标注来源编号。
- Prompt 要求「只依据给定资料回答，无依据就说不知道，并标注 [1][2]」。
- 前端展示引用，点击跳原文。

**产出**：完整问答链路 + 引用展示。

**检验标准**：50 条问题中，幻觉率（编造事实）< 10%；引用准确率 > 85%。

### Day 14 · 评测与复盘

**任务**
- 建 100 条黄金集（问题 + 正确文档 ID + 参考答案）。
- 写评测脚本，输出 Recall@5、忠实度、平均延迟、平均 token 成本。
- 做一次 A/B：改切分策略，看指标变化。

**产出**：`eval/` 目录 + 评测报告（Markdown）。

**检验标准**：报告里有「改动前后对比表」；能解释每个指标的含义与局限。

## 五、第 3 周：Agent 与工具调用（Day 15-21）

### Day 15 · Function Calling 基础

**任务**
- 定义 3 个工具（天气、汇率、计算器），用 Spring AI `@Tool` 或 Function 注册。
- 理解工具 Schema、参数校验、模型如何决定调用。

**产出**：能根据自然语言自动选工具并返回结果。

**检验标准**：20 条测试 query，工具选择正确率 > 85%。

### Day 16 · ReAct 循环

**任务**
- 手写 ReAct 循环（不依赖框架的黑盒 Agent）：Thought → Action → Observation → 循环。
- 加最大步数、超时、重复调用检测。

**产出**：`ReActAgent` 类。

**检验标准**：能完成「查 A 城市天气 → 根据温度推荐穿衣 → 换算当地货币」的多步任务；超过 8 步自动终止。

### Day 17 · 记忆系统

**任务**
- 短期记忆：对话窗口。
- 长期记忆：把关键事实抽成结构化条目存库，按相关性召回。
- 实现「用户偏好」记忆：说过「我不吃辣」，后续推荐要遵守。

**产出**：`AgentMemory` 双通道实现。

**检验标准**：跨会话（重启服务）后仍能记住用户偏好。

### Day 18 · 工具安全与权限

**任务**
- 给工具分级：只读 / 低风险写 / 高风险写。
- 高风险工具改为「生成待审批动作」，人工确认后由独立执行器落地。
- 加审计日志（谁、何时、调了什么、参数、结果）。

**产出**：工具权限矩阵 + 审批表 + 审计日志。

**检验标准**：构造一个「让 Agent 直接退款」的诱导输入，验证被拦截并生成审批单。

### Day 19 · 多智能体（了解即可）

**任务**
- 实现两个角色：Planner（拆任务）+ Executor（执行）。
- 跑一个「调研某技术并输出报告」的任务。

**产出**：简易双 Agent 协作。

**检验标准**：能说清「什么时候不该用多智能体」（任务简单、延迟敏感、成本敏感时单 Agent 更好）。

### Day 20 · MCP 入门

**任务**
- 理解 MCP 的 Host / Client / Server 角色与 Tools/Resources/Prompts 原语。
- 写一个最小 MCP Server（暴露 2 个工具），用客户端连上调用。

**产出**：可运行的 MCP Server。

**检验标准**：能用 MCP Inspector 或客户端列出并调用工具；能解释 MCP 与 Function Calling 的区别（协议层 vs 模型能力）。

### Day 21 · 复盘 + 串成项目

**任务**
- 把 Day 15-20 串成「个人助理 Agent」：查资料、算数、记事、需审批的操作。
- 写复盘：最难的三个点。

**产出**：可运行 Agent 项目。

**检验标准**：演示 3 个完整任务流；每个失败案例能说出根因。

## 六、第 4 周：工程化与作品集（Day 22-30）

### Day 22 · 可观测性

**任务**
- 加 Trace ID 贯穿：请求 → 检索 → 模型调用 → 工具调用。
- 记录：首 token 延迟、总延迟、token 数、工具调用次数、错误码。
- 用 Micrometer + Prometheus + Grafana 出面板。

**产出**：Grafana 面板截图 + 埋点代码。

**检验标准**：能按 Trace ID 还原一次完整请求的耗时分解。

### Day 23 · 成本与缓存

**任务**
- 建 token 账本：按用户/接口/模型维度统计。
- 实现精确缓存（hash）与语义缓存（向量相似度 > 阈值命中）。
- 测缓存命中率与成本下降。

**产出**：成本报表 + 缓存层。

**检验标准**：重复问题场景下成本下降 > 40%，缓存误命中（语义相似但答案不同）< 3%。

### Day 24 · 限流、降级与安全

**任务**
- 租户级 RPM/TPM 限流（Redis 令牌桶）。
- 模型熔断与降级。
- Prompt 注入防御：输入隔离、指令与数据分隔、输出校验、工具权限。

**产出**：限流过滤器 + 安全校验链。

**检验标准**：压测到配额上限时正确返回 429；构造 5 种注入 prompt，拦截率 ≥ 80%。

### Day 25 · 评测体系

**任务**
- 建三套评测：检索（Recall）、生成（忠实度/相关性）、端到端（任务完成率）。
- 用 LLM-as-judge 打分，抽 30 条人工校验一致率。

**产出**：评测流水线 + 基线报告。

**检验标准**：能说出「LLM-as-judge 的偏差来源」以及如何校准。

### Day 26 · 压测与调优

**任务**
- JMeter/wrk 压测，记录 P50/P95/P99、错误率、token 消耗速率。
- 找出瓶颈（检索、模型、序列化、连接池），做一次优化。

**产出**：压测报告（优化前后）。

**检验标准**：至少一个指标提升 30% 以上，且能解释原因。

### Day 27 · 项目整理

**任务**
- 挑 2 个项目（RAG + Agent），补齐 README、架构图、ADR、评测报告。
- 统一 docker-compose，确保别人能一键启动。

**产出**：两个可交付仓库。

**检验标准**：找一个朋友按 README 从零跑通，不需要你口头指导。

### Day 28 · 简历改写

**任务**
- 每个项目写 3 条 bullet：做了什么 + 技术取舍 + 量化结果。
- 删掉「熟悉/了解」这类虚词，全部换成动作与数字。

**产出**：新版简历。

**检验标准**：每条 bullet 都能被追问 3 层而答得上来。

### Day 29 · 模拟面试

**任务**
- 准备 20 个高频问题的答案：RAG 切分、召回优化、Agent 失控、幻觉治理、成本控制、评测方法。
- 找人或用 AI 做一次 45 分钟模拟面试，录音回听。

**产出**：问答手册 + 录音复盘。

**检验标准**：每个回答控制在 2 分钟内，有结构（结论 → 原因 → 例子 → 数据）。

### Day 30 · 复盘与下一步

**任务**
- 写一份 30 天复盘：做了什么、指标如何、哪些还没懂。
- 定下一个 90 天计划（深入方向：Agentic RAG / 多智能体 / 平台化）。

**产出**：复盘文档 + 90 天计划。

**检验标准**：能清晰说出「我现在能做什么岗位、差什么」。

## 七、每日时间分配模板（2.5 小时）

| 时段 | 时长 | 内容 |
|---|---|---|
| 输入 | 40 min | 读文档/源码/文章，只读当天需要的 |
| 动手 | 80 min | 写代码，必须跑起来 |
| 验证 | 20 min | 按当天检验标准自测，记录数据 |
| 记录 | 20 min | 写笔记：今天学到什么、卡在哪、明天第一步 |

**关键**：输入时间不能超过 1/3。看视频看到爽但不动手，是最大的时间黑洞。

## 八、常见失败模式

| 失败模式 | 表现 | 解法 |
|---|---|---|
| 收藏癖 | 存了 50 篇教程没跑通一个 | 每天必须先跑通再读下一篇 |
| 追求完美 | 一直在优化切分，项目没上线 | 先跑通端到端，再优化单点 |
| 只做 demo | 没有评测、没有指标 | 第 14 天强制建黄金集 |
| 频繁换题 | 一周换三个项目 | 一个项目做完再开下一个 |
| 只学不用 | 能讲概念写不出代码 | 每个概念必须落到一个方法 |
| 忽略成本 | 本地测试很爽，上线烧钱 | 从 Day 3 就统计 token |
| 不看源码 | 框架黑盒，出问题抓瞎 | 至少读一次 Spring AI 的 Advisor 链 |

## 九、30 天之后往哪走

三条路线，按兴趣选：

1. **应用深耕**：Agentic RAG、多智能体、工作流编排、评测体系 → 高级 AI 应用工程师。
2. **平台方向**：LLM 网关、推理服务、向量平台、成本治理 → AI 基础设施工程师。
3. **业务方向**：把 AI 嵌进具体业务（客服、风控、研发效能）→ AI 解决方案/技术负责人。

共同点是：**继续用 Java**。AI 应用层的大量工程问题（并发、事务、消息、可观测、权限）正是后端工程师的强项，不要丢掉这个优势去和算法同学拼模型。

## 十、面试常见追问

**Q1：30 天学的东西够用吗？会不会很水？**
30 天给的是「能跑通 + 能讲清取舍」的工程能力，不是研究能力。面试官考察应用岗，重点是你有没有踩过真实坑、有没有指标意识，这两点 30 天足够建立。深度靠后续项目持续积累。

**Q2：为什么不学 Python？**
应用层用 Java 完全够（Spring AI、LangChain4j 生态成熟），而且能复用你已有的并发、Spring、数据库经验。学 Python 的边际收益主要在算法与数据处理生态，那是另一个岗位方向。

**Q3：没有 GPU、没有预算怎么办？**
用便宜 API（DeepSeek/通义）做开发，本地用 Ollama 跑小模型做离线测试；embedding 用开源模型本地跑（bge-small）。整个 30 天的 API 成本可以控制在 100 元以内。

**Q4：怎么证明这 30 天的成果？**
两个可运行仓库 + 两份评测报告 + 一篇复盘。仓库要能一键启动，报告要有前后对比数据，复盘要写清失败与修正。这三样比任何证书都有说服力。

## 总结

30 天计划的核心不是「学完多少知识」，而是**建立一条可重复的工程闭环**：

> 定目标 → 跑通最小链路 → 建评测 → 找瓶颈 → 优化 → 用数据证明。

这条闭环跑通一次，你就有能力自己往前走；跑不通，学再多概念也只是纸上谈兵。

从今天开始，先做 Day 1 的那件事：调一次 API，打印 usage，记录三组 temperature 的差异。**别做计划收藏家，做那个今天就把代码跑起来的人。**

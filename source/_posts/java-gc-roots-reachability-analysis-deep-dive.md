# 【JVM 底层】GC Roots 与可达性分析深度解析：根集合枚举、OopMap 与四种引用可达性

## 面试官：JVM 怎么判断一个对象该被回收？

这是 JVM 面试的第一道门槛。很多人张口就来：「引用计数 + 可达性分析」。再追问一句「那 GC Roots 到底包含哪些？为什么 Java 不用引用计数？枚举根节点的时候 STW 在停什么？」——大部分人就开始支吾了。

这篇文章把「可达性分析」这条主线从算法一路挖到 HotSpot 的实现细节：为什么引用计数被淘汰、GC Roots 的完整集合、根枚举为什么要 STW、OopMap 是怎么把「找根」这件事从「扫描整个栈」变成「查表」的、以及在并发标记时代 SATB 与增量更新如何配合根集合工作。

## 一、先否定一个答案：为什么不用引用计数？

引用计数（Reference Counting）的思路很朴素：每个对象维护一个计数器，有引用加一，引用失效减一，归零即回收。

它有三个致命问题：

1. **循环引用无法回收**。`a.next = b; b.next = a;` 之后两者计数都不为 0，即使外部已经不可达，内存也永远不会释放。这是纯引用计数的死穴。
2. **写屏障开销无处不在**。Counter 每次赋值都要维护，属于「高频路径上的额外成本」，对吞吐影响很大。
3. **线程安全成本高**。多线程并发修改引用还要保证计数原子性，进一步放大开销。

Python、Swift、ObjC 用引用计数，是因为它们要么配了循环检测器（Python 的 gc 模块），要么是 ARC 编译期插桩 + 明确的生命周期语义。而 HotSpot 选择了另一条路：**从一组确定的「根」出发做图遍历，能走到的对象存活，走不到的就是垃圾。**

```java
// 循环引用在可达性分析下完全不是问题
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
// 两个 Node 互相引用，但已不可达 -> 可回收
```

## 二、GC Roots 到底包含哪些？

网上常见的说法是「虚拟机栈中引用的对象、方法区静态属性引用的对象、常量引用的对象、JNI 引用的对象」。这个说法对，但不完整。完整的根集合（HotSpot 视角）：

| 根类型 | 说明 | 典型来源 |
| --- | --- | --- |
| 虚拟机栈局部变量 | 每个线程当前栈帧中局部变量表里的引用 | 方法参数、局部变量 |
| 方法区静态属性 | 类的 `static` 字段引用 | `static Object cache` |
| 方法区常量 | 运行时常量池中的引用（String 常量池等） | `static final String` 指向的实例 |
| JNI 引用 | 本地方法栈中 JNI Reference | `NewGlobalRef` 创建的全局引用 |
| 活跃线程对象 | 所有存活的 `Thread` 实例 | 线程本身也是根 |
| 类加载器 | 系统类加载器、被已加载类引用的加载器 | 防止类被卸载 |
| 同步监视器 | 被 `synchronized` 持有的对象 | monitor 中保存的对象引用 |
| JVM 内部引用 | 系统类、基本类型 Class、常驻异常对象等 | HotSpot 内部结构 |
| Class 对象 | 每个已加载类的 `java.lang.Class` 实例 | 类的元数据入口 |

一个容易被忽略的点：**根是「集合」，而不是「对象本身」**。HotSpot 内部真正维护的是「根集合」（Root Set），它是一个由若干内存区间组成的抽象结构，GC 需要能枚举出根集合中所有引用，这个过程叫 **根枚举（Root Enumeration）**。

### 面试追问：`static final` 常量引用的对象一定是根吗？

不一定。是「**持有该引用符号的常量池条目所在类仍然存活**」时，这个引用才是根。如果类被卸载了，这条根也随之消失。所以 `ClassLoader` 泄漏会导致大量本应回收的对象被静态字段死死抱住。

## 三、根枚举为什么要 STW？「一致性快照」

GC 线程要枚举根，就必须有一个前提：**在枚举过程中，根集合不会发生变化。**

如果应用线程还在跑，可能出现这种情况：GC 刚扫完某个栈帧，应用线程马上在该栈帧里写入一个新引用；GC 认为这个局部变量是 null，于是把对象回收了，但应用线程马上就要用它——程序直接崩。

所以 HotSpot 必须在 **安全点（Safepoint）** 让所有线程停下来，这个停顿就是常说的 STW（Stop The World）。注意：**可达性分析本身可以是并发的，但根枚举的「快照一致性」必须靠 STW 保证。**

这就引出了两个工程问题：

1. 停多久取决于「枚举根有多快」；
2. 能不能让「找根」不靠遍历整个栈？

## 四、OopMap：把「扫描栈」变成「查表」

假设一个方法有 1000 行代码、几百个局部变量，而当前只执行到第 37 行——如果 GC 要靠遍历局部变量表逐槽位判断「这一格是指针还是 int」，那开销不可接受。

HotSpot 的做法是 **OopMap（Ordinary Object Pointer Map）**：JIT 在编译方法时，会在 **安全点位置** 记录下「此刻栈帧和寄存器中，哪些位置存放的是对象引用」。

```text
// 概念示意：某个 safepoint 处的 OopMap
[pc=0x1a2b] stack: [0]=oop, [1]=int, [2]=oop, [3]=long
            rbx=oop, rdx=int
```

于是根枚举退化成一个极简操作：**在安全点处，按 OopMap 直接把这几个槽位的引用取出来即可，不需要逐格扫描，也不需要解释器逐条猜类型。**

OopMap 的代价是「需要内存 + 需要维护」，所以 HotSpot 只在 **安全点（Safepoint）** 和 **安全区域（Safe Region）** 记录它，而不是每条指令都记。这也解释了为什么热点代码里的安全点稀疏——每多一个安全点，就多一份 OopMap 元数据。

### 安全点 vs 安全区域

- **安全点**：代码中显式插入的「可枚举根」的位置。方法调用、循环回边、异常跳转等被认为是安全点。
- **安全区域**：线程处于 `sleep`、阻塞 IO、`native` 等状态时无法走到安全点的区间。线程进入安全区域时会标记自己「已进入」，GC 遇到处于安全区域的线程可以选择忽略它——因为这段区间内引用关系不会变化。

面试常问：「GC 时线程卡在 `Thread.sleep()` 怎么办？」答：它处于安全区域，GC 可以安全地不枚举它的栈。

## 五、并发标记时代的根：SATB 与增量更新

现代收集器（CMS、G1、ZGC）的标记阶段是 **并发** 的：GC 线程和应用线程一起跑。可并发就带来「漏标」问题——三色标记下，两个条件同时成立就会漏标：

1. 黑色对象新增了对白色对象的引用；
2. 所有灰色对象到该白色对象的引用都消失了。

HotSpot 用 **写屏障（Write Barrier）** 在赋值语句里插桩，有两种经典处理：

- **增量更新（Incremental Update，CMS）**：记录「新增引用」，把它重新置灰，重新扫描。破坏条件 1。
- **原始快照（SATB，Snapshot At The Beginning，G1）**：记录「删除引用」，把被删除的旧引用记录下来，当作「拍照那一刻它还在」。破坏条件 2。

SATB 的语义非常关键：**G1 的标记是基于「标记开始时」的对象图快照的。** 所以标记开始后新产生的对象，在本轮会被当作「存活」（隐式标记为存活），留到下一轮；这会让「浮动垃圾」稍微多一点，但换来更低的写屏障成本（只需要记录删除，不需要重新扫描）。

而 **根集合本身在并发标记期间也会变**。所以并发标记结束前后还有一次很短的 STW（G1 的 Remark / Final Mark），用来处理 SATB 队列里剩余的根，以及「根区域扫描（Root Region Scanning）」的结果。

## 六、四种引用与「可达性」的精细分级

严格来说，Java 里「可达」不是二值，而是四档，直接决定了对象能不能在本轮被回收：

| 引用类型 | 回收时机 | 典型用途 |
| --- | --- | --- |
| 强引用 | 永不主动回收 | 普通 `new` |
| 软引用 `SoftReference` | 内存不足（临近 OOM）时回收 | 图片/缓存兜底 |
| 弱引用 `WeakReference` | 下一次 GC 必回收 | `WeakHashMap`、ThreadLocal key |
| 虚引用 `PhantomReference` | 回收前入队，用于收尾 | 堆外内存释放（`Cleaner`） |

关键在于：**软/弱/虚引用本身也是对象，也参与可达性分析**，只是它们指向的对象被特殊对待：

- 弱引用对象（Referent）如果只被弱引用可达，标记阶段就判定为「可回收」；
- `ReferenceQueue` 用于在对象被回收后通知持有者。

```java
ReferenceQueue<Object> queue = new ReferenceQueue<>();
Object obj = new Object();
WeakReference<Object> ref = new WeakReference<>(obj, queue);
obj = null;
System.gc();
// 稍后 queue.poll() 会拿到 ref，说明 obj 已被回收
Reference<?> r = queue.remove(1000);
System.out.println(r != null ? "已回收并入队" : "未回收");
```

**ThreadLocal 内存泄漏**的本质就是：Entry 的 key 是弱引用（GC 后 key 变 null），value 是强引用，而 Entry 本身挂在 Thread 的 `ThreadLocalMap` 上——只要线程还活着，value 就一直被强引用可达。所以必须 `remove()`。

## 七、生产排查：怎么判断「谁在引用它」？

OOM 现场最常见的困惑是「明明没人用了，为什么还活着」。排查路径：

1. `jmap -dump:live,format=b,file=heap.hprof <pid>` 或容器内 `jcmd <pid> GC.heap_dump`。
2. 用 MAT 打开，看 **Dominator Tree** 找最大支配者。
3. 对可疑对象用 **Path to GC Roots**（重点看 `exclude weak/soft references`）。
4. 如果根路径是一条 `static` 字段，基本就是静态集合类缓存泄漏；如果是 `ThreadLocalMap$Entry`，就是 ThreadLocal 没 remove；如果是 `ClassLoader`，就是类加载器泄漏。

一个特别容易踩的坑：**PermGen/Metaspace 泄漏会连带泄漏整个类加载器下的所有对象**，因为 `ClassLoader` 本身是根，它持有的所有 Class 元数据、静态变量都随之存活。动态代理、热部署、脚本引擎（反复 `new` GroovyShell/URLClassLoader）是重灾区。

## 八、面试常见追问清单

**Q1：可达性分析用什么算法遍历？**
深度优先或广度优先都能做，HotSpot 实际实现中有并发标记的「标记栈」与溢出处理，G1 还用到 SATB 队列。

**Q2：为什么根枚举必须 STW，标记却可以并发？**
根枚举需要「边变化则结论失效」的强一致快照；并发标记则用写屏障 + SATB/增量更新来容忍变化。

**Q3：`finalize()` 会不会让对象「复活」？**
会。JVM 会把「只被 Finalizer 引用、且有 `finalize()` 未执行」的对象放入 F-Queue，由一个低优先级线程执行，执行期间对象可能重新变得可达——这就是「一次复活」。这也是 `finalize` 被废弃（JDK 18 起标记废弃、JDK 20+ 推荐 `Cleaner`）的原因。

**Q4：`System.gc()` 会让根枚举更频繁吗？**
不会改变根的集合，只会触发一次 GC 周期；`-XX:+DisableExplicitGC` 可以让它变成空操作，但要注意 DirectByteBuffer 依赖 `System.gc()` 的兜底释放逻辑。

**Q5：栈上分配和 GC Roots 冲突吗？**
不冲突。逃逸分析判定对象不逃逸后，对象直接分配在栈帧上，压根不进入堆，也就无所谓可达性——它随栈帧出栈自然消亡。

## 九、小结

把这条链路串起来：

**引用计数被淘汰 → 可达性分析 → 根集合必须一致 → 安全点 STW → OopMap 让枚举变快 → 并发标记用写屏障维持三色不变式 → 四种引用细化「可达」的含义 → 出问题时顺根路径定位。**

面试里只要能把「为什么要 STW」和「OopMap 解决了什么」讲清楚，就跨过了「背八股」和「真的懂」的分界线。剩下的，交给 `jmap` + MAT 在生产里反复练习。

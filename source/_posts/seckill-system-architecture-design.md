# 【系统设计】高并发秒杀系统架构设计：从流量削峰到库存扣减

## 面试官：做过秒杀系统吗？说说你是怎么设计的？

秒杀是后端面试中**出现频率最高**的系统设计题，没有之一。它把高并发场景下的所有经典问题都浓缩在了一起：**高流量冲击、超卖、热点数据、缓存一致性、限流降级**。今天这篇，我们从零开始，把秒杀系统的完整设计思路、核心代码和面试追问一次讲透。

## 一、秒杀的业务特点与核心难点

秒杀（Seckill）的业务模型很简单：**在极短时间内（通常几秒到几分钟），以极低价格限量售卖少量商品**。但它的技术特征却极其极端：

| 特点 | 描述 | 带来的问题 |
|------|------|-----------|
| 瞬时流量巨大 | 开售瞬间 QPS 可达平时百倍千倍 | 打垮应用层与数据库 |
| 读写比例极端 | 读多写少，热点集中在少数商品 | 缓存热点、单点压力 |
| 库存有限 | 如 100 件商品，10 万人抢 | 超卖风险 |
| 时间敏感 | 开售前蓄客，开售后瞬间释放 | 流量脉冲，无法水平扩容应对 |

核心难点可以归纳为三个词：**削峰（把瞬时流量摊平）、限流（保护下游）、防超卖（保证数据正确）**。

## 二、整体架构设计：分层削峰

一个成熟的秒杀架构，从用户请求到数据库，需要经过 **6 层防线**：

```
用户（APP/H5）
  │
  ▼
① 前端层：静态化 + CDN + 按钮置灰 + 答题/验证码
  │
  ▼
② 网关层：限流（令牌桶）、黑白名单、风控
  │
  ▼
③ 应用层：无状态集群、本地缓存、接口级限流
  │
  ▼
④ Redis 层：预扣库存（Lua 原子操作）、热点数据
  │
  ▼
⑤ MQ 层：异步下单、流量削峰、异步落库
  │
  ▼
⑥ 数据库层：乐观锁扣库存、订单落库
```

### 第 1 层：前端——把流量挡在门外

- **静态化**：秒杀页面是静态页面，商品详情、倒计时等静态资源全部上 CDN，动态接口只留一个"参与秒杀"的入口。
- **按钮置灰 + 倒计时**：未到开售时间，按钮不可点，避免提前请求。
- **验证码/答题**：开售瞬间自动弹出验证码，人为制造"处理时间"，把瞬时 QPS 摊平（人为削峰）。
- **随机延迟**：客户端在开售瞬间加一个 0~500ms 的随机延迟再发请求，避免所有用户在同一毫秒打进来。

### 第 2 层：网关——限流与风控

网关（Nginx / Spring Cloud Gateway / APISIX）做**全局限流**：

- 按 IP、按用户维度限流（如单用户 1 秒最多 1 次请求）；
- 黑名单拦截脚本机器人；
- 风控规则：同一个收货地址多个账号、新注册账号等标记风险。

限流算法这里用**令牌桶**即可，秒杀场景对突发流量容忍度低，也可以用**漏桶**保证绝对匀速。

### 第 3 层：应用层——无状态与本地缓存

- 应用层必须是**无状态**的，可以随时水平扩容。秒杀前按预估流量扩容到目标实例数。
- 秒杀商品的基本信息（名称、图片、价格）放在**本地缓存（Caffeine）+ Redis 二级缓存**，不走 DB。
- 接口层做**用户维度限流**：同一个 userId 在秒杀接口上做幂等校验，防止重复点击。

### 第 4 层：Redis——库存预扣减（防超卖核心）

**千万不能让所有请求直接打数据库**。正确做法是：**提前把库存加载到 Redis，在 Redis 里用 Lua 脚本完成"校验库存 + 扣减库存"的原子操作**。

```lua
-- 秒杀扣库存 Lua 脚本
-- KEYS[1] = 库存 key（如 seckill:stock:1001）
-- KEYS[2] = 用户已购 key（如 seckill:bought:1001）
-- ARGV[1] = userId
-- ARGV[2] = 限购数量

-- 1. 一人一单校验：用户是否已购买
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return -1  -- 已购买，拒绝
end
-- 2. 库存校验
local stock = tonumber(redis.call('get', KEYS[1]))
if not stock or stock < tonumber(ARGV[2]) then
    return 0  -- 库存不足
end
-- 3. 扣减库存
redis.call('decrby', KEYS[1], ARGV[2])
-- 4. 记录用户
redis.call('sadd', KEYS[2], ARGV[1])
return 1  -- 秒杀成功
```

**为什么必须用 Lua？** 因为 Redis 的 `get` + `decrby` 是两个操作，在高并发下不保证原子性；而 Lua 脚本在 Redis 中是**单线程原子执行**的，天然避免了竞态。

**为什么不在 Redis 里直接生成订单？** Redis 不擅长持久化复杂业务数据，它只负责"谁抢到了"这个高并发判定，抢到之后的生产动作全部异步化。

### 第 5 层：MQ——异步下单与削峰

Redis 扣减成功只是"拿到了资格"，真正的下单是异步的：

1. 秒杀成功 → 发送消息到 MQ（如 RocketMQ / Kafka），消息体包含 userId + 商品Id + 秒杀令牌；
2. 订单服务消费消息，**在数据库事务里**完成：扣减 DB 库存 + 生成订单 + 创建支付单；
3. 用户在页面上轮询或通过 WebSocket 收到"下单结果"。

MQ 在这里起到了两个作用：**削峰**（DB 的消费速度是恒定的，不会瞬间被打爆）和**解耦**（秒杀服务与订单服务互不阻塞）。

### 第 6 层：数据库——用乐观锁兜底

MQ 异步消费时，数据库扣库存**绝不能**用"查库存 → 判断 → update"这种先查后改的方式，必须用**乐观锁**：

```sql
-- 方案一：条件更新（推荐），利用 stock > 0 保证不超卖
UPDATE seckill_stock
SET stock = stock - 1
WHERE goods_id = #{goodsId} AND stock > 0;

-- 受影响行数为 1 表示扣减成功，为 0 表示库存不足
```

```sql
-- 方案二：版本号乐观锁（适合非库存类更新）
UPDATE seckill_stock
SET stock = stock - 1, version = version + 1
WHERE goods_id = #{goodsId} AND version = #{oldVersion};
```

**为什么不直接用数据库？** 秒杀瞬间 10 万 QPS 打到 MySQL 上，即使每次 SQL 只要 1ms，数据库的连接池和行锁也会立刻被打满。Redis 单机 QPS 可以到 10 万+，天然适合做第一道闸门。

## 三、防止超卖的完整链路

超卖的本质是：**多个并发请求同时读到剩余库存 > 0，然后都执行了扣减**。我们的防线是层层递进的：

| 层级 | 手段 | 防什么 |
|------|------|--------|
| Redis Lua | 原子扣减 + 用户去重 | 并发超卖、一人多单 |
| MQ 异步 | 串行消费，DB 压力可控 | DB 被击穿 |
| DB 乐观锁 | `stock > 0` 条件更新 | 最后一道兜底，绝对不超卖 |
| 订单幂等 | 唯一索引（userId + goodsId） | 重复消息、重复提交 |

即使 Redis 和 MQ 全挂了，数据库的 `stock > 0` 条件更新依然能保证**不超卖**——这就是兜底的意义。

## 四、热点问题的进一步优化

### 1. 热点 key 打爆单台 Redis

秒杀商品的库存 key 是典型的热点 key，所有请求都打在同一把锁上。优化手段：

- **本地缓存前置**：秒杀商品的基本信息放 Caffeine，只有"扣库存"这个必须强一致的操作用 Redis；
- **多级库存分片**：把库存 key 拆成 `seckill:stock:1001:0` ~ `seckill:stock:1001:9` 十个分片，请求按 userId 哈希路由到不同分片，压力分摊到多台 Redis 节点；
- **热点 key 探测 + 本地缓存兜底**（读多写少场景）。

### 2. 秒杀令牌（Token）机制

为了防止用户**提前拿到秒杀接口地址后脚本刷接口**，可以采用"秒杀令牌"模式：

1. 用户开售前先请求 `getSeckillToken` 接口，服务端校验时间窗 + 用户身份后签发一个带签名、有时效的 token（如 5 秒有效）；
2. 真正下单时必须在请求头携带 token，服务端验签通过才放行；
3. 令牌还可以携带商品 ID、用户 ID，防止"黄牛代抢"。

### 3. 库存预热与回滚

- **库存预热**：开售前把 DB 库存加载进 Redis（`SETNX` 防重复初始化）；
- **超时回滚**：抢到资格但 15 分钟内未支付，需要把库存加回来——通过延迟队列或定时任务扫描超时订单，用 Lua 脚本 `srem` 用户 + `incrby` 库存，原子完成。

## 五、面试常见追问整理

**Q1：Redis 扣了库存，但 MQ 消费失败导致订单没生成，库存不就少了？**
答：这是典型的"分布式事务"问题。常规做法是**本地消息表 + 定时对账**：订单服务记录一条"待处理"消息，定时任务扫描补偿；同时用 RocketMQ 事务消息（half message + 本地事务 + 回查）保证"扣库存成功"与"发消息成功"要么都发生、要么都不发生。最终一致性即可，秒杀场景允许短暂的库存显示不一致。

**Q2：为什么不用分布式锁而用 Lua？**
答：分布式锁（如 Redisson）能保证互斥，但每次请求都要获取锁，锁的获取/释放本身有网络开销，且锁粒度是"整个扣库存操作"，并发能力不如 Lua 脚本（Redis 单线程原子执行，天然串行化）。在 10 万 QPS 下，Lua 是性能和正确性的最佳平衡。

**Q3：如果 Redis 宕机了怎么办？**
答：秒杀入口直接降级——接口返回"活动太火爆"，或者走 DB 兜底（DB 乐观锁能扛住少量流量，但扛不住 10 万 QPS）。生产上 Redis 一定是**主从 + 哨兵或 Cluster**，秒杀这种关键场景还要做**多级缓存 + 熔断降级**预案。

**Q4：Redis 库存和 DB 库存怎么对账？**
答：定时任务（如每分钟）比对 Redis 剩余库存 + 未支付订单占用 vs DB 剩余库存，不一致时以 DB 为准修正 Redis，并告警人工介入。

**Q5：秒杀接口怎么防脚本刷？**
答：验证码/滑块、用户维度限流、秒杀令牌、设备指纹、风控规则（同一 IP 多账号、同收货地址多账号）多管齐下。

## 六、总结

秒杀系统的设计精髓，一句话概括：**把"瞬时的高并发写"转换成"平缓的异步写"，把"数据库的强一致压力"前置到"Redis 的原子操作"**。记住这条主线——前端挡流量、网关限流、Redis 预扣、MQ 削峰、DB 乐观锁兜底、异步对账补偿——面试时顺着这条链路讲，再配合能写出来的 Lua 脚本和 SQL，基本就是满分回答。

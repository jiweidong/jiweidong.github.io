# MySQL 联合索引与最左前缀原则深度解析：从 B+ 树结构到索引失效场景

## 面试官：联合索引 (a, b, c) 最左前缀原则，能命中哪些查询？

这是 MySQL 索引方向出现频率最高的问题，也是线上 SQL 优化翻车率最高的知识点。很多人只会背"最左前缀"四个字，但不知道为什么、边界在哪、哪些场景会失效。本文从 B+ 树结构出发，把联合索引彻底讲透。

## 一、联合索引的 B+ 树到底长什么样？

单列索引的 B+ 树，非叶子节点存索引值，叶子节点存主键（聚簇索引）或行指针。

**联合索引 (a, b, c) 的 B+ 树：**

```
                    [1, 100, 'x']
                   /            \
        [1, 200, 'a']          [2, 100, 'b']
        /           \          /           \
[1,100,'x']  [1,200,'a']  [2,100,'b']  [2,200,'c']
 (叶子节点：还包含主键 id，可回表)
```

**关键：联合索引的排序规则是逐列比较的**

1. 先按 **a** 排序
2. a 相同的，再按 **b** 排序
3. a、b 都相同的，再按 **c** 排序

这个排序规则就是**最左前缀原则的根本原因**：索引数据是按"先 a 后 b 后 c"的顺序组织的，所以查询条件必须从最左列开始连续匹配，才能利用索引的有序性快速定位。

## 二、最左前缀原则：能用和不能用的边界

假设索引 `idx(a, b, c)`，一一分析：

| 查询条件 | 索引使用情况 | 原因 |
|---------|-------------|------|
| `WHERE a = 1` | ✅ 用到 a | 从最左列开始 |
| `WHERE a = 1 AND b = 2` | ✅ 用到 a, b | 连续匹配 |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ 用到 a, b, c | 全匹配 |
| `WHERE b = 2` | ❌ 用不到索引 | 跳过了最左列 a |
| `WHERE c = 3` | ❌ 用不到索引 | 跳过了 a, b |
| `WHERE b = 2 AND c = 3` | ❌ 用不到索引 | 跳过了 a |
| `WHERE a = 1 AND c = 3` | ⚠️ 只用 a，c 用不到 | b 断开，c 无法定位 |
| `WHERE a > 1 AND b = 2` | ⚠️ a 用于范围，b 用不到 | 范围查询后索引失效 |

### 2.1 为什么 `a = 1 AND c = 3` 只用 a？

因为 B+ 树先按 a 排序，再按 b 排序。当 b 条件缺失时，a=1 对应的是一个**区间**（里面 b 从小到大排列），在这个区间内 c 是**无序的**（因为排序键是 b 而不是 c）。无法二分查找 c，只能用 a 定位区间后再全扫这个区间内的记录过滤 c。

### 2.2 为什么范围查询后面的列用不到？

`a > 1 AND b = 2`：MySQL 用索引定位 a>1 的起始位置，然后**顺序扫描**。扫描过程中 a 在变，b 是散乱分布的（每个 a 值下 b 从最小到最大），无法用 b=2 做索引内的快速过滤，只能逐条判断。

> 注意：MySQL 8.0 的**索引跳跃扫描（Index Skip Scan）** 可以在某些场景下让 `WHERE b = 2`（跳过 a）用上索引，但条件苛刻（a 的基数要小），不能依赖。

## 三、实战：联合索引设计

### 3.1 高频查询反推索引

```sql
-- 业务高频查询：按用户查订单，按时间排序
SELECT * FROM t_order
WHERE user_id = 123 AND status = 'PAID'
ORDER BY create_time DESC LIMIT 20;
```

索引设计思路：`idx(user_id, status, create_time)`

- `user_id` 等值 → 精确定位
- `status` 等值 → 缩小范围
- `create_time` 排序 → **索引天然有序，避免 filesort**（这是联合索引的最大隐藏价值）

### 3.2 排序也能用上联合索引

```sql
-- 索引 (a, b) 下，ORDER BY 利用索引有序性
SELECT * FROM t WHERE a = 1 ORDER BY b;      -- ✅ 索引排序，无 filesort

SELECT * FROM t WHERE a = 1 ORDER BY b, c;   -- ❌ c 不在索引 (a,b) 里，filesort
SELECT * FROM t WHERE a = 1 ORDER BY c;      -- ❌ 跳过 b，filesort
```

**规律**：`ORDER BY` 的列也必须满足最左前缀（且与 WHERE 的等值列连续衔接），才能用索引排序。

### 3.3 覆盖索引：联合索引的进阶玩法

```sql
-- 索引 idx(user_id, status, create_time)
-- 查询只取这三列 + 主键 → 索引覆盖，无需回表
SELECT user_id, status, create_time
FROM t_order
WHERE user_id = 123 AND status = 'PAID'
ORDER BY create_time DESC;

-- EXPLAIN 结果中 Extra = Using index ✅
```

高频查询把要查的列都塞进联合索引，就能避免回表，性能再上一个台阶（注意不要为了覆盖盲目加列，索引不是越多越好）。

## 四、索引失效场景大全（面试必背）

下面这些"看着能用、实际失效"的场景，是线上慢查询的元凶：

| 场景 | 示例 | 原因 |
|------|------|------|
| 对索引列使用函数 | `WHERE DATE(create_time) = '2026-08-16'` | 函数破坏了索引值 |
| 隐式类型转换 | `WHERE phone = 13800138000`（phone 是 varchar） | 类型转换导致无法比较索引值 |
| 模糊匹配前导通配符 | `WHERE name LIKE '%张%'` | 无法确定起始位置 |
| OR 连接非索引列 | `WHERE a = 1 OR b = 2`（b 无索引） | 必须全表扫 |
| NOT IN / NOT EXISTS | `WHERE status NOT IN (1, 2)` | 无法用索引范围定位 |
| 索引列参与运算 | `WHERE a + 1 = 5` | 破坏了索引值 |
| 联合索引不满足最左前缀 | `WHERE b = 2` | 上面已分析 |
| 优化器放弃索引 | 小表全扫比走索引快 | 统计信息/回表成本 |

### 4.1 函数失效的正确写法

```sql
-- ❌ 函数包住索引列
SELECT * FROM t_order WHERE DATE(create_time) = '2026-08-16';

-- ✅ 改成范围查询，索引生效
SELECT * FROM t_order
WHERE create_time >= '2026-08-16 00:00:00'
  AND create_time <  '2026-08-17 00:00:00';
```

### 4.2 隐式转换的坑

```sql
-- phone 是 varchar 类型，查询条件写成数字
SELECT * FROM t_user WHERE phone = 13800138000;
-- MySQL 会把 varchar 转成数字比较，索引失效
-- ✅ 正确写法：加引号
SELECT * FROM t_user WHERE phone = '13800138000';
```

## 五、如何验证？EXPLAIN 看这里

```sql
EXPLAIN SELECT * FROM t_order
WHERE user_id = 123 AND status = 'PAID'
ORDER BY create_time DESC;
```

重点看三列：

| 列 | 含义 | 好 | 坏 |
|----|------|----|----|
| key | 实际用的索引 | idx_xxx | NULL（全表扫） |
| key_len | 索引使用长度 | 越长说明用到的列越多 | 明显偏短说明只用了部分列 |
| Extra | 附加信息 | Using index | Using filesort（排序没走索引） |

**key_len 是验证最左前缀用了几列的黄金指标**：`user_id`(8B) + `status`(1B) + `create_time`(5B 或 8B)，如果 key_len 只有 9，说明只用到了前两列。

## 六、面试高频追问

**Q1：联合索引 (a, b) 和单列索引 a + 单列索引 b 有什么区别？**
联合索引 (a,b) 一棵树同时服务 a 和 a,b 查询，且 b 天然有序（可服务排序）；两个单列索引中，b 的索引无法服务 `WHERE a=1 AND b=2`（MySQL 一般只能选其中一个索引，另一个回表过滤）。所以 (a,b) 通常优于 a+b 两个单列索引，但要注意：如果还有独立的 `WHERE b=2` 查询，则单独建 b 索引也有必要。

**Q2：最左前缀里的"最左"指什么？**
指索引定义时最左边的列。注意是**定义顺序**，不是 SQL 书写顺序。`WHERE b=2 AND a=1` 也能命中（优化器会重排），核心是条件里必须包含最左列 a，且连续。

**Q3：索引建的越多越好吗？**
不是。每个索引都是一棵 B+ 树，写操作要维护所有索引，插入/更新变慢；索引也占磁盘和内存。原则：**只为高频查询建索引**，用 `SHOW INDEX` 定期清理冗余索引（如 (a) 可以被 (a,b) 覆盖时，单独 (a) 就是冗余）。

**Q4：为什么范围查询右边的列会失效，有什么例外？**
MySQL 8.0 对 `a > 1 AND b = 2` 引入了 **Range Optimization for Skip Scan**，部分场景 b 也能用上，但收益有限。通用建议：**把等值条件的列放前面，范围条件的列放最后**，如 `idx(user_id, status, create_time)` 中 user_id 等值在前。

**Q5：联合索引字段顺序怎么定？**
黄金法则：① 等值条件优先；② 区分度高的在前（筛选掉更多数据）；③ 范围/排序字段放最后；④ 经常排序的字段利用索引有序性。例如用户订单查询：`user_id`（等值、高区分度）→ `status`（等值）→ `create_time`（排序/范围）。

## 总结

- **本质**：联合索引 B+ 树按"逐列比较"排序，最左前缀是由数据结构决定的，不是规则
- **能用**：从最左列开始连续匹配，等值列可任意组合（不跳过），排序字段紧跟等值列
- **失效**：跳过中间列、范围查询后的列、函数/隐式转换/LIKE 前置通配/OR 等
- **验证**：EXPLAIN 看 key、key_len、Extra，key_len 是判断用了几列的黄金指标
- **设计**：等值在前、高区分度在前、范围/排序在后、覆盖索引提性能

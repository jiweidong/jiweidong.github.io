# 【AI 转型】AI 应用开发能力模型与技能矩阵：从 Prompt 到 Agent 的 20 项能力拆解

## 前言

很多 Java 工程师对"转 AI"的理解停留在：**会调用大模型 API、会写 Prompt、会跑个 RAG Demo**。但真正投简历、上面试时才发现，面试官问的是：

- 你的 RAG 召回率怎么评测？召回为空时怎么定位是切分问题还是 Embedding 问题？
- 你点多了以后 Token 成本怎么控？上下文超了怎么办？
- Agent 调工具失败了怎么重试与兜底？怎么做权限与审计？
- Prompt 被注入攻击，你怎么防？

**"会用 SDK"和"能交付生产系统"之间，隔着一整套能力模型。** 本文给出一个面向 Java 转 AI 的**四层能力模型 + 20 项技能矩阵**，每项都给出「验证方式」和「对应文章」，让你能自评、能排优先级、能在面试里讲清楚自己站在哪一层。

> 配套阅读：本系列总纲《AI 应用开发工程师学习路线全景》（6 阶段路线）。

## 一、为什么要能力模型

没有模型，学习会陷入三种病：

1. **追热点病**：今天 LangChain、明天 MCP、后天 Agent，每个都浅尝辄止；
2. **伪能力病**：能跑 Demo 就以为掌握了，一遇到生产问题（幻觉、成本、超时、评测）就露馅；
3. **乱序病**：还没搞懂 Token 与上下文，就去做多智能体协作。

**能力模型的作用：把"AI 应用开发"这个模糊岗位，拆成可衡量、可排序、可补强的能力单元。**

## 二、四层能力模型

```
┌───────────────────────────────────────────────────────┐
│ L4 架构层    Agent 编排 / 多智能体 / 系统设计 / 成本压降  │
├───────────────────────────────────────────────────────┤
│ L3 工程层    评测 / 可观测 / 安全 / 并发 / 缓存 / 灰度     │
├───────────────────────────────────────────────────────┤
│ L2 应用层    RAG / 工具调用 / 结构化输出 / 记忆 / 提示工程 │
├───────────────────────────────────────────────────────┤
│ L1 基础层    LLM 认知 / Token / Embedding / API 调用      │
└───────────────────────────────────────────────────────┘
```

- **L1 基础层**：不写这层，后面全是玄学；
- **L2 应用层**：把 LLM 变成"能干活的功能"；
- **L3 工程层**：决定 Demo 与生产的分界线，**最容易被忽视、面试最加分**；
- **L4 架构层**：决定你能带项目还是只能写模块。

## 四、逐层拆解与达标线

### L1 基础层（第 1~4 项）

这是**门槛项**，缺了就会在后两层"知其然不知其所以然"。

- **能力 2（Token 管理）** 是面试最爱问的生产题：上下文超限怎么截断？长对话怎么摘要压缩？怎么核算一次 RAG 问答的 Token 账？对应《上下文窗口与 Token 管理深度实战》。
- **能力 4（Java SDK）** 对 Java 工程师是"平移"：把 `RestTemplate` 换成 `ChatClient`，把 DTO 换成 `Prompt/Response`。

**达标线**：能独立完成"多轮对话 + 结构化输出"的小服务。

### L2 应用层（第 5~10 项）

把 LLM 变成产品功能的六块拼图，**RAG 是重中之重**。

- **能力 8~9（RAG）**：不要只会"跑通"，要能回答"召回为空/答非所问"该怎么排查。参见《RAG 全链路深度实战》《Spring AI RAG 深度实战》。
- **能力 10（记忆）**：多轮对话的上下文是有预算的，必须有摘要/滑动窗口/向量记忆策略。

**达标线**：能交付一个内部知识库问答，且能拿出召回评测数据。

### L3 工程层（第 11~16 项）

**这一层是"Demo 工程师"与"AI 应用工程师"的真正分水岭。**

- **能力 12（评测）**：没有评测的 RAG 调参就是玄学。要会建黄金集、算 Recall@K / MRR / Faithfulness。
- **能力 14（成本）**：Token 是钱。缓存（精确+语义）、模型路由（小模型兜大模型）、输出长度控制，都是实打实的 KPI。
- **能力 15（安全）**：Prompt 注入、越权检索、输出合规，生产事故重灾区。
- **能力 16（并发）**：LLM 调用是慢 IO，Java 的**虚拟线程**在这里终于大显身手。

**达标线**：能独立负责一个 AI 功能的上线，含评测、监控、成本与安全。

### L4 架构层（第 17~20 项）

从"写功能"到"设计系统"。

- **能力 17（Agent 架构）**：ReAct / Plan-and-Execute / Reflection，能讲清适用边界并手写实现。
- **能力 18~19（编排与多智能体）**：DAG、状态机、Human-in-the-loop、角色协作。
- **能力 20（系统设计）**：企业知识库、AI 客服、AI 搜索等整体方案。

**达标线**：能主导一个 Agent 系统从 0 到 1 的架构设计与技术选型。

## 五、自评表（1~5 分）

| 层级 | 项 | 自评(1-5) | 备注 |
|---|---|---|---|
| L1 | 1~4 | | <3 分先别学 Agent |
| L2 | 5~10 | | RAG 要 ≥3 |
| L3 | 11~16 | | 想进大厂这层要 ≥3 |
| L4 | 17~20 | | 对应高级/专家岗 |

**打分建议**：「能给别人讲清楚原理」给 4 分，「能独立在生产落地并解决故障」给 5 分，「跑过 Demo」最多 2 分。

## 六、Java 工程师的能力迁移映射

好消息是，Java 后端的大量能力**可以直接迁移**：

| 你已有的能力 | 在 AI 场景的映射 |
|---|---|
| Spring/依赖注入 | Spring AI Bean 装配、Advisor 链 |
| REST/SSE 开发 | LLM 流式输出、Agent 回调 |
| 高并发/JUC/虚拟线程 | 并发 LLM 调用、批处理 |
| 缓存/Redis | 语义缓存、向量缓存 |
| 可观测（Micrometer/OTel） | LLM Trace、Token 计量 |
| 限流熔断（Sentinel/Resilience4j） | 模型网关降级 |
| 消息队列 | 异步 Agent 任务、长任务编排 |
| 数据库/索引调优 | 向量库选型与检索调优 |

**需要补齐的缺口**：LLM/Embedding 基础认知、提示工程、RAG 检索原理、评测方法学、Agent 范式。**这些恰好是本文矩阵 L1~L2 的部分，也是学习路线前 3 阶段要解决的。**

## 七、常见"伪能力"陷阱

1. **"我会搭 RAG"** ≠ 会用评测证明它好；
2. **"我接过 Agent Demo"** ≠ 处理过工具失败、死循环、成本失控；
3. **"我 Prompt 写得溜"** ≠ 能保证输出稳定可解析；
4. **"我用过 LangChain4j"** ≠ 理解其抽象为什么这么设计；
5. **"我调过 OpenAI"** ≠ 会做多模型路由与降级。

**面试时，把"做过"讲成"踩过什么坑、怎么量化、怎么兜底"，立刻从 Demo 工程师里脱颖而出。**

## 八、怎么用这份矩阵

1. **先自评**，把 ≤2 分的项圈出来；
2. **按层补**：L1 不满别跳 L3；L2 的 RAG 必扎实；
3. **每项配一个产出物**：一篇笔记、一个可运行 Demo、一份评测报告；
4. **三个月一轮回**：重新自评，看哪层涨了分。

**记住：AI 应用工程师的护城河，从来不是"会调 API"，而是 L3 工程层与 L4 架构层——而这恰好是 Java 工程师最好迁移、也最稀缺的地方。**

## 九、总结

- 能力模型 = 四层（基础/应用/工程/架构）× 20 项能力，可自评、可排序；
- **L3 工程层是 Demo 与生产的分水岭**，也是面试最能拉开差距的地方；
- Java 后端的工程能力可直接迁移，缺口集中在 LLM 认知、Prompt、RAG 与评测；
- 下一步：对照《AI 应用开发工程师学习路线全景》，把矩阵缺口排进你的学习计划。

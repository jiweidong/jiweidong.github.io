# 【系统设计】企业 AI Copilot 平台架构设计

## 前言

一个公司里，AI 功能通常是这样长出来的：

- 客服团队接了一个大模型 API，做了个问答机器人；
- 研发团队自己写了个代码补全插件；
- 运营团队用低代码平台接了个「写文案」按钮；
- 数据团队又搞了一套 Text-to-SQL。

半年后，公司有 7 套 LLM 调用、5 份重复的 RAG 管线、4 个不同版本的 prompt、3 套计费口径，以及一个没人说得清的问题：**这个月大模型到底花了多少钱，花在谁身上？**

企业 AI Copilot 平台要解决的，就是把「各自接 API」变成「共享一套能力底座」。它不是一个聊天窗口，而是一层**面向全公司的 AI 基础设施**。

本文给出一套可落地的架构：接入层、统一网关、编排层、能力层、模型层，重点讲清楚四个最容易设计错的地方——多租户隔离、工具注册、权限下推、成本分摊。

---

## 一、先定边界：平台该做什么，不该做什么

| 平台该做 | 平台不该做 |
|---|---|
| 统一接入协议（Web / IM / IDE / OpenAPI） | 替业务决定产品交互 |
| 统一鉴权、配额、审计 | 替业务写业务 prompt |
| 模型接入与路由、快照锁定 | 自己训练基础模型 |
| 工具/知识/记忆的注册与治理 | 替业务维护私有数据 |
| 成本计量与分摊 | 替财务做预算审批 |
| 评测、灰度、可观测 | 替业务背业务指标 |

一句话：**平台提供「能力」和「治理」，业务提供「场景」和「数据」。**

## 二、总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层  Web Copilot │ IM 机器人 │ IDE 插件 │ OpenAPI │ 内部系统 │
└───────────────────────────┬──────────────────────────────────┘
                            │ 统一协议（SSE / WebSocket / HTTP）
┌───────────────────────────▼──────────────────────────────────┐
│ 统一网关                                                      │
│  身份认证 │ 租户识别 │ 配额限流 │ 模型路由 │ 审计日志 │ 成本记账 │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 编排层                                                        │
│  Prompt 注册表 │ Agent Runtime │ 工具注册中心 │ 工作流引擎      │
└───────┬───────────────────┬───────────────────┬──────────────┘
        │                   │                   │
┌───────▼──────┐   ┌────────▼───────┐   ┌───────▼──────────────┐
│ 能力层        │   │ 数据层          │   │ 模型层                │
│ RAG 检索      │   │ 向量库          │   │ 模型注册表            │
│ 记忆          │   │ 文档库          │   │ 多供应商适配          │
│ 评测          │   │ 会话/审计存储   │   │ 配额/降级/快照        │
│ 内容审核      │   │ 成本明细        │   │ 缓存（精确/语义）     │
└──────────────┘   └────────────────┘   └──────────────────────┘
```

关键设计原则：

1. **所有请求必须经过网关**：任何业务直连模型供应商，都意味着绕过配额、审计和记账；
2. **编排层无状态**：会话、任务、成本都外置，便于水平扩容；
3. **模型层只暴露「逻辑模型名」**：业务写 `chat-standard`，不写 `gpt-4o-2026-xx`；
4. **每一层都能独立降级**：模型挂了降级到备用，检索挂了降级到纯生成，工具挂了降级到只读。

## 三、多租户：隔离级别要按数据敏感度选

「多租户」不是加个 `tenant_id` 就完事。不同数据要用不同隔离级别：

| 隔离级别 | 做法 | 成本 | 适用 |
|---|---|---|---|
| L1 逻辑隔离 | 共享索引/表，查询强制带 `tenant_id` filter | 最低 | 普通知识库、公开文档 |
| L2 物理隔离（索引级） | 每租户独立索引/collection | 中 | 客户数据、部门知识库 |
| L3 实例隔离 | 独立向量库/数据库实例 | 高 | 金融、医疗、强合规 |
| L4 部署隔离 | 独立集群/独立 VPC | 最高 | 私有化交付 |

### 3.1 L1 的三个必做项

共享索引最容易被「少写一个 filter」打穿。防御要三道：

```java
// 1. 入参层面：tenant 从凭证解析，绝不从请求体读
public record TenantContext(String tenantId, String userId, Set<String> scopes) {}

// 2. 检索层面：在框架层强制注入，不允许业务手写
public SearchRequest scopedSearch(String query, TenantContext ctx) {
    return SearchRequest.of(s -> s
            .index("kb-" + ctx.tenantId())      // L2：索引名带租户
            .query(q -> q.bool(b -> b
                    .must(m -> m.match(mm -> mm.field("content").query(query)))
                    .filter(f -> f.term(t -> t.field("tenant_id").value(ctx.tenantId()))))));
}

// 3. 存储层面：行级安全兜底（PostgreSQL RLS / 独立 schema）
```

### 3.2 租户不是「客户」

企业内部平台通常有三层：**公司 → 部门 → 用户**。配额、知识库、工具权限往往按部门配置，计费按成本中心归集。数据模型至少要有：

```
tenant（租户/公司）
  └── org_unit（部门/团队，树形）
        └── user
              └── app（业务应用，真正的调用方）
```

配额挂在 `app` 上，账单归集到 `org_unit`，权限继承沿树向上。这套模型不定清楚，后面所有计量都会返工。

## 四、统一鉴权：用户身份与服务身份要分开

平台里有两类调用：

| 类型 | 身份 | 凭证 | 权限来源 |
|---|---|---|---|
| 用户发起 | 员工/客户 | OIDC / OAuth2 用户 token | 用户在业务系统的权限 |
| 服务发起 | 业务应用 | mTLS / 服务 token | 应用被授予的 scope |

### 4.1 工具调用必须「代表用户」

这是 Copilot 平台最核心的安全设计。假设 Agent 要帮用户查订单：

- 不能用平台的超级服务账号查——它会绕过用户权限；
- 应该用 **token exchange（RFC 8693）** 换一个「代表该用户、且 scope 被收窄」的短期 token；
- 下游服务按这个 token 做鉴权，天然复用已有权限体系。

```java
// 伪代码：工具执行前换取代表用户的 token
String userToken = tokenExchange.exchange(
        serviceToken,
        Map.of("subject_token", userAccessToken,
               "audience", tool.audience(),
               "scope", String.join(" ", tool.requiredScopes())));

ToolResult result = toolClient.call(tool, args, userToken);
```

### 4.2 权限下推到检索，而不是检索后过滤

RAG 场景（已有专文讨论）要先在检索条件里带 ACL，而不是取回 Top-50 再过滤。否则会出现「召回 50 条，过滤后只剩 2 条」的召回悖论。

平台层可以提供统一的 `AclFilter` 接口，让各知识库适配：

```java
public interface AclFilter {
    /** 返回可直接下推到检索引擎的过滤表达式 */
    FilterExpr forUser(TenantContext ctx, String knowledgeBaseId);
}
```

## 五、工具注册中心：平台的「应用商店」

工具是 Copilot 的手脚，也是最容易失控的地方。每个工具必须有不可变的 manifest：

```json
{
  "name": "crm.query_order",
  "version": "2.3.0",
  "description": "按订单号或用户手机号查询订单状态",
  "whenNotToUse": "不要用于退款、改地址等写操作",
  "inputSchema": {
    "type": "object",
    "properties": {
      "orderNo": { "type": "string", "pattern": "^[0-9]{12}$" },
      "phone":   { "type": "string", "pattern": "^1[3-9][0-9]{9}$" }
    },
    "additionalProperties": false
  },
  "sideEffect": "read",
  "requiredScopes": ["crm.order.read"],
  "timeoutMs": 3000,
  "owner": "crm-team",
  "sla": { "p99Ms": 800, "availability": "99.9" }
}
```

### 5.1 准入五道门

| 门 | 检查项 | 不通过的后果 |
|---|---|---|
| Schema 门 | JSON Schema 合法、`additionalProperties=false` | 模型传错参数导致误操作 |
| 权限门 | `requiredScopes` 已注册、可被 exchange | 越权调用 |
| 副作用门 | 写操作必须声明、必须支持幂等键 | 重试导致重复下单 |
| 超时门 | `timeoutMs` 必填且 ≤ 平台上限 | 长尾拖垮会话 |
| 归属门 | owner 团队、值班人、SLA | 出问题找不到人 |

### 5.2 工具数量与检索

工具超过 20~30 个后，全量塞进 prompt 会显著降低选择准确率（已有专文讲工具检索）。平台层要提供：

- **工具分组**：按业务域打包，模型先选组再选工具；
- **动态工具集**：按用户权限、当前页面上下文裁剪；
- **工具检索**：BM25 + 向量召回 + 重排，只把 Top-8 放进 prompt。

### 5.3 版本与退役

工具 manifest 不可变，升级即新版本：

```
crm.query_order@2.2.0  →  deprecated（仍可调用，告警）
crm.query_order@2.3.0  →  active
crm.query_order@1.x    →  retired（拒绝调用，返回明确错误）
```

退役不能直接删。旧会话、旧 prompt 可能还引用旧版本，直接删会变成「模型能看见工具名但调不通」的诡异状态。

## 六、模型层：业务永远不写模型名

```java
// 错误：业务硬编码模型名
chatClient.prompt().options(ChatOptions.builder().model("gpt-4o-2026-01").build());

// 正确：业务写逻辑模型名，由平台解析
chatClient.prompt().options(ChatOptions.builder().model("chat-standard").build());
```

平台维护一张映射表：

| 逻辑名 | 主模型 | 备用模型 | 用途 | 最大 token |
|---|---|---|---|---|
| `chat-fast` | 小模型 A | 小模型 B | 分类、改写、路由 | 4k |
| `chat-standard` | 中模型 | 备用中模型 | 通用对话 | 16k |
| `chat-reasoning` | 推理模型 | 备用推理模型 | 复杂规划 | 32k |
| `embedding-default` | 向量模型 | — | 检索 | — |

好处：

- 换供应商只改映射，业务无感；
- 按租户灰度新模型（10% 租户走新模型）；
- 成本核算按逻辑名聚合，不随供应商价格波动而失真；
- 降级策略清晰：主模型 429/5xx 超阈值 → 自动切备用。

**Embedding 是例外**：换 embedding 模型等于换索引，必须整库重建 + 双写灰度，不能像 chat 一样无缝切换。

## 七、成本分摊：从「月底一张账单」到「实时账本」

LLM 成本有三个特点：**按 token 计费、价格随模型差异巨大、容易被少数用户吃掉**。所以记账必须是实时的、多维的。

### 7.1 记账维度

| 维度 | 用途 |
|---|---|
| `tenant_id` / `org_unit` | 部门分摊 |
| `app_id` | 业务应用成本 |
| `user_id` | 异常用量定位 |
| `feature` | 功能级 ROI（客服/写作/代码） |
| `model` / `prompt_version` | 模型与 prompt 优化效果 |
| `cache_hit` | 缓存节省核算 |

### 7.2 预扣 + 结算

流式调用无法预知输出 token，所以采用两阶段：

```
1. 预扣：按 max_tokens 估算上限，先从配额扣减（Redis Lua 原子）
2. 结算：流结束后按实际 usage 回补差额
3. 超时/断流：按已产出 token 结算，剩余退还
```

```java
public record Usage(String tenantId, String appId, String model,
                    long inputTokens, long outputTokens, boolean cacheHit) {}

public void settle(Usage u) {
    long costMicros = pricing.costMicros(u);   // 用「微元」避免浮点误差
    quota.refund(u.tenantId(), reservedMicros - costMicros);
    ledger.append(u, costMicros);              // 写成本明细（异步、批量）
    meterRegistry.counter("llm.cost.micros",
            "tenant", u.tenantId(), "model", u.model()).increment(costMicros);
}
```

### 7.3 三个必须的护栏

1. **单用户日预算**：防止一个脚本刷爆整个部门配额；
2. **异常检测**：某 app 的 token/请求比突增 3 倍，自动告警；
3. **缓存抵扣核算**：语义缓存命中也要记账（成本为 0），否则无法证明缓存的价值。

## 八、可观测：一条 trace 贯穿到底

```
trace_id
 ├── span: gateway.auth
 ├── span: gateway.quota
 ├── span: orchestration.prompt_render
 ├── span: retrieval.search          (top_k, 命中数, 耗时)
 ├── span: llm.chat                  (model, input_tokens, output_tokens, ttft)
 ├── span: tool.call                 (tool, 耗时, 状态)
 └── span: guardrail.output          (命中规则, 处置)
```

指标分三层：

| 层 | 指标 | 用途 |
|---|---|---|
| 技术 | QPS、P99、错误率、429 率 | 稳定性 |
| 成本 | token/请求、单次成本、缓存命中率 | 经济性 |
| 质量 | 采纳率、修改率、弃答率、转人工率、点踩率 | 有效性 |

**质量指标是平台最容易缺的一层**。没有它，你只能证明「系统没挂」，证明不了「系统有用」。

## 九、降级：四级开关

| 级别 | 触发 | 动作 | 用户感知 |
|---|---|---|---|
| L1 模型降级 | 主模型 429/5xx 超阈值 | 切备用模型 | 质量略降 |
| L2 检索降级 | 向量库超时 | 跳过检索，纯生成 + 提示「未引用知识库」 | 准确性下降 |
| L3 功能降级 | 工具大面积失败 | 关闭写工具，只保留只读 | 功能减少 |
| L4 排队限流 | 全局过载 | 排队 / 拒绝低优先级租户 | 变慢或失败 |

关键原则：**降级要显式告知用户**。偷偷降级比报错更伤信任——用户会以为「AI 今天变笨了」，而不是「系统过载了」。

## 十、安全与合规清单

- **Prompt 注入**：检索内容与用户输入都视为不可信，工具调用前做参数白名单校验；
- **输出审核**：流式滑窗审核，命中高危立即截断（已有专文）；
- **PII**：日志与 trace 中脱敏，原文只存加密字段；
- **数据出境**：按租户配置模型路由，敏感租户只走境内模型；
- **审计留存**：谁、什么时候、用什么 prompt、调了什么工具、返回了什么，至少留 6 个月；
- **密钥管理**：供应商 key 存 KMS，按租户/应用维度隔离，禁止打进镜像。

## 十一、演进路线：三步走

### 阶段一：统一网关（0~3 个月）

先解决「到处都是 key」的问题：

- 统一模型接入与鉴权；
- 基础配额与成本记账；
- 统一日志与 trace。

这一步不需要 Agent，价值立刻可见：成本可查、key 可管。

### 阶段二：能力平台（3~9 个月）

- Prompt 注册表与版本管理；
- RAG 能力复用（文档接入、切分、检索统一）；
- 工具注册中心与权限模型；
- 评测集与灰度发布。

### 阶段三：Agent 平台（9 个月+）

- 多步 Agent Runtime（规划、工具、记忆、人工介入）；
- 多智能体协作与工作流编排；
- 自助式应用搭建（低代码编排）；
- 成本优化（级联、缓存、批处理）。

**不要跳过阶段一直接做 Agent 平台**。没有统一网关，Agent 的每次工具调用都是一个新的安全漏洞和一笔说不清的成本。

## 十二、面试追问

**Q1：多租户怎么保证数据不串？**

分三层：凭证里解析租户（不信任请求体）、检索/查询在框架层强制注入租户过滤、存储层用行级安全或独立索引兜底。敏感租户直接升到物理隔离。

**Q2：工具调用为什么要 token exchange，不能直接用服务账号？**

服务账号是平台身份，权限过大且无法归因到人。token exchange 换来的是「代表该用户、scope 收窄、短期有效」的 token，下游鉴权天然复用现有权限体系，也能审计到具体用户。

**Q3：怎么防止某个业务把预算吃光？**

三道护栏：单用户/单应用日预算、实时用量异常检测（token/请求比突增）、按优先级排队。配额用 Redis Lua 原子预扣，流式结束后按实际 usage 结算。

**Q4：换模型为什么不能像换配置一样简单？**

Chat 模型可以，因为输入输出语义稳定；Embedding 模型不行，向量空间变了，旧索引全部失效，必须双写 + 回填 + 灰度 + 召回率回归。

**Q5：平台怎么证明自己有价值？**

技术指标证明稳定，成本指标证明省钱，质量指标（采纳率、弃答率、转人工率）证明有用。三者缺一不可，尤其质量指标最容易被忽略。

## 十三、总结

企业 AI Copilot 平台的本质，是把「AI 能力」当成一项**需要治理的基础设施**来建设：

- **入口统一**：所有调用过网关，才有配额、审计、记账；
- **身份清晰**：用户身份与服务身份分离，工具调用代表用户；
- **工具可治理**：manifest 不可变、准入有门、退役有流程；
- **模型可替换**：业务只写逻辑名，平台管映射与快照；
- **成本可分摊**：实时账本、多维归集、预算护栏；
- **降级可感知**：四级开关，显式告知。

做对了这些，业务团队接 AI 只需要三行代码；做错了，每个团队都会长出一套自己的「AI 中间层」，最后公司收获七套账单和一堆事故。

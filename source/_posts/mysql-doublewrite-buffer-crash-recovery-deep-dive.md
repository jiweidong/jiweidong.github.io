# 【MySQL 底层】InnoDB 双写缓冲（Doublewrite Buffer）深度解析：页断裂、崩溃恢复与性能取舍

## 面试官：数据库机器突然断电，重启之后为什么数据不是坏的？

大多数人第一反应是"因为有 redo log"。这个答案不算错，但它解释不了另一个更隐蔽的问题：**redo log 本身也是一个文件，它靠什么保证不坏？**

再想深一层。InnoDB 写数据页的单位是 16KB，而操作系统写磁盘的最小单位是 512B（或 4KB）。一次 16KB 的写入不是原子的——如果在写到一半的时候断电，磁盘上就会留下一个**写了一半的页**。这种页既不是旧数据，也不是新数据，而是一堆新旧混杂的字节。等恢复流程拿起 redo log 去"重放"时，它无法判断这个页到底是完整的还是残缺的，于是就有了经典的 **"页断裂"（torn page / partial page write）** 问题。

双写缓冲（Doublewrite Buffer）就是为了解决这个问题而存在的。它是 InnoDB 里非常小、但非常关键的一块逻辑。下面从它的物理结构、写入流程、恢复流程、性能开销一路讲到 8.0 的新变化。

---

## 一、页断裂到底是怎么发生的

先把问题量化清楚。

InnoDB 的页大小默认 16KB。假设现在要把页 P 从版本 A 刷成版本 B，磁盘写入过程中断电：

```
磁盘上的页 P：
┌──────────────┬──────────────┐
│ 新数据（前 8KB）│ 旧数据（后 8KB）│
└──────────────┴──────────────┘
         ↑ 写到这里断电
```

这个页现在处于"半新半旧"状态。它内部有自己的校验：

- **页头/页尾的 checksum**：InnoDB 每个页头部有 `FIL_PAGE_SPACE_OR_CHKSUM`，页尾有 `FIL_PAGE_END_LSN`，用来校验页的完整性；
- 重新计算 checksum 会发现对不上，但问题是：**checksum 只能告诉你"这页坏了"，不能告诉你"它应该长什么样"。**

如果只有 redo log 一种机制，恢复时 InnoDB 看到这个页 checksum 失败，理论上可以尝试重放 redo。但重放的前提是"我知道这个页的起点状态"。一个残缺的页既不是状态 A 也不是状态 B，redo 的物理/逻辑日志无法在一个损坏的页面上可靠地往前推。

所以必须有一个地方，**保证 16KB 的页写入是"可复原"的**。

## 二、双写缓冲的物理结构

### 2.1 经典布局（8.0.20 之前）

双写缓冲区的逻辑管理单元在内存中，物理存储则放在**系统表空间 `ibdata1`** 里的一块固定区域：

- 大小：**2MB**
- 页数：2MB / 16KB = **128 个页**
- 用途划分：每次刷脏页时，**一批最多 128 个页**可以被复制过去

注意一个常见误解：这 2MB 区域是"写坏页的备份"，但它的容量固定是 128 页，因此刷脏页是**分批进行**的，而不是一次性把 buffer pool 里所有脏页都写过去。

### 2.2 MySQL 8.0.20+ 的变化：独立 dblwr 文件

从 **MySQL 8.0.20** 开始，双写缓冲从 `ibdata1` 中移出，改成独立的 `.dblwr` 文件：

```
# innodb_data_home_dir/data 目录下
# 每个 doublewrite 文件对应一个 buffer pool instance
#dblwr/ 目录（或 ib_16384_0.dblwr / ib_16384_1.dblwr）
```

这样做的好处：

1. **摆脱 128 页上限**：可以按需扩展，支持更大的并发刷盘量；
2. **减少 `ibdata1` 的锁竞争**：原方案里双写区域在系统表空间的固定位置，会带来额外的串行化；
3. **支持并行刷脏**：新的实现引入了 `innodb_doublewrite_pages`、`innodb_doublewrite_batch_size` 等参数来调节批处理粒度。

## 三、一次脏页刷盘的完整流程

理解双写缓冲，关键是理解"**顺序写两次 + 一次 fsync 落盘**"这个设计。假设某次刷脏有 N 个页（N ≤ 128）：

```
步骤 1  把 buffer pool 中的 N 个脏页复制到内存中的 doublewrite buffer
        （纯内存拷贝，不落盘）

步骤 2  doublewrite buffer 里的 N 个页，顺序地写到磁盘上的 doublewrite 区域：
        ├─ 8.0.20 之前：写入 ibdata1 的 2MB 区域
        └─ 8.0.20 之后：写入独立 .dblwr 文件
        ★ 这是一次大块顺序写 + fsync

步骤 3  确认 doublewrite 区域已经落盘后，才把这 N 个页分别写到
        各自真正的表空间文件（.ibd / undo 等）

步骤 4  数据页落盘成功后，doublewrite 区域里的副本就可以被覆盖了
        （它不是日志，不需要保留，只在一个刷盘周期内有效）
```

用一张图看关键点：**先写到指定的连续位置，再写到各自的真实位置。**

```
                    ①内存拷贝
 buffer pool ────────────────────► doublewrite buffer(内存)
  脏页 N 个                              │
                                        │ ②顺序写 + fsync
                                        ▼
                    doublewrite 区域（磁盘连续区域）
                                        │
                                        │ ③分发写到真实位置
                        ┌───────────────┼───────────────┐
                        ▼               ▼               ▼
                     t1.ibd          t2.ibd          undo.ibd
```

### 3.1 为什么这样就能防页断裂

关键在**第二步**。磁盘的写入单位是扇区，当把 N 个 16KB 的页顺序写到一块连续的 doublewrite 区域时：

- 如果在第二步的中间断电，doublewrite 区域里的某个副本可能是不完整的；
- 但此时**真实表空间里的页还没被碰过**，仍然是完整的旧版本，机器恢复后数据是自洽的，只是少了一次未提交的更新（这由 redo 决定是否重放）；
- 如果第二步成功 fsync 了，那么 doublewrite 区域的副本一定完整，此时再去覆盖真实页，即使第三步断电，真实页坏了，也能**从对照的完整副本里拷回来**。

也就是说，双写缓冲把"不可复原的部分写"转化成了"可复原的备份先落盘"。它本质上是在**用户数据页和磁盘之间插入的一层"崩溃安全中转"**。

## 四、崩溃恢复时发生了什么

MySQL 启动时，InnoDB 的恢复分两个大阶段：**先处理双写缓冲，再重放 redo**。

```
阶段一：Doublewrite Recovery
  遍历 doublewrite 区域中的每个页
  ├─ 页的 checksum 正确  ──► 说明是完整副本，可以用于修复
  └─ 页的 checksum 损坏  ──► 丢弃（副本本身就没写完）

  再去检查真实表空间中的页：
  ├─ checksum 正确 ──► 什么都不用做
  └─ checksum 损坏 ──► 从 doublewrite 区域的完整副本拷贝回真实页

阶段二：Redo Apply
  用 redo log 从上次 checkpoint 的 LSN 开始，重放所有已提交但未刷盘的修改
```

**注意顺序：必须先做双写恢复，后做 redo 重放。**

原因很直白：redo 重放是"在页面上做增量修改"，它要求页的起点是一个可信的状态。如果页本身是断裂的，redo 重放出来的结果就是错的。所以双写恢复负责把页"修好"，redo 负责把页"更新到最新"。

这也解释了一个面试高频问题：**"双写缓冲和 redo log 是重复了吗？"**

不重复，职责完全不同：

| 机制 | 解决的问题 | 数据粒度 | 生命周期 |
|---|---|---|---|
| redo log | 已提交事务的修改不能丢 | 逻辑/物理混合的日志记录 | 持久，循环使用 |
| doublewrite | 数据页写入不能"写一半" | 完整 16KB 页副本 | 一个刷盘周期内有效 |
| undo log | 事务回滚、MVCC 快照 | 反向操作记录 | 事务结束/版本不可见后清理 |

## 五、性能开销：双写缓冲值不值

双写缓冲的代价是显而易见的：**每个脏页都要被写两次**（一次到 doublewrite 区域，一次到真实位置）。那为什么还要用它？

因为第一次写是**顺序的大块写**，第二次是**离散写**。顺序写在机械盘和 SSD 上都明显更快，而且两批写可以合并 fsync 次数。总的来说，双写缓冲带来的额外开销通常在 **5% ~ 15%** 的写入吞吐下降量级（具体取决于磁盘、batch 大小、竞争情况），换来的是崩溃时的数据安全。

### 5.1 什么时候可以安全地关掉它

这是非常经典的追问："**你的业务能接受丢数据吗？**"

只要满足下面任意一条，双写缓冲就可以考虑关闭（`innodb_doublewrite=OFF`）：

1. **使用支持原子写的文件系统/存储**：例如 ZFS、部分企业级 SSD 阵列声称 16KB 原子写，页断裂在硬件层就不会发生；
2. **有更上层的一致性保证**：例如云数据库本身做了副本 + 强一致同步，主库崩了直接从备库切换（但要评估故障切换时的数据丢失窗口）；
3. **业务数据和从库可重建**：比如纯缓存、可重算的分析数据；
4. **MySQL 8.0.20+ 的 `innodb_doublewrite=DETECT_ONLY`**：只做检测不做恢复（用于诊断），不能替代真正的保护。

### 5.2 关键参数一览

```ini
[mysqld]
# 双写缓冲总开关：ON(默认) / OFF / DETECT_ONLY(8.0.20+)
innodb_doublewrite = ON

# 8.0.20+：每个 batch 的页数上限（默认 128）
innodb_doublewrite_pages = 128

# 8.0.20+：单个 batch 最多处理的页数（8.0.20 引入，默认 128）
innodb_doublewrite_batch_size = 128

# 8.0.20+：双写文件所在目录（可与数据目录分盘）
# innodb_doublewrite_dir = /data/dblwr

# 8.0.30+：双写文件数量，独立控制（默认按 buffer pool instance）
# innodb_doublewrite_files = 2
```

配合刷盘策略一起看：

```ini
# redo 的刷盘策略，决定事务提交的持久化强度
innodb_flush_log_at_trx_commit = 1   # 每次提交 fsync，最安全
# 0 = 每秒刷，崩溃可能丢 1 秒
# 2 = 提交时写 OS cache，由 OS 决定刷盘

# 数据文件刷盘方式，O_DIRECT 可绕过 OS page cache，减少双写与 page cache 的双重缓冲
innodb_flush_method = O_DIRECT
```

**一个常见误区**：有人以为 `innodb_flush_log_at_trx_commit=2` 就能关掉双写。不是的，它只影响 redo 的刷盘时机，与数据页的页断裂保护是两回事。反过来，即使 redo 设成 2，双写缓冲依然在保护数据页的完整性。

## 六、实战：怎么观察双写缓冲

### 6.1 看统计信息

```sql
-- 双写相关的页数统计（8.0）
SHOW GLOBAL STATUS LIKE 'Innodb_dblwr%';
-- Innodb_dblwr_pages_written   : 写入双写区域的页数
-- Innodb_dblwr_writes          : 双写区域的写入次数
```

在 8.0.20 之前，这些信息更多体现在 `SHOW ENGINE INNODB STATUS` 里：

```
SHOW ENGINE INNODB STATUS\G
...
Pages written 1234567
...
```

### 6.2 看双写文件

```bash
# 8.0.20+ 在数据目录下可以看到 .dblwr 文件
ls -lh /var/lib/mysql/#ib_16384_*.dblwr
# -rw-r----- 1 mysql mysql 192K  #ib_16384_0.dblwr
# 大小 = 页大小 × 页数，会随配置和 buffer pool 规模变化
```

### 6.3 用压测验证开关的影响

不要凭感觉猜，动手测：

```bash
# 打开/关闭双写，用 sysbench 对比写入吞吐
sysbench --db-driver=mysql --mysql-user=root \
  --mysql-socket=/var/lib/mysql/mysql.sock \
  --tables=10 --table-size=1000000 \
  --threads=32 --time=120 \
  oltp_write_only prepare

# 基准：innodb_doublewrite=ON
sysbench ... oltp_write_only run

# 对比：SET GLOBAL innodb_doublewrite=OFF; （需要重启或动态支持）
sysbench ... oltp_write_only run
```

对比时要同时记录 `iostat -x 1` 的 `w/s`、`%util`、`await`，以及 `Innodb_dblwr_pages_written` 的增幅，才能把"额外写放大"量化出来。

## 七、面试常见追问

**Q1：双写缓冲和 redo log，谁的顺序在前？**

写入时是"双写区域 → 真实页"，redo 的 fsync 在事务提交时就已发生，与刷脏页是两个时间点。恢复时是"双写修复 → redo 重放"。记住 **"先修页，再重放"**。

**Q2：既然双写缓冲也要 fsync，为什么比直接写两次数据页快？**

因为双写区域是**连续顺序写**，一次 fsync 可以覆盖一整批（最多 128 个页）；而真实页的写入是分散的。批量 fsync 摊薄了每次刷盘的系统调用和磁盘寻道开销。

**Q3：双写缓冲会丢数据吗？断电时会不会连双写区域也坏？**

双写区域本身也可能写坏，但它在"写双写"和"写真实页"之间做了时序上的隔离：真实页坏时，双写副本必然是完整的（因为真实页的写入发生在双写副本 fsync 成功之后）。这是靠写入顺序保证的，不需要双写副本自身"永不损坏"。

**Q4：为什么 8.0.20 要把双写从 ibdata1 挪出来？**

原有实现受 128 页上限约束，且在系统表空间固定区域内操作，多个 buffer pool instance 刷脏时要竞争，容易成为写密集场景的瓶颈。独立 `.dblwr` 文件支持按实例分配、可扩展容量、可单独放置到更快的设备上。

**Q5：`innodb_doublewrite=OFF` 但 `innodb_flush_log_at_trx_commit=1`，安全吗？**

不完全安全。redo=1 保证的是"已提交事务的日志不丢"，但**如果数据页写坏了，redo 无法在一个损坏的页上正确重放**，重启后可能直接报页损坏（`Database page corruption`）。两者保护的是不同层面，不能互相替代。

## 八、总结

- **页断裂**的本质：16KB 页的大小超过了磁盘最小原子写单位，写入过程中断电会产生无法解释的"半新半旧"页。
- **双写缓冲**用"先顺序写一份完整副本，再覆盖真实页"的方式，把不可恢复的写变成可恢复的写。
- **崩溃恢复顺序**：先双写修复（补坏页），再 redo 重放（追更新）。
- **代价与收益**：约 5%~15% 的吞吐下降，换来断电后的数据页完整性；只有确认存储支持原子写或有强一致副本时，才建议关闭。
- **8.0.20+** 是重要的实现分水岭，独立 `.dblwr` 文件、可配置 batch、可独立分盘。
- 排查时看 `Innodb_dblwr_pages_written` / `Innodb_dblwr_writes` / `SHOW ENGINE INNODB STATUS`，并用 sysbench 做开关对比量化影响。

一句话记住它：**redo log 保证"提交的日志不丢"，双写缓冲保证"页的写入不烂"。**

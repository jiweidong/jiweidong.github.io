# 【系统设计】搜索系统架构设计：索引构建、查询理解、召回排序与个性化全解析

## 面试官：设计一个站内搜索系统，你怎么做？

很多同学的答案是：「上 Elasticsearch，把数据同步进去，`match` 查一下就行」。

这个回答能撑过 5 分钟。接下来的追问就挡不住了：

- 数据怎么进 ES？全量 + 增量怎么保证一致？
- 用户搜「怎么退换货」搜不到「退货流程」怎么办？（同义词/语义）
- 搜「华为手机」为什么不该召回「华为平板」？（意图与相关性）
- 排序凭什么把 A 排在前？相关性怎么定义、怎么评估？
- 大促流量涨 10 倍怎么办？重建索引时线上不能停怎么办？

搜索系统是**「数据 + 检索 + 排序 + 工程」**的复合体。这篇文章按「索引 → 查询理解 → 召回 → 排序 → 工程化」五段主线讲透。

---

## 二、索引构建：一致性与实时性

搜索系统的「数据从哪来、怎么进索引」是最容易被低估的部分，也是面试中区分度高的话题。

### 数据链路

```text
业务库 MySQL
    │
    ├─(1) 全量：定时任务 / 数据导出 ──► 离线数仓 ──► 批量建索引
    │
    └─(2) 增量：Binlog(Canal) ──► Kafka ──► 索引构建消费者 ──► ES
                  ▲
                  └─ 双写 / 业务 MQ 消息（可靠消息）
```

**三种同步方式对比**：

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 双写 | 业务代码同时写 DB 和 ES | 简单 | 耦合业务、一致性差、失败难补偿 |
| Binlog 订阅（Canal） | 解析 MySQL Binlog | 无侵入、可靠 | 与 DB 结构耦合、有延迟 |
| 业务 MQ | 业务发消息，消费者写 ES | 解耦、灵活 | 需要业务改造、可能丢消息 |

**推荐方案**：**MySQL Binlog（Canal）为主 + 全量重建兜底 + 对账校验**。

### 全量重建：如何做到不停机

搜索索引的字段、分词器、Mapping 变更往往需要**重建索引**。直接删了重建会导致线上不可用。正确姿势是**别名切换（Alias + Reindex）**：

```text
1. 新建索引 products_v2，写入全量数据
2. 双写：增量数据同时写 v1 和 v2（或用 Binlog 补差）
3. 校验：对比 v1 和 v2 的文档数、抽样结果
4. 切换别名：products -> products_v2（原子操作）
5. 观察一段时间后删除 v1
```

```json
// 别名切换：一次请求原子完成
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products_v1", "alias": "products" } },
    { "add":    { "index": "products_v2", "alias": "products" } }
  ]
}
```

**要点**：读请求永远走**别名**，索引名不写死在代码里。

### 增量一致性与延迟

- **近实时（NRT）**：ES 默认 `refresh_interval=1s`，写入后最多 1 秒可搜到；
- **写后读一致性**：用户刚发布的商品立刻搜索不到，体验很差。解决：写入时带上 refresh 或**结果合并**（把「用户自己的最新数据」手动合并进搜索结果）；
- **乱序问题**：Kafka 消费可能乱序（更新和删除交叠），要用**版本号 / 时间戳**做条件更新，丢弃旧版本：

```java
// 条件更新：只有新版本才覆盖（用 ES 的 version / script 实现）
if (incomingVersion <= existingVersion) {
    return;   // 丢弃过期消息
}
```

- **删除**：物理删除 vs 逻辑删除（软删标记 + 查询过滤），搜索场景常用**软删 + 定期物理清理**，便于回滚。

## 三、查询理解：把「人话」变成「检索式」

这是搜索系统**最体现工程智慧**的一层，也是和「直接用 ES」的最大差距。

```text
用户输入: "华为手机 5000左右 拍照好的"
   │
   ├─ 分词:      [华为手机] [5000] [左右] [拍照] [好]
   ├─ 纠错:      "华为手几" → "华为手机"
   ├─ 同义词:    "移动电话" → "手机"，"退换货" → "退货|换货"
   ├─ 归一化:    尺寸/单位/大小写/繁简/全半角
   ├─ 意图识别:  品类=手机, 价格区间=[4000,6000], 属性=拍照好
   └─ Query 改写: 华为 AND (手机 OR 智能手机) AND 价格:[4000 TO 6000]
```

### 分词

中文分词是搜索的基础。工程上常用：

| 方案 | 说明 |
| --- | --- |
| 词典分词（IK） | 基于词典 + 规则，可控、可干预，主流 |
| 新词发现 | 从日志挖掘未登录词，定期更新词典 |
| 自定义词典 | 品牌、型号、行业术语必须人工维护 |

**关键实践**：搜索分词与索引分词必须使用**同一套词典和分词器**，否则「索引时分出的词」和「查询时分出的词」对不上，召回率会崩。这也是 `elasticsearch-chinese-analyzer-ik` 里反复强调的点。

### 纠错（Spell Correction）

```text
"平果手机" → "苹果手机"
"华维"     → "华为"
```

工程实现：

1. **词典 + 编辑距离**：对查询词做 1~2 个编辑距离的候选生成，按词频/热度排序；
2. **拼音纠错**：同音字混淆（平果/苹果）用拼音索引召回；
3. **N-gram 模型**：统计相邻字共现概率；
4. **日志挖掘**：从「零结果查询」中挖掘高频错别字。

**重要原则**：纠错宁可**少纠**也不**错纠**。错纠会直接毁掉用户意图。通常设置高阈值，且只对高频词纠错。

### 同义词与查询扩展

```text
退换货 → [退货, 换货]
手机   → [智能手机, cellphone]
```

- **索引期扩展** vs **查询期扩展**：查询期扩展更灵活、可动态调整；索引期扩展会放大索引体积。
- **双向同义词** vs **单向**：`华为 → 华为技术` 单向即可；`手机 ↔ 智能手机` 双向。
- **权重控制**：扩展词权重应低于原词，避免噪声召回。

### 意图识别

```text
"华为mate60"     → 实体/商品意图
"怎么退货"       → 问答/教程意图
"华为 vs 小米"   → 对比意图
"附近的充电宝"   → 本地/位置意图
```

意图决定了**召回哪些数据源**（商品库 / 文章库 / FAQ 库）和**用哪套排序策略**。工程上常用规则 + 轻量分类模型。

## 四、召回：多路并行

召回的目标是**在保证相关性的前提下，尽可能不遗漏**。常见通路：

| 召回通路 | 实现 | 适用 |
| --- | --- | --- |
| 倒排召回 | ES/Lucene 倒排索引，BM25 打分 | 精确匹配、关键词 |
| 向量召回 | 双塔 embedding + ANN（HNSW） | 语义匹配、模糊意图 |
| 短语/精确召回 | `match_phrase`、`term` | 品牌/型号精确匹配 |
| 类目/标签召回 | 结构化过滤 | 意图明确的查询 |
| 个性化召回 | 用户历史行为 | 有画像的用户 |
| 规则召回 | 运营干预（置顶、屏蔽） | 兜底/干预 |

### 多路融合

```java
public List<Doc> recall(QueryQuery q) {
    List<CompletableFuture<List<Doc>>> fs = List.of(
        async(() -> invertedRecall(q), executor),
        async(() -> vectorRecall(q), executor),
        async(() -> categoryRecall(q), executor)
    );
    return fs.stream()
            .map(CompletableFuture::join)
            .flatMap(List::stream)
            // 加权融合：同一 doc 来自多路则分数累加
            .collect(Collectors.toMap(Doc::getId, d -> d,
                     (a, b) -> a.mergeScore(b)))
            .values().stream()
            .sorted(Comparator.comparingDouble(Doc::getScore).reversed())
            .limit(500)
            .collect(Collectors.toList());
}
```

**要点**：

- **每路独立超时与降级**，单路失败不影响整体；
- **融合策略**：分数归一化后加权（RRF 倒数排名融合也很常用）；
- **去重**：同一文档多路命中要合并分数而非重复。

### 相关性：BM25 与向量检索的取舍

| 维度 | BM25（倒排） | 向量检索 |
| --- | --- | --- |
| 匹配方式 | 词面匹配 | 语义匹配 |
| 可解释性 | 高 | 低 |
| 精确匹配 | 强（型号、品牌） | 弱 |
| 同义/语义 | 弱（需同义词） | 强 |
| 性能 | 极高 | 依赖 ANN 索引 |
| 冷启动 | 无需训练 | 需训练 embedding |

**实践结论**：**两者融合**（hybrid search）。精确类查询（品牌型号）以倒排为主，模糊语义查询以向量为主，用加权或 LTR 统一融合。

## 五、排序：从 BM25 到学习排序（LTR）

### 打分演进

```text
第一代：TF-IDF / BM25（纯文本相关性）
第二代：BM25 + 业务特征（销量、评分、时效）线性加权
第三代：LTR（Learning to Rank）机器学习排序
第四代：个性化 + 多目标（相关性 × 转化 × 体验）
```

### BM25 公式直觉

```text
score(q, d) = Σ IDF(term) × [ tf × (k1+1) ] / [ tf + k1 × (1 - b + b × |d|/avgdl) ]
```

- `IDF`：词越稀有，权重越大；
- `tf`：词频，但**有饱和**（出现 100 次不会比 10 次重要 10 倍）；
- `b`：文档长度归一化强度。

### LTR 三要素

| 要素 | 说明 |
| --- | --- |
| 特征 | 文本相关性、query-doc 匹配、doc 质量（销量/评分/时效）、用户特征、上下文 |
| 标签 | 点击、转化、停留时长，或人工相关性标注（0-3 分） |
| 模型 | Pointwise / Pairwise（RankNet）/ Listwise（LambdaMART、LambdaRank） |

**LambdaMART** 是最经典的 LTR 算法，直接优化 NDCG；工程上用 LightGBM 就能训练。

### 相关性评估指标

| 指标 | 含义 |
| --- | --- |
| **NDCG@K** | 归一化折损累计增益，考虑位置权重，最常用 |
| **MAP** | 平均精度均值 |
| **MRR** | 第一个相关结果排名的倒数 |
| **P@K / R@K** | Top-K 准确率/召回率 |
| **零结果率** | 无结果查询占比（体验核心指标） |
| **点击率/转化率** | 线上真实效果 |

**离线 + 在线双评估**：离线指标提升不代表线上提升（离线偏差），必须 AB 实验验证。

### 个性化

在相关性基础上叠加个性化：

```text
final_score = relevance_score
            + w1 * user_preference(doc)
            + w2 * personalization_boost
```

工程要点：

- **不能过度个性化**：个性化权重过大会导致「搜索结果和用户已有认知不符」，反而伤害体验；
- **探索与利用**：新用户无画像时用全局热门 + 快速试探；
- **多样性**：同一品牌/类目不要占满首页（打散）。

## 六、性能与工程化

### 缓存体系

搜索是典型的「读多写少、查询重复率高」场景，缓存收益极高。

| 层级 | 内容 | 命中率 |
| --- | --- | --- |
| CDN/接入层 | 静态资源 | — |
| 网关/本地缓存 | 热门 query 结果 | 中高 |
| 分布式缓存（Redis） | query → docId 列表 | 高 |
| 结果缓存 | 完整结果（含排序） | 高 |
| 索引缓存 | OS Page Cache / ES 文件缓存 | 极高 |

**多级缓存关键点**：**缓存 docId 而不是完整文档**——用 id 回表能保证文档内容更新后立即可见，避免「搜索列表是新的、点进去是旧的」。参考 `caffeine-multi-level-cache-practice`。

### 分片与扩容

- **索引分片数在创建时确定，不能改**（只能重建），所以**分片数要留足余量**（参考 `elasticsearch-shard-strategy-scaling`）；
- **副本数**决定读吞吐与容灾；
- **冷热分离**：热点索引放 SSD 节点，历史数据放冷节点（ILM 生命周期管理）；
- **读写分离**：大批量写入走独立节点，避免影响查询。

### 大促治理

```text
1. 容量评估：按峰值 QPS × 冗余系数准备机器
2. 预热：提前把热门 query 跑一遍，warming 缓存
3. 限流：网关层按用户/接口维度限流
4. 降级：关掉向量召回、个性化、LTR 精排，退化为纯 BM25
5. 兜底：返回运营配置的固定内容
```

**降级必须提前演练**，不能等到大促当天才第一次按下开关。

### 可观测性

| 类型 | 指标 |
| --- | --- |
| 系统 | QPS、P99、错误率、各阶段耗时、ES 慢查询 |
| 业务 | 零结果率、点击率、转化率、Top1 点击率 |
| 质量 | NDCG 抽样、相关性人工抽检 |
| 数据 | 索引文档数、同步延迟、同步失败数 |

**搜索日志是宝库**：零结果查询、低点击查询、高频查询都是优化相关性和挖掘需求的输入。

## 七、面试常见追问

**Q1：ES 和搜索引擎的关系？**

ES 是**检索引擎**，提供倒排索引和基础打分。完整的搜索系统还需要**查询理解、多路召回、LTR 排序、个性化、缓存、降级**——这些 ES 不负责，需要你在上层自研。

**Q2：怎么保证数据一致性？**

Binlog 增量同步 + 全量重建兜底 + 版本号条件更新（丢弃乱序旧消息）+ 定时对账。写入后延迟（NRT）通常 1 秒内可接受。

**Q3：重建索引怎么不停机？**

别名（Alias）+ 双写 + 数据校验 + 原子切换。读永远走别名，索引名不写死。

**Q4：相关性怎么优化？**

三步：① 查询理解（分词/同义词/纠错）提升召回；② 引入业务特征做线性加权；③ 升级到 LTR（LambdaMART），用日志和人工标注训练，NDCG 评估，AB 验证。

**Q5：搜不到结果怎么办？**

兜底策略：同义词扩展 → 分词粒度调整（细粒度/字粒度）→ 向量召回 → 类目推荐 → 热门推荐 → 「猜你想搜」。目标是把「零结果率」压到极致。

**Q6：搜索和推荐的区别？**

搜索是**主动的、query 驱动的**，核心是「相关性」（准确满足意图）；推荐是**被动的、无 query 的**，核心是「兴趣匹配」。搜索相关性错了用户会立刻流失，所以对精确性要求更高。

## 八、总结

搜索系统的五层结构：

```text
查询理解 ─► 召回 ─► 粗排 ─► 精排(LTR) ─► 重排 ─► 返回
   │          │        │         │         │
分词/纠错   倒排+向量  轻量模型  LambdaMART 去重/打散
同义/意图   多路融合   特征工程  个性化     业务规则
   │                                                   ▲
   └───────────── 索引构建：全量 + Binlog 增量 ──────────┘
                  （别名切换实现不停机重建）
```

作为 Java 后端工程师，设计搜索系统时你要抓住四个工程关键点：

1. **索引一致性**：全量 + 增量 + 对账，别名切换实现零停机重建；
2. **查询理解**：分词器统一、同义词与纠错宁可少不可错；
3. **多路召回 + LTR**：混合检索，离线 NDCG + 在线 AB 双评估；
4. **缓存与降级**：缓存 docId 而非文档，大促前预热 + 演练降级。

「会用 ES」是入门，「能设计一个相关性可控、数据一致、能扛大促的搜索平台」才是面试官真正想听的答案。

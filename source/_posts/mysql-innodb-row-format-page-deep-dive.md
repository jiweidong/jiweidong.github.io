# 【MySQL 底层】InnoDB 行格式与数据页结构深度解析：从 Compact/Dynamic 到页存储物理布局

## 面试官：知道一条 INSERT 语句在磁盘上是怎么存的吗？

很多人背了 B+ 树、背了聚簇索引，但问到「一行记录在磁盘上的物理结构长什么样」就卡壳了。今天我们从 InnoDB 的**行格式（Row Format）**和**数据页（Page）**两个层面，把「一行数据 + 一页数据」彻底讲透。这才是理解索引、碎片、大字段存储的基础。

---

## 一、行格式的演进：Redundant → Compact → Dynamic

InnoDB 历史上主要有四种行格式：

| 行格式 | 出现版本 | 特点 | 适用场景 |
|--------|---------|------|---------|
| Redundant | MySQL 5.0 之前 | 老格式，字段偏移量用 2 字节存，存储冗余大 | 基本淘汰 |
| Compact | MySQL 5.0 | 紧凑行格式，变长字段长度列表 + NULL 位图 | 5.6 前默认 |
| Dynamic | MySQL 5.7 默认 | Compact 的改进版，**大字段（TEXT/BLOB）全部溢出存储**，行内只留 20 字节指针 | 当前主流默认 |
| Compressed | 与 Dynamic 同代 | 在 Dynamic 基础上支持页级压缩（透明压缩） | 数据压缩需求 |

**MySQL 8.0 中默认行格式就是 Dynamic**。可以用下面的 SQL 查看和设置：

```sql
-- 查看当前默认行格式
SHOW VARIABLES LIKE 'innodb_default_row_format';  -- dynamic

-- 查看表的行格式
SHOW TABLE STATUS LIKE 'orders'\G

-- 建表时显式指定
CREATE TABLE t (
  id INT PRIMARY KEY,
  content TEXT
) ROW_FORMAT=DYNAMIC;
```

> 面试开场白：Compact 是理解一切行格式的基石，Dynamic 只是把「大字段溢出策略」改了，行内骨架和 Compact 完全一致。所以下面先啃 Compact。

## 二、Compact 行格式：一行记录的内存布局

一条 Compact 格式的记录在页内按以下顺序排列：

```
┌─────────────────────────────────────────────────────────┐
│ 变长字段长度列表 (逆序存放)  │  NULL 标志位(1字节)  │  记录头信息(5字节)  │
├─────────────────────────────────────────────────────────┤
│ RowID (6字节, 可选) │ 事务ID (6字节) │ 回滚指针 (7字节) │ 各列数据... │
└─────────────────────────────────────────────────────────┘
```

### 2.1 变长字段长度列表（逆序！）

对于 `VARCHAR`、`VARBINARY`、`TEXT`、`BLOB` 等变长字段，InnoDB 需要记录其实际字节长度，列表**按照字段逆序存放**（为了配合记录头里 next_record 的「向前偏移」设计，CPU 顺序读取更友好）。

长度存储规则（面试常考）：

- 列内容 ≤ 255 字节：用 **1 字节**存长度。
- 列内容 > 255 字节：用 **2 字节**存长度（前提是列定义最大长度 > 255，如 VARCHAR(300)）。
- **NULL 值的变长字段不占长度列表空间**。

### 2.2 NULL 标志位

一个字节（8 个 bit）最多标记 8 个可空字段，每个 bit 对应一个可空列，**同样逆序排列**，值为 1 表示该列为 NULL。可空列超过 8 个就用 2 字节。注意：**主键列和 NOT NULL 列不参与 NULL 位图**。

NULL 列本身不占用存储空间（除了位图里那 1 bit），这也是为什么「能 NOT NULL 就 NOT NULL」能省空间的底层原因。

### 2.3 记录头信息（5 字节 = 40 bit）

| 名称 | 大小(bit) | 含义 |
|------|----------|------|
| delete_mask | 1 | 记录是否被删除（**标记删除**，不是物理删除） |
| min_rec_mask | 1 | B+ 树每层非叶子节点的最小记录会置 1 |
| n_owned | 4 | 槽内拥有的记录数（配合 Page Directory） |
| heap_no | 13 | 记录在页堆中的位置号（0=Infimum，1=Supremum） |
| record_type | 3 | 0=普通记录 1=非叶子节点最小记录 2=Infimum 3=Supremum |
| next_record | 16 | **下一条记录的相对偏移量**（可为负） |

关键点：页内记录通过 `next_record` 组成**单向链表**，且**物理上无序、逻辑上有序**（按主键从小到大串起来）。

### 2.4 隐藏列

除了用户定义的列，InnoDB 还会附加三个隐藏列（按需存在）：

- `DB_ROW_ID`（6 字节）：**表没有主键且没有非空唯一键时**才会生成，作为聚簇索引的隐含主键。所以「强烈建议显式主键」——否则 InnoDB 悄悄帮你加 6 字节，还可能导致隐藏列顺序问题。
- `DB_TRX_ID`（6 字节）：最近一次修改该记录的事务 ID——**MVCC 判断版本链的基石**。
- `DB_ROLL_PTR`（7 字节）：回滚指针，指向 undo log 中该记录的上一版本，形成**版本链**，供 MVCC 快照读回溯。

## 三、大字段溢出：Compact 与 Dynamic 的分水岭

一个 16KB 的数据页不可能装下几 MB 的 TEXT。InnoDB 规定：**一条记录的最大长度不能超过页大小的一半（约 8KB）**，否则触发「行溢出（Row Overflow）」。

- **Compact 行格式**：溢出时，页内只保留该字段的**前 768 字节**（前缀），后面接一个 20 字节的指针指向溢出页，剩余数据存放在「溢出页」中。
- **Dynamic 行格式**：溢出时，页内**完全不留数据**，只存 20 字节指针指向溢出页，整列数据都在溢出页。所以 Dynamic 的页利用率更高——表里哪怕只查普通小字段，也不用把大字段前缀读进 buffer pool。

> 面试题：为什么行最大长度约是 65535 字节（VARCHAR 的上限）？因为 MySQL 层用 2 字节表示字段长度（最大 65535），而 InnoDB 层面一条记录实际能放多少，还受「页大小/2 - 记录头 - 隐藏列」约束，超过就走溢出。VARCHAR(N) 的 N 是**字符数**，实际占用还要乘以字符集最大字节数（utf8mb4 是 4），所以 `VARCHAR(16383)` 在 utf8mb4 下已经逼近 65535 字节上限，再大就只能用 TEXT。

## 四、数据页（Page）结构：16KB 的微观世界

页是 InnoDB 磁盘与内存交换的最小单位，默认 16KB。一个聚簇索引的叶子页长这样：

```
┌─────────────────────────────────────┐
│ File Header       38 字节  (页头)      │  ← 页号、上一页/下一页指针、校验和、LSN
├─────────────────────────────────────┤
│ Page Header       56 字节            │  ← 页目录槽数、记录数、空闲空间起点等
├─────────────────────────────────────┤
│ Infimum + Supremum  (虚拟最大最小记录) │  ← 每个页固定的两条伪记录
├─────────────────────────────────────┤
│ User Records       (用户记录)         │  ← 按主键升序的单向链表
├─────────────────────────────────────┤
│ Free Space         (空闲空间)         │
├─────────────────────────────────────┤
│ Page Directory     (页目录)           │  ← 槽(slot)，每组约 4~8 条记录
├─────────────────────────────────────┤
│ File Trailer      8 字节  (页尾)      │  ← 校验和 + LSN，用于崩溃恢复时校验
└─────────────────────────────────────┘
```

### 4.1 File Header 与 File Trailer

File Header 里的 `FIL_PAGE_PREV` / `FIL_PAGE_NEXT` 把同一索引的页串成**双向链表**——这就是 B+ 树「叶子节点横向扫描」的物理基础，范围查询（`WHERE id BETWEEN a AND b`）顺着链表走即可。File Trailer 存校验和与 LSN，与 Header 配合做**页级崩溃恢复校验**（redo log 应用前先校验页是否完整，防止半页写问题）。

### 4.2 页内记录的组织：链表 + 页目录

1. 页内 User Records 物理上按插入顺序追加在空闲区，但通过 `next_record` 指针在**逻辑上按主键升序**串联。
2. 为了快速查找，InnoDB 把记录分组，每组约 4~8 条，**每组最后一条记录（组长）的地址放进 Page Directory 的槽（slot）**，组长记录的 `n_owned` 字段记录组内成员数。
3. 查找时先在页目录里**二分查找槽**定位到组，再在组内顺序扫描。这就是「页内查找 = 二分 + 线性」的真相。

### 4.3 Infimum 与 Supremum

每个页固定有两条虚拟记录：Infimum（页内最小记录，heap_no=0）和 Supremum（页内最大记录，heap_no=1），它们不占用用户空间，只作为链表的头尾哨兵，保证「任何记录插入都有前驱后继」，简化边界处理。

## 五、物理布局带来的三个实战结论

### 5.1 为什么主键要顺序插入？

页内记录按主键逻辑排序。如果主键是自增 ID，新记录总是追加在页尾（或新页），**页分裂极少发生**；如果主键是 UUID 等随机值，新记录大概率要插入到已有页的中间：

- 页满了 → **页分裂**：申请新页，把一半记录搬过去，更新 File Header 双向链表指针；
- 频繁分裂 → 产生大量**碎片页**和空洞，索引膨胀；
- 每次插入涉及页内记录的移动与 next_record 重排，写放大严重。

这就是「**自增主键 > UUID 主键**」的底层原因（之前也写过主键设计对比，这里是存储层机理）。

### 5.2 为什么 DELETE 不释放空间？

记录头 `delete_mask` 只是**标记删除**：记录仍占着页空间，只是从链表上摘除、加入页的空闲可复用链表。只有当页内空间不足且需要插入新记录时，才会真正复用这些「洞」。大量删除后表的物理文件并不缩小——这就是表碎片化（之前写过碎片化治理）的来源之一，也解释了 `OPTIMIZE TABLE` 为什么能回收空间（重建表 = 重新紧凑排布所有记录）。

### 5.3 为什么说「行格式影响性能」？

- Dynamic 下大字段全部溢出，普通查询的页能装更多行，**缓冲池命中率更高**；
- 扫描小字段时不会把溢出页读进内存，IO 更少；
- 反例：若把超长字段和主查询字段混在 Compact 行内（前缀 768B 留在行内），页密度下降，全表扫描变慢。

## 六、动手验证

```sql
-- 1. 确认表行格式与数据页大小
SHOW TABLE STATUS LIKE 't'\G
SHOW VARIABLES LIKE 'innodb_page_size';   -- 16384

-- 2. 查看是否发生行溢出（TEXT 列单独存于溢出页）
-- 通过 performance_schema 或直接看 information_schema.INNODB_TABLESPACES 的 FS_BLOCK_SIZE

-- 3. 观察页分裂：对随机主键表批量插入后，查看索引大小膨胀
SELECT
  table_name, index_name,
  stat_size_in_pages * 16 / 1024 AS size_mb
FROM mysql.innodb_index_stats
WHERE database_name = 'test' AND table_name = 't';
```

用 `innodb_page_size` 确认 16KB 后，可以反推：单行记录（不含溢出）能容纳的最大列组合 ≈ 16384 / 2 字节以内，超出即触发溢出，这就是为什么「一行不要塞太多大字段」是硬规范。

## 七、面试常见追问

**Q1：Compact 和 Dynamic 的区别就一个？**
核心区别是溢出字段的存储策略：Compact 留 768 字节前缀在行内 + 20 字节指针；Dynamic 只留 20 字节指针。其余行内结构一致。MySQL 5.7+ 默认 Dynamic。

**Q2：变长字段长度列表为什么要逆序存放？**
为了和记录头的 next_record「相对偏移、向前寻址」的设计配合：从记录头向后读时，可以顺序拿到最后面的字段长度，CPU 缓存友好。记住「长度列表逆序、NULL 位图逆序」这两个反直觉点即可。

**Q3：没有主键的表，InnoDB 会怎样？**
如果既没有主键也没有非空唯一键，InnoDB 会自动生成 6 字节的隐藏 RowID 作为聚簇索引键，且这个 RowID 是表级别的单调递增值（全局唯一），插入会集中在页尾。但隐藏主键不可控，建议始终显式定义主键。

**Q4：页内查找一条记录，时间复杂度是多少？**
页目录槽二分查找 O(log n) 定位组 + 组内（≤8 条）顺序扫描，近似 O(log n)。注意这是页**内部**；跨页走的是 B+ 树层级（通常 2~4 层），每层一次 IO。

## 总结

一行记录 = 变长长度列表（逆序）+ NULL 位图 + 记录头 + 隐藏列（RowID/事务ID/回滚指针）+ 数据列；一页数据 = 文件头 + 页头 + 哨兵记录 + 按主键逻辑有序的记录链表 + 页目录（槽）+ 文件尾。理解这两个结构，页分裂、碎片、大字段溢出、MVCC 版本链、标记删除这些「看似独立」的知识点就全部串起来了——面试官再往下追问任何存储层问题，你都能回到这张物理蓝图上来。

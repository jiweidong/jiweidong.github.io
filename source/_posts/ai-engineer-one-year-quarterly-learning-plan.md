# 【AI 转型】Java 后端转 AI 应用开发的一年

## 前言

市面上不缺「30 天速成」「60 天入门」的计划。真正的问题是：**速成之后呢？**

我见过太多 Java 后端的学习轨迹：花两周看完 Prompt 教程，跟着敲了一个 RAG Demo，买了本《大模型应用开发》，然后在第三个月卡住——Demo 能跑，但说不清为什么要重排、不知道 Token 成本怎么算、面试被问「你的 Agent 怎么评测」直接哑火。再往后，工作一忙，学习就断了。

转型不是短跑，是**一年的结构性投入**。这篇文章给出一份可执行的年度计划：四个季度，每季度一个明确的能力台阶、一个可交付的项目、一组可验证的验收标准。每周投入按 10 小时设计（工作日晚上 1 小时 + 周末半天），适合在职工程师。

先说结论：**一年后你应该能独立设计并上线一个多租户的 RAG + Agent 应用，能说清每个技术选型的取舍，并有可展示的作品和可复述的踩坑。**

---

## 一、先定义终点：目标岗位到底要什么

把招聘 JD 拆开，AI 应用开发工程师（非算法岗）的高频要求集中在五块：

| 能力块 | 具体表现 | 权重 |
|---|---|---|
| LLM 应用开发 | Prompt、结构化输出、流式、Function Calling | ★★★★★ |
| RAG 体系 | 切分、Embedding、向量库、混合检索、重排、评测 | ★★★★★ |
| Agent 工程 | 工具调用、工作流、记忆、多轮状态、人工介入 | ★★★★☆ |
| 工程化 | 可观测、成本、限流、安全、灰度 | ★★★★☆ |
| 后端基本功 | Java/Spring、并发、数据库、分布式 | ★★★☆☆（你的优势） |

注意最后一行：**你的 Java 功底是资产，不是包袱**。企业级 AI 应用最缺的不是会调 API 的人，而是能把 AI 能力做成**稳定、可运维、可计费**的系统的后端工程师。

所以这份计划的设计原则是：**用 AI 补上新能力，用 Java 放大差异化**。

## 二、全年路线总览

| 季度 | 主题 | 核心产出 | 能力验收 |
|---|---|---|---|
| Q1 | 打通调用链 | 一个带流式输出与结构化结果的 Spring AI 服务 | 能独立解释一次 LLM 调用的全链路 |
| Q2 | RAG 做深 | 企业知识库问答（含评测与可观测） | 能定位并量化 RAG 的每个环节损耗 |
| Q3 | Agent 落地 | 带工具、记忆、审批的 Agent 应用 | 能设计可恢复、可审计的 Agent 流程 |
| Q4 | 平台化与影响力 | 多租户 AI 平台 + 技术输出 | 能讲清架构取舍，能通过 AI 岗面试 |

每季度 13 周，按 **8 周学习 + 3 周项目 + 2 周复盘输出** 分配。

## 三、Q1：打通调用链（第 1~13 周）

### 3.1 目标

从「会写 CRUD」变成「能解释一次 LLM 调用从请求到响应的每一跳」。

### 3.2 学习内容

| 周 | 主题 | 关键问题 |
|---|---|---|
| 1-2 | LLM 基础 | Token 是什么？上下文窗口、温度、top_p 如何影响输出？ |
| 3-4 | Prompt 工程 | 指令、示例、分隔符、输出格式约束；为什么要少而精 |
| 5-6 | Spring AI 入门 | ChatClient、Advisor、流式 SSE、结构化输出 |
| 7-8 | LangChain4j 对照 | 两套框架的抽象差异，什么时候选哪个 |
| 9-10 | 工程基础 | 超时、重试、限流、密钥管理、日志脱敏 |
| 11-13 | 项目一 | 带流式输出的「技术文档问答助手」 |

### 3.3 项目一：流式文档问答

最小可用版本：

```java
@RestController
public class ChatController {
    private final ChatClient chatClient;

    @GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> chat(@RequestParam String q) {
        return chatClient.prompt()
                .system("你是 Java 技术顾问，回答不超过 200 字")
                .user(q)
                .stream()
                .content();
    }
}
```

必须额外做到的（这才是和教程的区别）：

1. **首字节延迟（TTFT）打点**，并和总耗时分开统计；
2. **客户端断开时取消上游调用**，否则白烧 Token；
3. **按用户维度记录 Token 消耗**，能算出每次对话的成本；
4. **Prompt 版本化**，改 prompt 能回滚。

### 3.4 验收标准

- 能画出「浏览器 → Nginx → Spring Boot → LLM Provider」的完整时序图；
- 能解释 `Flux` 背压在这里为什么重要；
- 能用一句话说清「为什么流式不能用普通 `@RestController` 返回值」；
- 项目有 README、有架构图、有成本估算。

## 四、Q2：RAG 做深（第 14~26 周）

### 4.1 目标

RAG 是 AI 应用的主战场，也是最容易被低估的部分。会调 `VectorStore.similaritySearch()` 不算会 RAG，**能定位「答不准」到底出在切分、召回还是生成**才算。

### 4.2 学习内容

| 周 | 主题 | 关键问题 |
|---|---|---|
| 14-15 | 文档解析与切分 | 固定长度 vs 语义切分 vs 版面感知；chunk 大小怎么定 |
| 16-17 | Embedding | 维度、归一化、多语言、Matryoshka；如何选型 |
| 18-19 | 向量库 | pgvector / Milvus / Qdrant / ES 的取舍与 Java 客户端 |
| 20-21 | 混合检索与重排 | BM25 + 向量 + RRF；Cross-Encoder 的收益与延迟代价 |
| 22-23 | 评测 | 黄金集、召回率、忠实度、答案相关性；RAGAS 思路 |
| 24-26 | 项目二 | 企业知识库问答（带权限与引用） |

### 4.3 项目二：企业知识库问答

相比项目一，必须增加四件事：

1. **权限过滤**：不同部门只能检索自己的文档，过滤必须下推到向量库，而不是检索后再过滤（否则召回数量会崩）；
2. **引用溯源**：每个答案带原文片段和文档 ID，点得回去；
3. **评测集**：50~100 条「问题 + 标准答案 + 应命中文档」，每次改切分策略都跑一遍；
4. **可观测**：记录每次检索的 query、召回文档、重排分数、最终 prompt，能回放。

一个常见的评测表：

| 指标 | 定义 | 目标 |
|---|---|---|
| Recall@5 | 前 5 条是否包含正确文档 | > 85% |
| MRR | 正确文档的平均倒数排名 | > 0.7 |
| Faithfulness | 答案是否忠于原文 | > 0.9 |
| 拒答准确率 | 无答案时是否正确说「不知道」 | > 80% |

### 4.4 验收标准

- 能解释「为什么 chunk 太大召回准但生成差，太小则相反」；
- 能说清 RRF 的公式和它解决什么问题；
- 能拿出评测数据证明某次优化有效（而不是「感觉好多了」）；
- 能估算 10 万文档的向量存储成本与查询延迟。

## 五、Q3：Agent 落地（第 27~39 周）

### 5.1 目标

从「问答」升级到「办事」。Agent 的难点不在 ReAct 循环，而在**失败处理、状态管理和权限边界**。

### 5.2 学习内容

| 周 | 主题 | 关键问题 |
|---|---|---|
| 27-28 | Function Calling | 工具 schema 设计、参数校验、并行调用 |
| 29-30 | Agent 架构 | ReAct / Plan-Execute / Reflection 的适用场景 |
| 31-32 | MCP | 协议模型、Server 实现、工具发现与权限 |
| 33-34 | 记忆与状态 | 短期/长期记忆、检查点、断点续跑 |
| 35-36 | 工作流与 HITL | DAG 编排、人工审批、超时恢复 |
| 37-39 | 项目三 | 运维排障 Agent（只读诊断 + 写操作审批） |

### 5.3 项目三：运维排障 Agent

场景：输入一个告警，Agent 自主查询指标、日志、变更记录，给出根因假设和处置建议；涉及重启/扩容等写操作时必须人工审批。

关键设计：

- **工具分级**：只读工具直接执行，写工具走审批流；
- **步数预算**：最多 8 步，超出强制收敛并输出「未定位」；
- **幂等**：每个工具调用带幂等键，重试不产生副作用；
- **可回放**：完整记录每步的输入输出，能复现决策过程；
- **评测**：用 20 个历史故障做黄金集，看「根因是否命中」「步数是否超标」。

### 5.4 验收标准

- 能说清 ReAct 和 Plan-Execute 在什么场景下会选错；
- 能设计一个「工具调用失败后不会失控」的重试策略；
- 能解释 MCP 相比自定义 HTTP 工具的优势与代价；
- 项目能演示「审批中断 → 恢复执行」的完整流程。

## 六、Q4：平台化与影响力（第 40~52 周）

### 6.1 目标

从「能做一个应用」到「能支撑多个团队」。这一季的关键词是**多租户、成本、治理、表达**。

### 6.2 学习内容

| 周 | 主题 | 关键问题 |
|---|---|---|
| 40-41 | LLM 网关 | 多模型路由、降级、配额、密钥托管 |
| 42-43 | 成本治理 | Token 账本、缓存、模型分级、预算告警 |
| 44-45 | 安全 | Prompt 注入、输出护栏、工具沙箱、数据脱敏 |
| 46-47 | 可观测 | Trace、GenAI 语义约定、评测回归 |
| 48-49 | 系统设计 | 多租户隔离、限流、灰度、容量规划 |
| 50-52 | 输出与面试 | 博客/分享、简历重构、模拟面试 |

### 6.3 项目四：多租户 AI 平台

把前三个项目的能力收拢成一个平台：

```
接入层：API Key / OAuth，按租户限流
路由层：模型路由（成本/质量/可用性）
能力层：Chat / RAG / Agent 三类服务
治理层：配额、审计、评测、告警
数据层：向量库、会话存储、Token 账本
```

### 6.4 验收标准

- 能画出多租户隔离的三个层次（数据、配额、工具权限）；
- 能算清「1000 日活用户、人均 20 轮对话」的月度成本；
- 能设计一套「模型降价/涨价时的路由切换」方案；
- 有一篇能讲 30 分钟的技术分享，或 5 篇成体系的博客。

## 七、每周 10 小时怎么分配

| 时段 | 时长 | 内容 |
|---|---|---|
| 工作日晚上 ×3 | 3h | 看文档/源码，写最小验证代码 |
| 周六上午 | 4h | 项目推进（唯一的大块时间） |
| 周日晚上 | 2h | 写笔记/博客，复盘本周 |
| 碎片时间 | 1h | 读论文摘要、看社区讨论 |

三条纪律：

1. **每学一个概念，必须写一段可运行的代码验证**。看十篇文章不如跑通一次。
2. **每周必须有一次输出**（笔记、博客、分享），输出倒逼理解。
3. **项目优先于课程**。课程可以停，项目不能停——项目是面试唯一能聊 40 分钟的东西。

## 八、项目阶梯：四个项目如何逐级复用

| 季度 | 项目 | 复用关系 | 简历价值 |
|---|---|---|---|
| Q1 | 流式文档问答 | 基础调用链 | 证明你会调模型 |
| Q2 | 企业知识库 | 复用 Q1 的流式与成本模块 | 证明你懂 RAG |
| Q3 | 运维排障 Agent | 复用 Q2 的检索做工具检索 | 证明你会做 Agent |
| Q4 | 多租户平台 | 收拢前三者 | 证明你能做架构 |

不要每个季度换一个新想法。**同一个系统持续演进**，你才能在面试里讲出「第一版为什么不行、第二版改了什么、数据怎么变的」——这才是高级工程师的叙事。

## 九、常见失败模式

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 教程收集癖 | 收藏 50 个课程，一个没做完 | 只跟一条主线，其余全部屏蔽 |
| Demo 即终点 | 能跑通但说不清原理 | 每个组件写「为什么不用另一个」 |
| 只学不做 | 理论一套套，没作品 | 项目时间不得低于 40% |
| 追新不追深 | 每月换框架 | 一年内主框架不变，只换实现细节 |
| 不做评测 | 「感觉效果不错」 | 任何优化必须有数字前后对比 |
| 闭门造车 | 不知道业界怎么做 | 每月读 2 篇工程博客，参加 1 次分享 |

## 十、一年后你应该能回答的问题

如果这份计划执行到位，下面这些问题你不需要准备就能答：

1. 你的 RAG 系统 Recall@5 是多少？怎么测的？瓶颈在切分还是重排？
2. 一次对话的成本是多少？Token 都花在哪？怎么降 50%？
3. Agent 调错工具怎么办？你怎么防止它死循环？
4. 多租户下怎么保证 A 公司检索不到 B 公司的文档？
5. 模型供应商挂了，你的系统怎么降级？
6. 你为什么选 pgvector 而不是 Milvus？
7. 你的 Prompt 改了怎么保证不退步？

能答出来，简历上写「熟悉 RAG/Agent」才不是空话。

## 十一、总结

1. 转型是**结构性投入**，不是速成。按季度设台阶，比按天打卡更可持续。
2. Q1 打通链路、Q2 做深 RAG、Q3 落地 Agent、Q4 平台化，每一季都有可交付物。
3. **Java 功底是差异化优势**：企业要的是能把 AI 做成生产系统的人。
4. 一个持续演进的系统，胜过四个互不相干的 Demo。
5. 评测和输出是两条主线：没有数字的优化是玄学，没有输出的学习是幻觉。

一年很长，但每周 10 小时，52 周就是 520 小时。足够把一个后端工程师，变成能独立设计 AI 应用的人。

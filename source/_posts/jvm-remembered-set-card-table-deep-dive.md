# 【JVM 底层】记忆集与卡表深度解析：跨代引用追踪与 GC 的底层机制

## 面试官：老年代对象引用新生代对象，Minor GC 是怎么找到它的？

这几乎是 JVM 面试中最容易被问倒的问题之一。大多数人知道分代收集，知道 Minor GC 只扫新生代，但很少有人能说清楚：**当老年代对象引用了新生代对象时，Minor GC 凭什么不漏掉这个"活"对象？**

答案就是今天的主角：**记忆集（Remembered Set）与卡表（Card Table）**。这是 G1、CMS 等几乎所有分代收集器的地基，也是理解写屏障、G1 RSet 的必经之路。

## 一、问题起源：分代收集的"跨代引用"难题

### 1.1 分代收集的前提

JVM 堆被划分为新生代（Eden + Survivor）和老年代，新生代对象朝生夕灭，于是有了 **Minor GC（只回收新生代）**。但这里藏着一个致命问题：

> Minor GC 要判断新生代对象是否存活，就必须知道"有没有别的对象引用它"。如果只扫描新生代内部，那么**被老年代对象引用的新生代对象**会被误判为垃圾——这会导致活对象被错误回收，程序直接崩溃。

### 1.2 最笨的解法：全堆扫描

最直接的做法是 Minor GC 时把整个老年代也扫一遍，看看哪些对象引用了新生代。但老年代动辄几个 GB，每次 Minor GC 都全量扫描老年代，停顿时间会暴涨，分代收集的意义就没了。

### 1.3 精确的解法：记忆集

更好的思路是：**只记录"老年代中哪些区域存在指向新生代的引用"**，GC 时只扫描这些区域即可。这个"记录跨代引用位置"的数据结构，就叫**记忆集（Remembered Set，简称 RSet）**。

用一句话概括记忆集的本质：

> 记忆集是一种抽象数据结构，用于记录"非收集区域"指向"收集区域"的指针信息，避免 GC 时全堆扫描。

## 二、卡表（Card Table）：记忆集最常见的实现

记忆集是抽象概念，实现方式有字长精度、对象精度、卡精度等。HotSpot 虚拟机采用的是**卡表（Card Table）**，它是"卡精度"的实现，也是面试的核心考点。

### 2.1 卡表的结构

卡表本身就是一个**字节数组**：

```java
CARD_TABLE [this address >> 9] = 0;  // 伪代码示意
```

- 把堆内存划分为一个个 **512 字节**的卡（Card）
- 每个卡对应卡表数组中的一个字节
- 该字节为 0 表示"卡是干净的"（dirty=0，无跨代引用）
- 该字节为 1 表示"卡是脏的"（dirty=1，可能含跨代引用）

![卡表结构示意]
```
堆内存:  [卡0:0-511B] [卡1:512-1023B] [卡2:1024-1535B] ...
                |            |              |
卡表数组:  [0x00]         [0x01]         [0x00]
           (干净)         (脏,含跨代引用)  (干净)
```

为什么是 512 字节？因为对象引用地址通常 8 字节对齐，512 = 2^9，用 `地址 >> 9` 即可定位卡表下标，一次移位运算搞定，极快。

### 2.2 卡表如何被"弄脏"：写屏障（Write Barrier）

卡表本身不会自动更新。当发生**老年代对象引用新生代对象**的赋值操作时，必须把对应卡标记为脏。HotSpot 通过**写屏障（Write Barrier）**在赋值操作前后插入一段代码：

```java
// 伪代码：引用赋值 a.field = b;
void oop_field_store(oop* field, oop new_value) {
    // ① 执行真正的赋值
    *field = new_value;
    // ② 写屏障：如果新值在新生代，标记老年代对象所在卡为脏
    if (is_in_young(new_value)) {
        dirty_card(field);  // 卡表对应字节置 1
    }
}
```

> **注意**：这里的"写屏障"和并发编程里的"内存屏障"（Memory Barrier）是两个完全不同的概念，前者是 JVM 层面的引用赋值钩子，后者是 CPU 指令层面的顺序保证，面试时别搞混。

### 2.3 为什么只需要"老→新"方向的记录？

Minor GC 只回收新生代，需要防止"老年代引用新生代对象"导致误回收，所以只需要记录**老年代指向新生代**的引用。

反过来，**新生代指向老年代的引用**不需要记录——因为 Minor GC 时新生代对象本身就是被扫描的对象，从新生代出发能自然找到老年代引用；而 Major GC / Full GC 会扫描整个堆，也不需要跨代记录。

## 三、卡表的经典面试问题：伪共享与卡表变脏

### 3.1 伪共享（False Sharing）

卡表更新不是原子的。如果多个线程同时更新**同一个卡表字节**，就会产生竞争。HotSpot 的做法是：
- 先判断卡是否已脏，**已脏则直接跳过**（减少重复写）
- 未脏则用 CAS 或锁保护写入

但更隐蔽的问题是**伪共享**：多个线程更新**相邻**的卡表字节时，虽然字节不同，但它们落在同一条 64 字节的 CPU 缓存行上，导致缓存行反复失效（缓存一致性协议要求缓存行是同步单位），性能骤降。

### 3.2 解决方案

HotSpot 在卡表更新时做了优化：

```java
// 伪代码：卡表更新的经典优化
if (card_is_dirty(card)) {
    return;  // 已经脏了，无需重复标记
}
// 使用 CMOV（条件移动）等无锁技巧或加锁标记
```

同时引入 **-XX:+UseCondCardMark** 参数（默认开启），用条件判断避免不必要的卡表写操作，缓解伪共享。

**面试追问：卡表变脏后，什么时候被清理？**
答：下一次 Minor GC 时，GC 扫描脏卡找到跨代引用后，会把对应卡重新标记为干净（0）。所以"脏"表示"上次 GC 之后可能产生了新跨代引用"，是一个"可能"而非"必然"，GC 需要扫描脏卡区域内的对象来确认。

## 四、G1 的记忆集：比卡表更进一步

### 4.1 G1 为什么不用传统卡表

G1 把堆划分为一个个 **Region**（默认约 1MB~32MB），不再有物理上的代隔离，而是逻辑上的"新生代 Region 集合 / 老年代 Region 集合"。G1 的收集（Mixed GC）是**按 Region 集合**进行的，所以它需要知道：**哪些其他 Region 引用了我要回收的 Region 集合**。

这比传统卡表复杂得多——G1 的记忆集是一个 **Per-Region 的 RSet**，记录"谁引用了我"，是一个哈希结构：

```
Region N 的 RSet:
  Region A (地址区间) -> 卡表（哪些卡脏）
  Region B (地址区间) -> 卡表
  ...
```

### 4.2 G1 RSet 的写屏障

G1 的写屏障做了重要优化，**并不是所有跨 Region 引用都记录**：

- 如果引用的目标 Region 在本次收集集合（CSet）中，必须记录
- G1 通过 `-XX:+UseG1WriteBarrier` 控制，且引入了 **SATB（Snapshot At The Beginning）** 写屏障处理并发标记阶段的漏标问题

G1 的 RSet 还使用了**粗粒度/细粒度**分级存储（哈希表 → 位图 → 卡表数组），在空间与查询速度之间做平衡。

### 4.3 面试高频追问：为什么 G1 需要 RSet 而传统 CMS 只需要全局卡表？

因为 CMS 的收集是"整代收集"，只需要一张全局卡表记录老→新引用；而 G1 是 **Region 级局部收集**，每次收集的 Region 集合不同，必须精确知道"哪些 Region 引用了当前 CSet"，所以需要 Per-Region 的 RSet。

## 五、从卡表到写屏障：三个概念的关系梳理

| 概念 | 作用 | 类比 |
|------|------|------|
| 跨代引用 | 老年代对象引用新生代对象 | 问题本身 |
| 记忆集（RSet） | 记录跨代引用位置的抽象数据结构 | 索引/台账 |
| 卡表（Card Table） | 记忆集的一种具体实现（卡精度） | 台账的具体格式 |
| 写屏障（Write Barrier） | 在赋值时维护卡表/RSet 的钩子 | 记账员 |
| 伪共享 | 相邻卡表字节竞争同一缓存行 | 台账页被多人抢着改 |

**一句话串联全流程：**
> JVM 把堆按 512 字节切成卡，赋值时通过写屏障把"可能含跨代引用"的卡标脏；Minor GC 时只扫描脏卡区域，从老年代对象出发顺着引用找到新生代对象，标记为存活，然后清理卡表。G1 把这张表升级成了 Per-Region 的 RSet，支持任意 Region 集合的局部收集。

## 六、源码级验证：HotSpot 中的卡表实现

在 HotSpot 源码（`share/gc/shared/cardTableBarrierSet.hpp`）中，卡表的核心定义：

```cpp
class CardTableBarrierSet : public BarrierSet {
  // 卡表数组，每个元素对应 512 字节堆空间
  jbyte* _byte_map;
  // 卡表大小
  size_t _byte_map_size;
  // 脏卡标记值
  static const int dirty_card = 0;
  static const int clean_card = 1;
  ...
};
```

写屏障入口（`cardTableBarrierSet.cpp`）：

```cpp
void CardTableBarrierSet::write_ref_field(oop* field, oop new_val) {
  if (is_in_young(new_val)) {          // 新值在新生代
    jbyte* card = byte_for(field);      // 地址 >> 9 定位卡
    *card = dirty_card;                 // 标记脏
  }
}
```

可以看到实现和前面伪代码完全一致：**判断新值是否在新生代 → 定位卡 → 标记脏**。

## 七、常见面试追问与答案

**Q1：Minor GC 时如何确定老年代对象引用了新生代对象？**
A：不是每次现找，而是平时通过写屏障维护卡表。GC 时扫描脏卡区域内的对象，沿着引用找到新生代对象并标记。

**Q2：卡表脏了之后一定会有跨代引用吗？**
A：不一定。卡表只标记"可能"，因为标记后引用可能被清除，GC 时扫描确认即可。脏卡只是缩小扫描范围。

**Q3：为什么卡大小是 512 字节？**
A：引用 8 字节对齐，512 字节的卡包含 64 个引用槽位；卡表本身开销可控（4GB 堆 → 8MB 卡表），且用移位运算 `>>9` 定位下标，性能最优。

**Q4：G1 的 RSet 与 CMS 的卡表有什么区别？**
A：CMS 是一张全局卡表（老→新）；G1 是每个 Region 一张 RSet（其他 Region → 本 Region），粒度更细、支持局部收集，但内存占用和写屏障开销更大。

**Q5：什么是 SATB 写屏障？和卡表写屏障一样吗？**
A：不一样。卡表写屏障用于维护跨代引用记录；SATB（Snapshot At The Beginning）是 G1 并发标记阶段用的，记录"并发标记开始时"的快照，通过写屏障把"被覆盖的旧引用"加入队列，防止并发标记期间对象漏标。

## 八、实战启示：这些知识能帮你做什么

1. **理解 GC 日志中的耗时**：看到 Minor GC 时间较长时，可以推测是脏卡区域扫描过多，排查是否有大量老年代对象频繁引用新生代对象（比如缓存持有短生命周期对象）。
2. **JVM 参数调优**：`-XX:+UseCondCardMark`、G1 的 `-XX:G1HeapRegionSize`、`-XX:G1RSetRegionEntries` 等都和记忆集内存/性能直接相关。
3. **面试谈资**：能讲清楚"写屏障 → 卡表 → 脏卡扫描"这条链路，再延伸到 G1 的 RSet 和 SATB，说明你对 GC 的理解不是背概念，而是懂机制。

## 总结

记忆集与卡表是分代收集的"眼睛"：它用 512 字节的卡 + 写屏障维护一张跨代引用索引，让 Minor GC 不必全堆扫描。G1 将其升级为 Per-Region 的 RSet，支撑起 Region 级局部收集。理解这条链路，你就真正打通了"对象分配 → 跨代引用 → 写屏障 → GC 扫描"的完整闭环。

# 【系统设计】广告系统架构设计：广告检索、竞价排序、计费扣费与反作弊全解析

## 面试官：设计一个广告投放系统，你怎么做？

广告系统和推荐系统长得很像——都是「在海量候选里选出若干个展现」——但它有三个**本质不同**：

1. **广告是花钱的**：每一次曝光都要精确扣费，涉及**资金**，一致性要求极高；
2. **广告有约束**：预算、排期、定向、频控，任何一个约束都必须严格满足；
3. **广告是对抗的**：广告主有动机作弊（刷量），流量方有动机刷收入，必须有反作弊体系。

一句话总结广告系统的核心矛盾：

> **在 100ms 内，从百万级广告中选出「满足所有约束、平台收益最大、用户体验可接受」的几条广告，并且扣费一分不差。**

这篇文章按「检索 → 排序 → 计费 → 反作弊」四段主线，把广告系统的架构讲透。

## 一、广告系统的角色与核心概念

先厘清几个必考概念：

| 概念 | 含义 |
| --- | --- |
| **DSP** | 需求方平台，广告主/代理商投放广告的系统 |
| **SSP** | 供给方平台，媒体方管理广告位与流量的系统 |
| **ADX** | 广告交易平台，撮合买（DSP）卖（SSP） |
| **RTB** | 实时竞价，每次曝光实时出价 |
| **CPM / CPC / CPA / oCPX** | 千次曝光/点击/转化/目标转化出价 |
| **eCPM** | 千次曝光预估收入 = 出价 × 预估点击率 × 1000 |
| **预算控制** | 日预算/总预算，不能超投 |
| **定向** | 人群、地域、时间、设备、上下文等约束 |
| **频控** | 对同一用户展示同一广告的次数限制 |

**核心公式**（排序目标）：

```text
eCPM = pCTR × bid × 1000     （CPC 计价）
eCPM = pCTR × pCVR × bid × 1000   （oCPX/CPA 计价）
```

广告排序就是**按 eCPM 排序**（再叠加质量分、体验约束等）。

### 计费方式与出价转换

广告主按 CPC 出价，但系统内部统一用 eCPM 排序：

```text
CPC 出价 2 元，预估 CTR 3%
=> eCPM = 2 × 0.03 × 1000 = 60 元

CPM 出价 50 元
=> eCPM = 50 元
=> CPC 广告排前面
```

**GSP（广义第二价格）**：胜出者只需支付「第二名 eCPM + 最小加价」对应的价格，这是拍卖理论中最经典的机制，也是面试常考的点。

## 三、定向过滤：倒排索引是骨架

广告定向的核心是**「用户标签 → 命中的广告」**。主流实现是**倒排索引（Inverted Index）**：

```text
标签(维度值)          广告ID列表
─────────────────────────────────
gender=M               [1001, 1002, 2001, 3005]
city=杭州              [1001, 2003, 3005]
interest=母婴          [2001, 2002]
age=25-30              [1001, 1002, 2002]
```

一次请求的查询过程：

```text
1. 把用户标签展开成检索词：{gender=M, city=杭州, interest=母婴, age=25-30}
2. 各标签取广告列表求交集
3. 得到候选广告集合
```

**求交集优化**：

- 按列表长度**升序求交**（先求最短的两个列表），减少中间结果；
- 用 `RoaringBitmap` 做位图交集，千万级 ID 的交集能在毫秒级完成；
- 支持「或」与「非」条件（如 `city=杭州 OR city=上海`，`NOT 已屏蔽广告主`）。

```java
// RoaringBitmap 求交集（示意）
RoaringBitmap candidates = null;
for (RoaringBitmap tagBitmap : tagBitmaps) {
    if (candidates == null) {
        candidates = tagBitmap.clone();
    } else {
        candidates.and(tagBitmap);          // 位图交集，天然有序且高效
    }
}
```

### 倒排索引的规模与更新

- 索引条目数 = 广告数 × 平均标签数，百万广告可达**千万级条目**；
- 索引**全量加载到内存**（分片多实例），保证低延迟；
- 广告上下线、定向变更需要**近实时更新**：通过 Kafka 广播索引变更消息，各实例增量更新，并定期全量重建兜底。

## 四、约束过滤：预算与频控

### 预算控制（Budget Pacing）

预算控制是广告系统里**最容易出现资金事故**的地方。

问题：如果 100 台广告检索实例各自记账，必然超投（每台都不知道别人花多少）。

**架构方案**：

```text
广告检索实例                     预算中心（集中式）
   │                                  │
   │── 1. 请求预扣（余额检查+扣减）────►│  Redis + Lua 原子操作
   │◄─ 2. 返回预扣成功/失败 ───────────│
   │                                  │
   │── 3. 曝光后确认扣费 ─────────────►│  精确记账 + 异步落库
   │                                  │
   │── 4. 未曝光则退还 ───────────────►│  预扣回滚
```

**核心设计**：

1. **预扣（Reserve）**：请求时先预扣一笔（按预估价格），失败则过滤该广告；
2. **确认（Commit）**：真正曝光后确认扣费，金额以确认为准；
3. **回滚（Rollback）**：预扣但未曝光，必须退还，并有超时自动回滚兜底；
4. **原子性**：Redis + Lua 脚本保证「检查余额 + 扣减」原子执行。

```lua
-- 预算预扣 Lua 脚本（简化）
-- KEYS[1] = budget:adid:20261012
-- ARGV[1] = reserveAmount
local remain = tonumber(redis.call('GET', KEYS[1]) or '0')
local need = tonumber(ARGV[1])
if remain < need then
    return 0            -- 余额不足
end
redis.call('DECRBY', KEYS[1], need)
return 1                -- 预扣成功
```

**预算平滑（Pacing）**：不能让预算在早上 9 点就跑完。两种策略：

- **预算均分**：每小时预算 = 日预算 / 24，配合「低于进度则加速、高于进度则限流」；
- **概率通过**：`passRate = 剩余预算 / 预估剩余消耗`，用随机数决定是否参与竞价。

```java
// 概率预算平滑
double passRate = Math.min(1.0, budgetService.remaining(adId) /
                               budgetService.predictRemainingCost(adId));
if (ThreadLocalRandom.current().nextDouble() > passRate) {
    return null;   // 本次不参与竞价
}
```

### 频控（Frequency Capping）

「同一用户对同一广告最多看 3 次/天」。

```java
// Redis 计数器 + 过期时间
String key = "freq:" + userId + ":" + adId + ":" + LocalDate.now();
Long cnt = redis.opsForValue().increment(key);
if (cnt == 1) {
    redis.expire(key, Duration.ofDays(1));   // 首次设置 TTL
}
if (cnt > maxFreq) {
    return null;   // 超过频控，过滤
}
```

**工程坑**：

- **热 Key**：头部用户高频请求同一 Key，用本地缓存 + 批量更新缓解；
- **原子性**：`INCR` + `EXPIRE` 不是原子的（若 `INCR` 后实例挂掉，Key 永不过期），用 Lua 合并；
- **一致性 vs 精度**：严格频控很难做到绝对精确，通常允许极小误差（**强一致频控会严重伤害延迟**）。

## 五、排序与竞价

### 精排与出价

排序依据是 eCPM：

```text
score = pCTR × bid × qualityFactor
```

工程要点：

- **校准（Calibration）**：模型预估的 pCTR 必须与实际点击率对齐，否则出价失真。常用保序回归（Isotonic Regression）校准；
- **多目标融合**：`score = w1*pCTR*bid + w2*pCVR*bid`，权重按业务目标调整；
- **质量分**：低质广告降权（体验约束），防止广告主靠高价霸屏。

### GSP 定价

```text
胜出广告 A 的 CPC = (下一名 eCPM / A 的 pCTR) + 最小加价
```

```java
// GSP 定价示意
double nextEcpm = ranked.get(1).getEcpm();      // 第二名 eCPM
double pctr = winner.getPctr();
double cost = nextEcpm / (pctr * 1000.0) + MIN_BID_STEP;
```

### 竞价流程时序

```text
前端请求 ─► 广告检索 ─► 定向过滤 ─► 约束过滤 ─► 粗排
    │
    └─► 精排打分 ─► 竞价排序 ─► 预算预扣 ─► 返回胜出广告
                                        │
   曝光事件 ◄───────────────────────────┘
    │
    └─► 确认扣费 ─► 频控更新 ─► 埋点回流 Kafka
```

### 超时与降级

广告请求有严格延迟预算（通常 100ms 内）。超过预算必须**降级**：

| 级别 | 降级策略 |
| --- | --- |
| 1 | 跳过精排，用粗排分数直接排序 |
| 2 | 跳过模型，用静态 eCPM（历史均值）排序 |
| 3 | 只走快通路（高预算优质广告） |
| 4 | 返回兜底广告（自有推广位）或空（宁可不赚钱，不能影响用户体验） |

## 六、扣费与资金一致性

广告扣费涉及**真金白银**，一致性要求远高于推荐系统。

### 扣费时机

| 计费方式 | 扣费触发 |
| --- | --- |
| CPM | 曝光上报后 |
| CPC | 点击上报后（需点击有效性校验） |
| CPA/oCPX | 转化上报后（归因窗口内） |

### 资金链路

```text
曝光/点击上报 ─► 事件校验(去重/反作弊) ─► 计费 Kafka ─► 计费服务
                                                          │
                       ┌──────────────────────────────────┤
                       ▼                                  ▼
              实时账单（Redis/DB）                 流水落库（MySQL）
                       │                                  │
                       ▼                                  ▼
                  预算扣减确认                        对账系统（日级）
```

**关键设计**：

1. **事件去重**：上报可能重复（网络重试），必须有唯一事件 ID + 幂等消费（参考 `mq-duplicate-consumption-deep-dive`）；
2. **预扣 + 确认 + 回滚**三阶段，保证不超投、不少扣；
3. **异步落库 + 幂等**：计费流水用「业务唯一键」做唯一索引，`INSERT ... ON DUPLICATE KEY UPDATE` 保证幂等；
4. **对账**：广告主账单 vs 平台流水 vs 第三方监测（如秒针），三方对账兜底；
5. **最终一致性**：预扣走 Redis（快），最终账单走 MySQL（准），两者差异由定时任务补偿。

### 一个典型事故：预扣泄漏

如果「预扣成功但请求流程异常退出」，预扣的预算就永远被占住（预算被「泄漏」）。解决方案：

- 预扣记录带 **TTL**（Redis Key 自动过期）；
- 定时任务扫描「预扣未确认」的订单，超时自动回滚；
- **双写**：预扣记录同时写 Redis 和本地内存，重启后可恢复。

## 七、反作弊：广告系统的免疫系统

广告作弊的动机：

- **广告主侧**：竞争对手恶意点击（点击欺诈）、刷转化骗赔付；
- **流量方侧**：媒体刷曝光/刷点击骗广告费；
- **用户侧**：薅羊毛、机器人流量。

### 作弊识别维度

| 维度 | 特征 |
| --- | --- |
| 设备 | 设备指纹重复、模拟器、Root/越狱、ID 伪造 |
| 行为 | 点击间隔极短、无滑动、点击坐标集中、无停留 |
| 网络 | IP 聚集、代理/VPN、IP 段异常 |
| 时间 | 深夜集中、瞬时突增 |
| 关联 | 同设备多账号、团伙特征（图算法） |

### 架构

```text
广告事件 ─► 实时规则引擎（毫秒级）─► 拦截
              │
              └─► Kafka ─► Flink 实时特征 ─► 实时模型 ─► 动态拦截
                              │
                              └─► 离线数仓 ─► 离线模型（天级）─► 名单/模型更新
```

**多层防御**：

1. **实时规则**（毫秒级）：黑名单、频次阈值、设备指纹；
2. **实时模型**（秒级）：Flink 计算滑动窗口特征 + 在线模型打分；
3. **离线挖掘**（天级）：团伙识别（图算法）、异常聚集分析，产出黑名单；
4. **人工审核**：高风险广告主/媒体人工复核。

**工程要点**：

- **反作弊必须在计费之前**，否则先扣费后判定作弊，退款极其麻烦；
- **宁可放过、不可错杀**：误杀正常用户会损失收入，阈值要谨慎；
- **反作弊结果可申诉**，需要保存原始证据（点击日志、设备信息）。

## 八、数据与存储选型

| 用途 | 选型 | 说明 |
| --- | --- | --- |
| 倒排索引 | 自研内存索引 / RoaringBitmap + RocksDB | 低延迟、可增量 |
| 预算/频控 | Redis（Cluster）+ Lua | 原子、高性能 |
| 广告物料 | MySQL + 本地缓存 | 强一致、低频写 |
| 计费流水 | MySQL（分库分表） | 强一致、可审计 |
| 事件日志 | Kafka + HDFS/S3 | 高吞吐 |
| 实时特征 | Kafka + Flink + Redis/HBase | 秒级 |
| 报表 | ClickHouse / Doris | OLAP 聚合 |
| 账单对账 | MySQL + 离线数仓 | 日级批处理 |

**分库分表**：计费流水按天 + 广告主 ID 分片，历史数据归档到冷存储（参考 `large-table-hot-cold-data-archiving-deep-practice`）。

## 九、面试常见追问

**Q1：广告和推荐的区别？**

推荐优化「用户价值」（点击、时长），广告优化「平台收入 + 用户体验的平衡」。广告多了预算/计费/反作弊等**强一致**约束，而推荐是「有损可接受」的。

**Q2：怎么防止预算超投？**

集中式预算中心 + Redis Lua 原子预扣 + 确认/回滚三阶段 + 概率预算平滑 + 定时对账。

**Q3：CPC 广告怎么定价？**

用 eCPM 排序（`pCTR × CPC × 1000`），胜出价按 GSP（第二名 eCPM 折算的 CPC + 最小加价）。

**Q4：pCTR 预估不准会怎样？**

- 高估：广告主花了钱没点击，ROI 差，流失；
- 低估：广告竞价失败，平台收入下降。

所以需要**校准**，并用「实际消耗 / 预算」的动态反馈修正。

**Q5：频控怎么做到精准？**

很难绝对精准。通常用 Redis 计数器（允许少量误差），核心是**保证用户侧体验**而非「精确计数」。强一致频控的延迟代价不可接受。

**Q6：如何保证扣费一分不差？**

事件唯一 ID 去重 + 幂等消费 + 预扣/确认/回滚 + 三方对账。任何「异步 + 资金」的场景，对账都是最后一道防线。

## 十、总结

广告系统的四根支柱：

```text
┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
│  检索       │   │  排序竞价   │   │  计费扣费   │   │  反作弊     │
│ 倒排索引    │   │  eCPM/GSP  │   │ 预扣+确认   │   │ 规则+模型   │
│ Bitmap 交集 │   │ 预算平滑    │   │ 幂等+对账   │   │ 实时+离线   │
└────────────┘   └────────────┘   └────────────┘   └────────────┘
       └──────────── 100ms 延迟预算 + 分级降级 ────────────┘
```

和推荐系统相比，广告系统多了两件「必须较真」的事：

1. **钱**——预算不能超投、扣费不能错、账目要对得上；
2. **对抗**——反作弊是系统的一部分，不是可选项。

面试时，如果你能主动指出「预扣/确认/回滚三阶段」和「反作弊必须在计费之前」这两个点，基本就能证明你真的思考过资金型系统的设计，而不只是把推荐系统的架构换个壳。

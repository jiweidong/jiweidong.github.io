# 【面试必备】面试官：0.1 + 0.2 为什么不等于 0.3？浮点数 IEEE 754 深度解析

## 面试官：先来个热身，`0.1 + 0.2 == 0.3` 在 Java 里结果是什么？

```java
public class FloatDemo {
    public static void main(String[] args) {
        System.out.println(0.1 + 0.2);           // 0.30000000000000004
        System.out.println(0.1 + 0.2 == 0.3);     // false
        System.out.println(0.1f + 0.2f == 0.3f);  // false
        System.out.println(1.0 - 0.9);            // 0.09999999999999998
        System.out.println(0.1 * 3);              // 0.30000000000000004
    }
}
```

很多人第一次看到 `0.30000000000000004` 都会愣住：这不是计算机吗，怎么连小学算术都算不对？

**核心结论先抛出来：** 计算机底层用二进制表示一切数字，而十进制小数 `0.1`、`0.2` 在二进制世界里是**无限循环小数**，无法被精确表示。IEEE 754 标准规定了浮点数在内存中的存储格式，任何存储进内存的浮点数都只是真实值的**近似值**。两个近似值相加，误差自然被放大——这就是所有编程语言（Java、JavaScript、Python、C…）都躲不开的坑。

下面我们从二进制小数开始，一层层把它彻底讲透。

## 一、先搞懂：十进制小数怎么转二进制？

### 1.1 整数部分：除 2 取余

`13` 转二进制：不断除以 2 取余数，倒序排列：

```
13 / 2 = 6 余 1
 6 / 2 = 3 余 0
 3 / 2 = 1 余 1
 1 / 2 = 0 余 1
→ 1101
```

### 1.2 小数部分：乘 2 取整

`0.625` 转二进制：不断乘以 2，取出整数位，正序排列：

```
0.625 × 2 = 1.25 → 取 1，剩 0.25
0.25  × 2 = 0.5  → 取 0，剩 0.5
0.5   × 2 = 1.0  → 取 1，剩 0
→ 0.101
```

验证：`0.101₂ = 1×2⁻¹ + 0×2⁻² + 1×2⁻³ = 0.5 + 0 + 0.125 = 0.625` ✓

### 1.3 为什么 0.1 是无限循环小数？

用同样的方法算 `0.1`：

```
0.1 × 2 = 0.2 → 0
0.2 × 2 = 0.4 → 0
0.4 × 2 = 0.8 → 0
0.8 × 2 = 1.6 → 1
0.6 × 2 = 1.2 → 1
0.2 × 2 = 0.4 → 0   ← 注意：0.2 又回来了！
0.4 × 2 = 0.8 → 0
...
```

看到没？从 `0.2` 开始进入了**死循环**。所以 `0.1` 的二进制表示是：

```
0.0001100110011001100110011...（无限循环，循环节是 1100）
```

类比十进制里 `1/3 = 0.3333...` 永远写不完，二进制里 `0.1` 也永远写不完。**十进制下"干净"的小数，二进制下未必干净**——只有形如 `1/2ⁿ` 的分数（0.5、0.25、0.125、0.0625…）才能被二进制精确表示。

### 1.4 面试追问：那为什么 0.5、0.25 没问题？

因为 `0.5 = 2⁻¹`、`0.25 = 2⁻²`，它们的二进制展开是**有限的**：`0.5 → 0.1₂`，`0.25 → 0.01₂`。二进制能精确表示所有"分母是 2 的幂"的分数，而 `0.1 = 1/10` 的分母是 10（含因子 5），不是 2 的幂，所以必然循环。

## 二、IEEE 754：浮点数在内存里长什么样？

既然小数没法精确表示，计算机只能"截断存储"，这就需要一个**统一的存储标准**，否则不同机器、不同语言算出来的结果都不一样。1985 年 IEEE 发布了 754 标准，定义了浮点数的二进制格式，Java 的 `float`/`double` 完全遵循该标准。

### 2.1 科学计数法回顾

十进制科学计数法：`123.45 = 1.2345 × 10²`。二进制同理：

```
1.0101₂ × 2³ = 1010.1₂ = 10.5
```

IEEE 754 用**符号位 + 指数位 + 尾数位**三段来存一个数：

| 类型 | 总位数 | 符号位 S | 指数位 E（含偏移） | 尾数位 M（有效数字） | 精度 |
|------|--------|---------|------------------|--------------------|------|
| float | 32 | 1 | 8 | 23 | 约 7 位十进制 |
| double | 64 | 1 | 11 | 52 | 约 15~16 位十进制 |

以 `double` 的 `0.1` 为例，内存布局是：

```
S (1bit) | E (11bit 指数，偏移 1023) | M (52bit 尾数)
0        | 01111111011              | 1001100110011001100110011001100110011001100110011010
```

### 2.2 三个关键设计

**① 规格化与隐含位（leading 1）**

标准写法要求尾数首位必须是 `1`，即 `1.xxx × 2ᵉ`。既然第一位恒为 1，那就不存了！这 1 位是**隐含位**，白白多赚 1 位精度。例如 `0.1` 规格化后是：

```
0.1 = 1.1001100110011...₂ × 2⁻⁴
```

尾数只存小数点后面的 `1001100110011...`，52 位存不下就**舍入**——注意不是简单截断，而是"四舍六入五成双"（round to nearest even）。

**② 偏移指数（biased exponent）**

指数有正有负（`0.1` 的指数是 -4），为了不用符号位，标准把指数加上一个偏移量再存：`float` 偏移 127，`double` 偏移 1023。存的是 `e + bias`，取出时再减回去。这样指数域就可以直接用**无符号整数比较大小**，硬件实现更简单。

**③ 特殊值**

| 指数 E | 尾数 M | 含义 |
|--------|--------|------|
| 全 0 | 全 0 | ±0（正零负零） |
| 全 0 | 非 0 | 非规格化数（denormal，表示接近 0 的极小值） |
| 全 1 | 全 0 | ±Infinity（无穷大） |
| 全 1 | 非 0 | NaN（Not a Number） |

Java 里 `Double.POSITIVE_INFINITY`、`Double.NaN` 就是这么来的。**NaN 有个著名特性：`NaN != NaN` 恒为 true**，所以判断一个数是不是 NaN 要用 `Double.isNaN(x)`。

### 2.3 用代码看内存真相

Java 提供了 `Double.doubleToLongBits()` 可以把 double 的位模式直接抠出来：

```java
public static void main(String[] args) {
    double d = 0.1;
    long bits = Double.doubleToLongBits(d);
    // 符号位
    long sign = bits >>> 63;
    // 指数位：右移 52 位，取低 11 位
    long exp = (bits >>> 52) & 0x7FFL;
    // 尾数位
    long mant = bits & 0xFFFFFFFFFFFFFL;
    System.out.println("sign = " + sign);
    System.out.println("exp  = " + exp + " (实际指数 = " + (exp - 1023) + ")");
    System.out.println("mant = 0x" + Long.toHexString(mant));
    // 还原
    double back = (sign == 0 ? 1 : -1)
            * Math.pow(2, exp - 1023)
            * (1 + mant / Math.pow(2, 52));
    System.out.println("还原值 = " + new BigDecimal(back));
}
```

输出能看到 `0.1` 实际存储的值约等于：

```
0.1000000000000000055511151231257827021181583404541015625
```

没错，你写的 `0.1`，内存里存的是这个比 0.1 稍大一点点的数。这就是误差的源头。

## 三、为什么 0.1 + 0.2 = 0.30000000000000004？

现在可以精确解释了，分三步：

**第 1 步**：`0.1` 存为 ≈ `0.1000000000000000055511...`（略偏大）
**第 2 步**：`0.2` 存为 ≈ `0.2000000000000000111022...`（略偏大）
**第 3 步**：两个近似值相加，结果先按真实二进制精确算，再**舍入到 52 位尾数**。理想结果 `0.3` 本身存储值 ≈ `0.2999999999999999888977...`（略偏小），而两数相加后再舍入得到的值恰好落在 `0.30000000000000004` 上，与 `0.3` 的存储值不相等。

```java
System.out.println(0.1 + 0.2);   // 0.30000000000000004
System.out.println(0.3);          // 0.3（打印时做了最短表示优化）
```

> 补充：Java 的 `Double.toString()` 有个"最短表示"算法——它输出的不是存储值的完整小数，而是**能唯一区分这个 double 的最短十进制串**。所以 `0.3` 打印出来是 `0.3` 而不是那一长串，但 `0.1+0.2` 的结果和真正的 `0.3` 存储位不同，只能打印成 `0.30000000000000004`。

### 3.1 面试追问：float 的误差是不是更夸张？

```java
float f = 0.1f;
System.out.println(f);   // 0.1（最短表示）
// 但 float 0.1 实际存储为 0.100000001490116119384765625
```

float 尾数只有 23 位，相对误差约 `2⁻²⁴ ≈ 6×10⁻⁸`，即约 7 位有效十进制数字；double 尾数 52 位，相对误差约 `2⁻⁵³ ≈ 1.1×10⁻¹⁶`，约 15~16 位有效数字。**能用 double 就不要用 float**——尤其是金额、坐标这类对精度敏感的数据，float 的 7 位精度在乘以大数后误差会非常难看。

### 3.2 面试追问：误差会累积吗？

会，而且是**灾难性**的。经典反例：

```java
double sum = 0;
for (int i = 0; i < 10_000; i++) {
    sum += 0.1;
}
System.out.println(sum);  // 1000.0000000000016（而不是 1000）
```

每次加 0.1 都带一点舍入误差，1 万次累积后误差到了 `1.6×10⁻¹²`。循环次数越多、中间结果越大，相对误差越离谱。

## 四、金额计算怎么办？BigDecimal 也不是万能药

### 4.1 正确姿势

涉及金额、利息、汇率等**必须精确**的场景，用 `BigDecimal`，且**必须用字符串构造**：

```java
// ✅ 正确：字符串构造
BigDecimal a = new BigDecimal("0.1");
BigDecimal b = new BigDecimal("0.2");
System.out.println(a.add(b));  // 0.3 精确

// ❌ 错误：double 构造，等于把误差带进来
BigDecimal bad = new BigDecimal(0.1);
System.out.println(bad);       // 0.1000000000000000055511151231257827021181583404541015625
```

`new BigDecimal(0.1)` 是把 double 里存的"那个近似值"完整展开，误差原封不动。`BigDecimal.valueOf(0.1)` 内部其实也是先转字符串，等价于字符串构造。

### 4.2 BigDecimal 的坑

**① 除法要指定精度和舍入模式**，否则除不尽直接抛 `ArithmeticException`：

```java
// ❌ 抛异常
// new BigDecimal("1").divide(new BigDecimal("3"));
// ✅ 指定精度
BigDecimal result = new BigDecimal("1").divide(new BigDecimal("3"), 10, RoundingMode.HALF_UP);
```

**② 比较用 `compareTo` 而不是 `equals`**：`equals` 要求数值和 scale 都相等，`0.10` 与 `0.1` 用 `equals` 是 false，用 `compareTo` 才是 0。

**③ 数据库层面**：MySQL 金额字段用 `DECIMAL(18,2)` 而不是 `DOUBLE`；ORM 映射用 `BigDecimal` 而不是 `Double`。

**④ 性能**：BigDecimal 是对象运算，比 double 慢一个数量级。所以**不需要精确的场景（统计报表、评分、坐标）就用 double**，不要无脑 BigDecimal。

### 4.3 面试追问：那为什么不用 BigDecimal 做科学计算？

科学计算关心的是"相对误差可控"，double 的 `1.1×10⁻¹⁶` 相对精度对绝大多数物理、工程计算绰绰有余，而且硬件直接支持、快得多。BigDecimal 是十进制模拟，每个数都是对象，还容易在除法上抛异常——用错场景反而添乱。

## 五、面试追问环节：高频追问合集

### 5.1 追问一：怎么判断两个 double 相等？

**绝不能 `==`**。三种思路：

```java
// ① 绝对误差（不推荐：大数小数一视同仁，不合适）
Math.abs(a - b) < 1e-9

// ② 相对误差（推荐）
Math.abs(a - b) <= Math.max(Math.abs(a), Math.abs(b)) * 1e-9

// ③ 转 BigDecimal 精确比（金额场景）
new BigDecimal(Double.toString(a)).compareTo(new BigDecimal(Double.toString(b))) == 0
```

### 5.2 追问二：`Double.MAX_VALUE` 加 1 等于多少？

```java
double x = Double.MAX_VALUE;
System.out.println(x + 1 == x);  // true！
```

`Double.MAX_VALUE ≈ 1.8×10³⁰⁸`，尾数只有 52 位，这个量级下"1"根本落不进尾数的分辨率里，加了等于没加。同理：

```java
System.out.println(1e16 + 1 == 1e16);  // true，1e16 已经超过 double 的整数精确上限 2^53
```

**double 能精确表示的整数范围只有 `±2⁵³`（约 9×10¹⁵）**，超过这个范围的大整数（比如超过 2^53 的 id、时间戳毫秒运算）也会丢精度！这就是为什么 Snowflake ID 之类的 64 位整数在 JS 里会出问题，在 Java 里做 long 没问题，但**一旦转成 double 就可能悄悄变值**。

### 5.3 追问三：为什么 `Integer.MAX_VALUE + 1` 溢出没人管，浮点数却不报错？

整数溢出是"环绕"（wrap around），浮点溢出是"变无穷"：

```java
System.out.println(Integer.MAX_VALUE + 1);  // -2147483648（环绕）
System.out.println(Double.MAX_VALUE * 2);   // Infinity
System.out.println(1.0 / 0.0);              // Infinity
System.out.println(0.0 / 0.0);              // NaN
```

所以浮点运算**永远不抛异常**（Java 里浮点不检查溢出），结果变成 `Infinity`/`NaN` 后继续传染：`NaN` 参与的任何运算结果都是 `NaN`。线上代码如果出现大面积 NaN，很可能是某个分母算成了 0.0。

### 5.4 追问四：怎么才能让浮点运算是确定性的？

IEEE 754 本身就是确定性标准：**同样的输入、同样的运算顺序，在任何平台结果完全一致**（前提是不开 JVM 的 `-XX:+UseFastMath` 这类"快速但改变语义"的优化）。真正的问题是**运算顺序**——`(a+b)+c` 和 `a+(b+c)` 结果可能不同，这就是 Kahan 求和算法存在的原因：

```java
// Kahan 补偿求和：把每次舍入的误差存下来，下次加回去
static double kahanSum(double[] nums) {
    double sum = 0.0;
    double c = 0.0; // 补偿项
    for (double num : nums) {
        double y = num - c;
        double t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    return sum;
}
```

一万个 0.1 相加，朴素累加误差 `1.6e-12`，Kahan 求和能把误差压到 `~1e-16` 量级。

## 六、避坑清单（直接背）

| 场景 | 正确做法 |
|------|---------|
| 金额计算 | BigDecimal + 字符串构造 + 指定舍入模式 |
| 判断相等 | 相对误差比较 或 BigDecimal.compareTo |
| 存储金额到 DB | MySQL DECIMAL，不存 DOUBLE |
| 大整数超过 2^53 | 用 long/BigInteger，不要转 double |
| 除不尽 | BigDecimal.divide 必须给 scale + RoundingMode |
| NaN 判断 | Double.isNaN(x)，别用 x != x 之外的花活（其实 x != x 也行，但不直观） |
| 前端展示 | 后端统一格式化，别让前端拿原始 double 直接渲染 |
| JSON 传输 | 金额用字符串传输（BigDecimal.toString），防止 JS 精度丢失 |

## 七、总结：一张图记住核心

```
十进制小数 0.1
   ↓ 十进制转二进制：无限循环小数 0.0001100110011...
   ↓ IEEE 754 存储：S + 偏移指数 + 52位尾数（舍入截断）
   ↓ 得到近似值 0.1000000000000000055...
   ↓ 参与运算：近似值相加 → 结果再舍入 → 误差放大
   ↓ 输出 0.30000000000000004
```

**一句话回答面试官：** 0.1 和 0.2 在二进制下是无限循环小数，IEEE 754 浮点格式只能用有限位数存储它们的近似值，近似值相加后再舍入，结果与 0.3 的近似值不一致，所以 `0.1 + 0.2 != 0.3`。这不是 Java 的 bug，而是所有遵循 IEEE 754 的语言（包括 JavaScript 的 Number）共有的特性。工程上，精确场景用 BigDecimal，比较用误差阈值或 compareTo，存储用 DECIMAL——知道"为什么不准"，才能知道"什么时候该用什么"。

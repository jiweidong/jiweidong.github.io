# 【系统设计】直播弹幕系统架构设计：海量消息分发、房间分片与弹幕治理

## 面试官：设计一个支持百万人在线、每秒几十万条弹幕的直播系统

先说一句大实话：**弹幕系统本质上是一个"高扇出、低价值、可丢失"的实时消息系统**。

它和 IM 的根本区别在于业务预期：

| 维度 | IM 私聊 | 直播弹幕 |
| --- | --- | --- |
| 消息模型 | 点对点 / 小群 | 一对百万（广播扇出） |
| 可靠性 | 必达、有序、可回溯 | 尽力而为，允许丢 |
| 延迟要求 | 秒级可接受 | 300ms 内最佳 |
| 价值密度 | 极高 | 极低（丢了没人发现） |
| 峰值特征 | 平缓 | 脉冲式（大主播开播瞬间） |
| 存储 | 长期可查 | 短期可查 + 抽样留存 |

想清楚这句话，整个架构的取舍就顺了：**弹幕不需要像 IM 一样做 ACK 重传和离线消息，但必须在扇出、成本、治理上做到极致。**

面到这一步，面试官通常会顺着往下问五层：量级估算 → 长连接网关 → 房间分片 → 消息扇出 → 治理与存储。我们一层层拆。

---

## 一、量级估算：先算清楚"到底难在哪"

面试时不要一上来画架构图，先把数字摊开。

假设场景：

- 在线峰值 100 万观众
- 单直播间峰值 30 万人（头部主播）
- 峰值弹幕发送 20 万条/秒，其中 5 万条/秒来自头部房间
- 每个房间平均 20 个热门房间占掉 60% 的弹幕量

**扇出放大系数**是第一个关键指标：

```text
总下行消息数 = Σ(房间在线人数 × 房间弹幕速率)
```

头部房间：30 万人 × 假设每秒该房间 5000 条弹幕 = **1.5 亿条/秒下行**。

这个数字说明：**单纯靠"一条弹幕发给房间所有人"的朴素实现，网络出口直接爆掉。** 所以必须在两个层面做削减：

1. **源头削减**：弹幕在服务端先做合并、去重、降采样，再扇出（比如客户端每秒最多渲染 20 条，服务端就没必要推 5000 条）。
2. **按需削减**：低频观众只推送"高价值弹幕"（含关键词、付费弹幕、@、抽奖中奖），普通弹幕按帧聚合下发。

一个非常实用的降采样策略：**服务端按房间做"时间窗聚合"**，把 100ms 内的 N 条弹幕打包成一个批量帧下发。

```java
// 伪代码：按房间做 100ms 窗口聚合下发
public class DanmakuBatchDispatcher {
    private final Map<String, MessageAccumulator> accumulators = new ConcurrentHashMap<>();

    public void onDanmaku(String roomId, Danmaku msg) {
        MessageAccumulator acc = accumulators.computeIfAbsent(roomId,
                k -> new MessageAccumulator(k));
        acc.add(msg); // 内部队列 + 定时 flush
    }

    // 每 100ms 触发一次
    void flush(String roomId) {
        MessageAccumulator acc = accumulators.get(roomId);
        if (acc == null) return;
        List<Danmaku> batch = acc.drain();
        if (batch.isEmpty()) return;
        // 一帧推给房间内所有连接
        gateway.push(roomId, Frame.danmakuBatch(batch));
    }
}
```

这一个改动，就能把下行消息数从 1.5 亿/秒降到千万级，因为**把"按条扇出"变成了"按帧扇出"**。这是弹幕系统第一个、也是收益最大的优化点。

## 二、长连接网关：怎么扛住百万连接

弹幕的下行通道必须走长连接。选项有三个：

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 轮询（HTTP 短轮询） | 实现最简单 | 延迟高、无效请求多 | 已淘汰 |
| SSE | 单向、天然适合下行 | 浏览器并发连接数限制、无法上行 | 小众场景 |
| WebSocket | 双向、协议成熟 | 需要长连接治理 | **主流选择** |
| QUIC / WebTransport | 弱网表现好、无队头阻塞 | 生态仍在演进 | 前沿 |

主流是 **WebSocket + Netty**。单机连接数怎么估？

- Netty 单机 5 万～10 万连接是稳态值（取决于内存与文件描述符）
- 100 万在线 → **20 台网关**，留 2 倍冗余 → 40 台
- 每连接内存预算：ByteBuf 池化后约 10～30KB，加上业务 session 约 50KB

网关的核心职责其实只有三件事：

```text
1. 连接管理：握手鉴权、心跳保活、断线重连、连接数限流
2. 协议编解码：私有二进制协议（帧头 + 房间号 + 消息类型 + 负载）
3. 消息转发：订阅房间、接收弹幕、按房间下发
```

**网关必须无状态化**。连接是有状态的，但业务状态（用户在哪个房间、身份信息）必须放在外部 Redis，否则热重启会丢掉所有连接的用户上下文。

心跳设计要点：

- 客户端 30s 发一次 ping，服务端 90s 未收到则断开（`IdleStateHandler`）
- 心跳不要走业务线程池，走独立 Handler 避免被慢业务拖死
- 断线重连用**指数退避 + 抖动**，避免整点大主播开播时全网惊群

```java
// Netty 心跳与空闲检测
pipeline.addLast(new IdleStateHandler(90, 30, 0, TimeUnit.SECONDS));
pipeline.addLast(new HeartbeatHandler());
```

## 三、房间分片：百万房间怎么路由

一个平台可能有几十万到几百万个房间（大部分是长尾冷房间）。**路由的核心问题是：一个房间的所有连接应该落到同一台/同一组网关上吗？**

答案是**要做两级路由**：

```text
客户端 → 接入层（LVS/四层 LB）→ 网关集群（一致性哈希按 roomId 取模）
                                    ↓
                             房间订阅关系存 Redis
                                    ↓
                             弹幕消息总线（Kafka/Pulsar/自研 UDP 总线）
```

**为什么按 roomId 哈希分片？**

- 同一房间的弹幕只需要广播给订阅了该房间的网关，而不是全网关
- 哈希分片后，网关只需订阅"自己负责的房间"的 topic/频道
- 冷房间可以多个房间共享一个分片槽（时间轮 + 租约）

```java
// 房间 → 网关分片路由（带虚拟节点的一致性哈希）
public class RoomRouter {
    private final ConsistentHash<String> ring;      // 虚拟节点 160
    private final List<String> gatewayNodes;

    public String route(String roomId) {
        return ring.get(roomId);
    }

    // 冷房间合租：把空闲房间映射到共享槽
    public String routeColdRoom(String roomId) {
        return "shared-slot-" + (Math.abs(roomId.hashCode()) % 64);
    }
}
```

这里有个面试高频追问：**网关扩缩容时怎么办？**

一致性哈希解决的是"扩缩容时只迁移 1/N 的房间"，但迁移瞬间会有短暂的消息丢失/重复。对弹幕这是**完全可接受**的——这就是开篇说的"允许丢"的价值。

如果是 IM，这里就必须做复杂的迁移协商；弹幕直接让客户端重连、重新订阅新分片即可。

## 四、消息扇出：推 / 拉 / 混合

扇出模式有三种，弹幕系统实际上是**混合模式**：

### 4.1 小房间（< 1000 人）——推模式

网关直接遍历房间内的连接下发，简单直接。

### 4.2 中房间（1000 ~ 5 万人）——批量推 + 帧聚合

前面说的 100ms 批量帧，配合 Netty 的 `ChannelGroup` 写。

### 4.3 大房间（> 5 万人）——分层扇出（树形广播）

单个网关持有 3 万条连接的话，一次广播要写 3 万次。可以用 **扇出树**：

```text
源网关 → 一级中转（10 台）→ 二级中转（每台挂 10 台）→ 边缘网关 → 客户端
```

让中转节点只负责"复制+转发"，把压力从"1 个节点写 30 万次"变成"每层写 10 次"。这是 CDN 的思路迁移。

### 4.4 观众视角的"拉"：不要把不该看的都推下去

真实产品里，用户看到的弹幕远少于总弹幕。所以是**推拉结合**：

- 服务端推"高优先级弹幕"：付费弹幕、房管/主播弹幕、中奖通知、@我
- 普通弹幕按订阅关系推送，客户端本地做渲染裁剪（同屏最多 N 条）
- 观众如果往回翻历史弹幕，走**拉**（HTTP 拉取历史弹幕分页）

```java
// 弹幕优先级调度：高优先级立刻推，普通弹幕进聚合窗口
public enum DanmakuPriority { HIGH, NORMAL, LOW }

public void dispatch(String roomId, Danmaku msg) {
    if (msg.priority() == DanmakuPriority.HIGH) {
        gateway.push(roomId, Frame.single(msg));   // 立即推
    } else {
        batchDispatcher.onDanmaku(roomId, msg);    // 聚合后推
    }
}
```

## 五、弹幕存储：冷热分离 + 抽样

弹幕量级决定了**不可能全量持久化到 MySQL**。分三层：

| 层 | 存储 | 保留期 | 用途 |
| --- | --- | --- | --- |
| 热 | Redis List / ZSet（按房间） | 最近 15 分钟 ~ 1 小时 | 新进房用户拉历史、回放 |
| 温 | Kafka → HBase / TiDB / ClickHouse | 7 ~ 30 天 | 回放、报表、弹幕分析 |
| 冷 | 对象存储（压缩片段） | 长期 | 直播回放视频挂载弹幕文件 |

面试加分点：**弹幕可以"抽样存储"**。比如普通弹幕只存 1/10，付费弹幕全存。这样存储成本直接降一个数量级，而回放体验几乎无感。

写入路径：

```text
网关 → 消息总线(Kafka, 按 roomId 分区) → 落库消费者(批量写 HBase) + 分析消费者(ClickHouse)
```

按 `roomId` 做 Kafka 分区键，保证同房间弹幕有序；批量写用 `BufferedMutator`（HBase）或 `JDBC batch`（TiDB），把随机写变成顺序批量写。

## 六、弹幕治理：这才是真正的工程活

架构图画完不算完，弹幕的"脏活"全在治理上。

### 6.1 限流：分维度、分层级

```text
用户级：单用户 1 条/秒（普通）、5 条/秒（付费）
房间级：单房间下行限速（保护网关出口）
全局级：总入口 QPS 限流（保护后端）
```

用 **滑动窗口 + Redis Lua** 做原子限流，比固定窗口更平滑：

```lua
-- 滑动窗口限流（单位：毫秒）
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then return 0 end
redis.call('ZADD', key, now, now .. '-' .. math.random(1000000))
redis.call('PEXPIRE', key, window)
return 1
```

### 6.2 去重与折叠

- **幂等去重**：客户端生成 `clientMsgId`，服务端用 Redis SETNX + 短 TTL 去重，防止重连补发造成刷屏。
- **刷屏折叠**：同一用户短时间内重复内容，折叠为"xxx 发送了 N 条相似弹幕"。
- **敏感词**：用 **AC 自动机（Aho-Corasick）+ DFA** 做多模式匹配，比逐个 `contains` 快几个数量级；词库热更新用版本号 + 本地缓存。

```java
// 基于 Aho-Corasick 的敏感词过滤（简化示意）
public class SensitiveWordFilter {
    private volatile TrieNode root;   // 支持热更新

    public String filter(String text) {
        TrieNode node = root;
        StringBuilder sb = new StringBuilder(text);
        for (int i = 0; i < text.length(); i++) {
            node = node.next(text.charAt(i));
            if (node != null && node.isEnd()) {
                for (int j = node.start(); j <= i; j++) sb.setCharAt(j, '*');
                node = root;
            }
            if (node == null) node = root;
        }
        return sb.toString();
    }
}
```

### 6.3 风控与反垃圾

- 新号 / 无消费记录的账号弹幕进"影子队列"，仅自己可见（**shadow ban**）
- 高频关键词触发人工审核队列
- 机器刷屏特征：内容重复度 + 发送间隔方差 + 设备指纹

## 七、高可用与降级

弹幕系统的降级策略要"分层降级"，而不是一刀切挂掉：

| 故障 | 降级策略 |
| --- | --- |
| 消息总线不可用 | 网关本地直投本机连接，跨机降级为不投 |
| Redis 不可用 | 限流放行 + 本地缓存兜底（宁可多放不可全挂） |
| 存储写入慢 | 丢弃低优先级弹幕，只保付费/主播弹幕 |
| 网关过载 | 拒绝新连接，老连接继续服务（保大主播） |
| 全链路异常 | 客户端降级为本地"机器人弹幕"兜底 |

最后一条很真实：**很多直播平台在服务端异常时会下发一个预置的弹幕池**，用户体验上几乎感知不到。这就是"弹幕可丢失"的价值最大化利用。

## 八、面试常见追问

**Q1：弹幕为什么不用 Kafka 直接扇出给客户端？**
Kafka 是拉模型，客户端不可能直连 Kafka（几十万消费者、安全、协议不匹配）。正确做法是 Kafka 做网关间的消息总线，网关再推给客户端。

**Q2：怎么保证同一用户看到的弹幕顺序一致？**
按 `roomId` 分区保证 Kafka 内有序；网关单线程写 `Channel` 保证连接内有序。跨网关不保证全局有序——业务上也不需要。

**Q3：30 万人房间，一个网关挂了怎么办？**
网关无状态 + 客户端自动重连到哈希后的新网关；一致性哈希只影响 1/N 房间。断线期间弹幕丢失可接受，重连后拉最近 15 分钟 Redis 热数据补上。

**Q4：弹幕和礼物/点赞能共用一套架构吗？**
能。礼物是"高优先级弹幕"，点赞是"高频低价值事件"，用同一总线 + 不同优先级通道即可。点赞尤其适合**客户端聚合 + 服务端累加**（不需要每条都上行）。

**Q5：怎么防"弹幕机器人"刷屏？**
三层：接入层设备指纹/行为特征 → 业务层限流+去重 → 内容层敏感词+语义模型。再叠加"影子队列"让刷子以为发出去了。

---

## 总结

弹幕系统的设计精髓，可以浓缩成四句话：

1. **承认它可丢失**——放弃 IM 那套可靠性机制，是最大的架构红利；
2. **把按条扇出改成按帧扇出**——一个窗口聚合，行量降一个数量级；
3. **按 roomId 分片 + 网关无状态**——扩容、容灾、迁移都变成可接受的"丢一点"；
4. **治理比架构更重要**——限流、去重、折叠、风控、降级，才是线上不出事的关键。

下次面试官再问"设计一个弹幕系统"，你就从量级估算开始，一路讲到影子队列和降级池——层次感出来了，面试基本就稳了。

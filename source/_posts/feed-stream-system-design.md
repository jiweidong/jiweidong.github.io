# 【系统设计】Feed 流系统架构设计：从推拉结合到百亿级信息流

## 面试官：微博的首页信息流是怎么做的？如果让你设计一个 Feed 流系统，你会怎么设计？

Feed 流（信息流）是互联网最核心的业务形态之一：微博、朋友圈、抖音、小红书，全是 Feed 流。它和普通 CRUD 最大的区别在于——**每个用户看到的首页内容都不一样**，是"千人千面"的个性化时间线。设计 Feed 流，本质是解决三个问题：**内容怎么分发、时间线怎么生成、读多写多怎么扛**。

## 一、需求与指标

先定义清楚规模，才有设计依据：

- 日活用户 1 亿，月活 3 亿；
- 平均每个用户关注 200 个账号；
- 每秒新增内容（发帖）1 万条，峰值 5 万条；
- 每秒读取时间线（刷首页）10 万次，峰值 50 万次；
- 要求：**读延迟 < 200ms，写后延迟 < 1s 内可见**。

读是写的 10 倍以上——这是所有 Feed 流设计的出发点：**读多写少，必须为读优化**。

## 二、三种核心模型：推、拉、推拉结合

### 2.1 拉模式（Pull / 读扩散）

用户刷首页时，实时去拉取他关注的所有人的最新内容，再合并排序。

```
用户刷首页 → 查关注列表（200人）→ 分别拉每个人的最新内容 → 合并排序 → 返回
```

**优点**：写路径极轻——发帖只需要写一次自己的发布表，无任何额外成本；粉丝再多也不怕。

**缺点**：读路径重——每次刷新要拉 200 个人的内容再合并，大 V 的粉丝刷一次首页要触发海量查询；延迟高，合并排序复杂。

**适用**：关注数少、读频率低的场景，或作为兜底方案。

### 2.2 推模式（Push / 写扩散 / Fanout）

用户发帖后，系统**主动把内容推送到所有粉丝的时间线（收件箱）里**。

```
用户发帖 → 查粉丝列表（1000万）→ 往每个粉丝的收件箱写入内容 → 粉丝刷首页直接读自己的收件箱
```

**优点**：读路径极轻——刷首页就是一次收件箱读取，延迟极低；这也是"读多写少"场景的理想形态。

**缺点**：写路径重——一个千万粉丝的大 V 发一条微博，要写千万条数据（**写放大**）；粉丝活跃度低时浪费存储。

**适用**：粉丝量可控的场景（如企业内部系统、小规模社交产品）。

### 2.3 推拉结合（混合模式）——业界标准答案

核心思路：**普通用户用推，大 V 用拉**。

```
用户发帖：
- 粉丝数 <= 阈值（如 10 万）：走推模式，写入所有粉丝收件箱
- 粉丝数 > 阈值（大 V）：不推，标记"发帖成功"即可（内容进大 V 自己的发布表 + 粉丝的"大V关注表"占位）

粉丝刷首页：
1. 读自己的收件箱（普通用户推过来的内容）——快速返回
2. 异步合并拉取"关注的超粉用户"的最新内容（拉取量少：超粉一般不超过几十个）
3. 两部分按时间合并排序返回
```

**为什么这样设计？**

- 推模式保证了 99% 场景的读性能（收件箱 O(1) 读取）；
- 大 V 用拉模式，把"千万级写放大"化解为"百万粉丝各自拉一次"——总成本从 O(粉丝数) 降到 O(1)；
- 用户关注的超粉数量天然有限（微博上关注超过 100 个千万大 V 的人极少），拉取成本可控。

**阈值怎么定？** 核心是算账：推一条消息的成本 ≈ 写 N 次，拉的成本 ≈ 读 M 次。当 N（粉丝数）超过某个值时，推的成本就大于拉。业界常见阈值在 10 万~100 万之间，根据存储和带宽成本调优。

## 三、写路径架构

### 3.1 发帖主流程

```
用户发帖
  → API 网关 → 发帖服务（写入内容表，MySQL/分布式KV）
  → 写入成功 → 返回"已发布"
  → 异步触发 Fanout 任务（MQ 解耦）
      → 查询粉丝列表（关注关系服务）
      → 分批（每批 500~1000 个粉丝）写入收件箱（Redis 或时序存储）
      → 大 V 粉丝列表数量过大 → 标记占位，转拉模式
```

关键点：

- **发帖与 Fanout 解耦**：发帖主流程只写内容表，Fanout 走 MQ 异步，避免写放大拖慢发帖响应；
- **分批写收件箱**：一次 MQ 消息处理一批粉丝，控制 Redis 管道大小（pipeline 一次 500 条左右），避免大 Key 和连接风暴；
- **收件箱存储选型**：Redis ZSET（member=内容ID，score=时间戳）是最常见方案，天然支持按时间排序分页。

### 3.2 收件箱的存储细节

```java
// Redis ZSET 存储收件箱
ZADD feed:{userId} {timestamp} {feedId}

// 拉取首页：按时间倒序取 20 条
ZREVRANGE feed:{userId} 0 19
```

**问题来了：ZSET 无限增长怎么办？** 用户长期不刷，收件箱堆积到几十万条，内存爆炸。

业界解法：

1. **限制收件箱容量**：每个用户的收件箱只保留最近 N 条（如 1000 条），超出部分丢弃——用户也不会翻到几个月前的首页（回看历史走"个人主页/搜索"）；
2. **冷热分离**：热数据（7 天内）放 Redis，冷数据落 MySQL/对象存储，翻页超过热窗口就查冷库；
3. **惰性清理**：用户刷首页时顺带清理队尾过期数据，避免定时任务全量扫。

## 四、读路径架构

### 4.1 刷首页流程

```
用户刷首页
  → Feed 读取服务
  → 读收件箱 ZSET（Redis）取前 20 条 feedId
  → 批量查内容服务（mget 内容详情，本地缓存 + Redis 缓存 + MySQL 三级）
  → 异步拉取超粉最新内容（并发拉取，合并）
  → 合并排序 → 返回给客户端
```

### 4.2 性能关键点

1. **Feed 内容缓存**：Feed 详情（文字、图片、点赞数）必须缓存。微博的缓存命中率要做到 95%+，缓存穿透用布隆过滤器挡住。
2. **批量接口**：一次首页请求只允许 2~3 次批量网络调用（收件箱 1 次 + 内容 mget 1 次 + 超粉拉取 1 次），禁止 N 次串行调用。
3. **本地缓存**：热内容（大 V 刚发的爆款）在应用本地缓存一份，避免全部打爆 Redis。
4. **合并排序**：数据量小（< 50 条）直接在内存按时间排序即可，不需要复杂归并。

## 五、关注关系与异步一致性

### 5.1 关注/取关的 Fanout 处理

- **关注**：关注成功 → 异步把对方最近 N 条内容写入我的收件箱（"关注即见"体验）；
- **取关**：异步从收件箱删除对方内容（或标记过滤）；
- **新用户**：首次登录时后台预热收件箱（拉取所有已关注账号的最近内容）。

### 5.2 一致性保障

Fanout 是异步的，必然存在"我发了，但粉丝还没看到"的短暂延迟。方案：

- **最终一致性 + 兜底**：Fanout 失败的消息进死信队列重试，重试仍失败则落补偿表，定时扫描重发；
- **发帖延迟可见**：用户自己发的内容，读自己收件箱时必须立即可见（自己的内容直接写 + 不走异步）；
- **重放安全**：Fanout 消息带唯一 ID，消费幂等（收件箱 ZSET 天然幂等——同一 feedId 只存一份）。

## 六、面试高频追问

**Q1：Redis 存收件箱，数据量大怎么办？**
分片：按 userId 哈希分片到多个 Redis 集群；容量控制：只保留最近 1000 条；冷热分离：热数据 Redis + 冷数据 MySQL/对象存储。另外收件箱可以用 `Redis Cluster` 天然水平扩展。

**Q2：大 V 发帖，粉丝刷首页怎么保证不慢？**
超粉内容走拉模式：粉丝端最多并发拉取几十个超粉的最近内容（每个超粉的内容单独缓存），合并排序后返回。拉取用并行调用，总耗时可控在几十毫秒。

**Q3：Feed 流怎么做排序？**
基础版按时间倒序；进阶版用推荐算法（热度分 = 时间衰减 × 互动权重），但推荐排序对性能要求更高，一般做"粗排 + 精排"分层，且结果缓存。

**Q4：为什么不用 MySQL 一张大表 + 索引搞定？**
Follow 关系是"一对多"，一个千万粉丝大 V 的每条动态都要关联千万行（写放大无法避免，且 MySQL 扛不住千万级 QPS 读）；Redis ZSET 的 O(logN) 插入 + O(1) 范围读，性能差 2~3 个数量级。

**Q5：刷首页翻页怎么做？**
游标分页（`since_id` / `max_id`），不用 `offset`——中间插入新内容会导致 offset 分页重复/遗漏。

## 七、总结

Feed 流设计的核心矛盾是**写放大 vs 读放大**：推模式用写放大换读性能，拉模式用读放大换写简单，推拉结合则是对两种成本做最优化折中。再叠加收件箱容量控制、冷热分离、异步 Fanout、三级缓存这些工程手段，就构成了一套能扛百亿级信息流的架构。面试时抓住"**普通用户推、大 V 拉、Redis ZSET 收件箱、异步解耦、最终一致性**"这五个关键词，把账算清楚，基本就稳了。

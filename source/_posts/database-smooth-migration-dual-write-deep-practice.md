# 【数据库实战】数据库平滑迁移深度实战：全量增量同步、双写过渡与灰度切换回滚方案

## 面试官：公司要把订单库从 MySQL 5.7 迁到 MySQL 8.0，还要顺便分库分表，线上不能停服，你怎么设计这个迁移方案？

数据库迁移是每个后端工程师迟早要面对的高危操作：**表结构要改、数据量几个亿、业务不能停、出了问题要能回滚**。直接停机迁移（Maintenance Window）在小公司还能接受，大流量业务根本停不起。这一篇讲透业界标准的**平滑迁移四阶段方案**：存量同步 → 增量同步 → 双写过渡 → 灰度切换，以及每一步的 Java 落地细节与回滚预案。

## 一、迁移的整体目标与原则

### 1.1 三个核心目标

| 目标 | 说明 |
| --- | --- |
| 不停服 | 迁移全程业务可用，用户无感知 |
| 不丢数据 | 切换瞬间的数据也不能丢（0 丢失是理想，至少做到秒级可控） |
| 可回滚 | 出问题能在分钟级回到旧库，而不是「回不去了」 |

### 1.2 什么时候必须走平滑迁移

- 数据量大（千万级以上），全量导出导入耗时长；
- 停机窗口不可用（7×24 业务、跨境电商、金融支付）；
- 迁移伴随架构变更（分库分表、换引擎、改字段类型）。

## 二、阶段一：全量同步（存量数据搬运）

### 2.1 工具选型

| 工具 | 适用场景 | 特点 |
| --- | --- | --- |
| mysqldump / mysqlpump | 小数据量（GB 级） | 简单，但锁表/慢 |
| mydumper / myloader | 大数据量 | 并行导出导入，快 |
| DataX（阿里） | 异构数据源 | 支持 MySQL→MySQL/ES/Hive 等 |
| 自研导出导入 | 需定制清洗/转换 | 配合分片键路由 |

### 2.2 关键细节

**1. 一致性快照**：全量导出必须基于**同一时间点的一致性快照**，否则导出的数据自相矛盾。MySQL 用：

```sql
-- 开启可重复读隔离级别下的一致性快照
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- 导出全部表
```

或用 `--single-transaction`（InnoDB 下不锁表，基于 MVCC 快照）。

**2. 分片并行**：按主键范围或分片键把数据切成多个任务并行搬运，比如：

```java
// 伪代码：按主键范围分片并行导入
long minId = selectMinId();
long maxId = selectMaxId();
int shardCount = 16;
long step = (maxId - minId) / shardCount;
ExecutorService pool = Executors.newFixedThreadPool(shardCount);
for (int i = 0; i < shardCount; i++) {
    long from = minId + i * step;
    long to = (i == shardCount - 1) ? maxId : from + step;
    pool.submit(() -> migrateRange(from, to));   // 批量 SELECT + 批量 INSERT
}
```

**3. 全量期间的写入怎么办**：全量同步期间业务还在写旧库，这些增量数据由**阶段二的增量同步**负责追平。所以全量与增量必须**同时进行**。

## 三、阶段二：增量同步（追平线上写入）

### 3.1 基于 binlog 的增量同步

业界标准方案：**监听旧库 binlog，实时回放到新库**。

```text
旧库 binlog --> Canal / Maxwell / Debezium --> 解析成 DML 事件 --> 写入新库
```

以 Canal 为例：

```java
// Canal 客户端消费 binlog 变更（伪代码）
CanalConnector connector = CanalConnectors.newSingleConnector(
        new InetSocketAddress("127.0.0.1", 11111), "example", "", "");
connector.connect();
connector.subscribe("order_db\\..*");
while (running) {
    Message message = connector.getWithoutAck(100);   // 批量拉取
    for (CanalEntry.Entry entry : message.getEntries()) {
        if (entry.getEntryType() == CanalEntry.EntryType.ROWDATA) {
            // 解析出 表名 + 操作类型(INSERT/UPDATE/DELETE) + 变更前后数据
            replayToNewDb(entry);
        }
    }
    connector.ack(message.getId());   // 确认消费，防止丢数据
}
```

**重点**：

- **Canal 自身高可用**：Canal 挂掉会丢增量，所以要部署 Canal 集群 + 记录消费位点（position）到 ZK/DB，重启后从位点续传；
- **同步延迟监控**：对比「新库最新 binlog 位点」与「旧库当前位点」的差值，延迟超过阈值（如 5 秒）要告警——**切换前必须确认延迟为 0**；
- **DDL 同步**：Canal 默认不处理 DDL，表结构变更要单独脚本同步，注意顺序。

### 3.2 校验：数据对账

增量追平后，必须做**全量数据校验**，常见三种方式：

| 方式 | 原理 | 特点 |
| --- | --- | --- |
| 全量逐行比对 | 两边都查出来对比 | 最准，但慢 |
| 抽样比对 | 按主键抽样对比 | 快，覆盖不全 |
| 校验和（checksum） | 按分片计算 CRC/哈希汇总对比 | 快且覆盖全，业界主流 |

```sql
-- 分片校验：按 100 万主键为一个分片，对比新旧库的 CRC32 汇总
SELECT CONCAT(MAX(id), '_', SUM(CRC32(CONCAT_WS('#', id, order_no, amount, status))))
FROM order_table WHERE id BETWEEN 0 AND 1000000;
```

两边算出来的串一致，则该分片一致；不一致则二分定位差异行。

## 四、阶段三：双写过渡（最关键的一步）

### 4.1 为什么需要双写

直接切流量有个致命问题：**切换瞬间**旧库还在接收新写入（因为切换不是原子的），这些数据增量同步可能来不及追上。双写的作用是：

> 让应用层同时写旧库和新库，跑一段时间（通常 1~2 周），两边数据持续保持一致，为切换铺路。

### 4.2 双写的三种实现

**方案 A：应用层双写（最常用）**

在 DAO/Service 层加一个「双写开关」，写操作同时执行旧库写入 + 新库写入：

```java
@Component
public class OrderWriteService {

    @Value("${migration.dual-write:false}")
    private boolean dualWriteEnabled;

    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);            // 写旧库（主库，业务依赖它）
        if (dualWriteEnabled) {
            try {
                newOrderMapper.insert(order); // 写新库（旁路，失败不影响主流程）
            } catch (Exception e) {
                // 记录失败到重试表，由异步任务补偿
                dualWriteFailLogMapper.insert(new DualWriteFailLog(order));
            }
        }
    }
}
```

要点：

- **新库写失败不能影响主流程**——旁路写入必须 try-catch 包裹 + 失败记录 + 异步补偿；
- 新库写入要**幂等**（以业务主键/唯一键去重），因为补偿任务可能重放；
- 关闭新库的外键/唯一约束检查？不行——约束必须保持一致才能发现问题。

**方案 B：Canal 反向同步**

如果不想改业务代码，可以用 Canal 把旧库 binlog 同时回放给新库，等于「旧库写到哪，新库跟到哪」。缺点：**应用层显式写新库才能发现代码层面的兼容问题**（比如新库字段类型变了、分片键逻辑不对）。

**方案 C：中间件/代理层双写**

在 DAO 层用 AOP 切面统一拦截写操作双写，业务代码零侵入，但实现复杂度高，适合统一 DAO 框架的团队。

### 4.3 双写期间的常见坑

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 自增主键冲突 | 新旧库自增序列不同步 | 迁移后统一用雪花 ID 或显式指定主键 |
| 唯一键冲突 | 补偿任务重放导致重复 | 写入按业务唯一键去重（INSERT ... ON DUPLICATE KEY） |
| 事务不一致 | 旧库提交了，新库没提交 | 双写放同一个事务外层，或接受秒级不一致 + 对账兜底 |
| 分片键路由错误 | 新库查不到数据 | 双写前先写单测覆盖分片路由规则 |

## 五、阶段四：灰度切换与回滚

### 5.1 灰度策略

不要一把梭，按流量比例逐步切换：

```text
5% 流量 → 20% 流量 → 50% 流量 → 100% 流量
```

灰度实现方式：

1. **按用户维度**：用户 ID hash 取模，白名单用户先切；
2. **按接口维度**：读接口先切（风险低），写接口后切；
3. **配置中心开关**：用 Nacos/Apollo 的动态配置控制「读新库比例」和「写新库比例」，随时调整、随时回滚。

```java
// 灰度路由：按 userId 取模决定走新库还是旧库
public DataSource routeDataSource(Long userId) {
    int bucket = (int) (userId % 100);
    if (bucket < grayPercent) {   // grayPercent 由配置中心动态控制
        return newDataSource;
    }
    return oldDataSource;
}
```

### 5.2 切换期间写入怎么保证不丢

切换瞬间的写入是最大风险点，推荐**先切读、再切写**：

- **第一步**：读流量全切新库（写仍走旧库+双写）；
- **第二步**：观察新库读写延迟、错误率、数据一致性 1~2 周；
- **第三步**：写流量灰度切换（此时新旧库数据已一致，切换即「改一下路由」）；
- **第四步**：切换完成后保留**增量同步反向**（新库 binlog 同步回旧库）一段时间，作为回滚的底牌。

### 5.3 回滚预案（必须提前准备好）

| 回滚级别 | 操作 | 耗时 |
| --- | --- | --- |
| 配置回滚 | 配置中心把灰度比例调回 0 | 秒级 |
| 路由回滚 | 数据源路由改回旧库 | 分钟级 |
| 数据回滚 | 用保留的「新→旧」增量同步把数据倒灌回旧库 | 视数据量 |
| 全量回滚 | 旧库快照重建（最坏情况） | 小时级 |

**铁律**：没有回滚预案的迁移不要开工。切换前必须演练一次完整的「切换→发现问题→回滚」流程。

## 六、迁移全程的监控与检查清单

### 6.1 必须盯的指标

- 增量同步延迟（目标：切换前 0 延迟）；
- 双写失败率（目标：0）；
- 对账不一致分片数（目标：0）；
- 新旧库读写延迟对比、慢 SQL 数量、连接数；
- 业务错误率、超时率（灰度期间逐档观察）。

### 6.2 切换前 Checklist

```text
□ 全量同步完成，对账通过（全量校验和一致）
□ 增量同步延迟为 0，且持续稳定
□ 双写已开启并稳定运行 ≥ 1 周，失败率 0
□ 灰度路由代码已上线，配置中心开关可用
□ 回滚预案演练通过（新→旧反向同步链路可用）
□ 监控大盘、告警规则就绪
□ 通知相关方，选择业务低峰期执行
```

## 七、面试高频追问汇总

**Q1：为什么不能直接停机迁移？**
A：大流量业务停机代价高（每停 1 分钟都是钱），而且停机时间越长，出问题的概率越大；平滑迁移把风险分摊到几周里，每步都可验证、可回滚。

**Q2：双写会不会导致两边数据不一致？**
A：会，所以要三件套兜底：旁路写入失败记录 + 异步补偿、按业务唯一键幂等去重、定期全量对账。双写的目标不是「保证不出现不一致」，而是「不一致可发现、可修复」。

**Q3：Canal 同步延迟怎么压到 0？**
A：延迟主要来自解析和回放。做法：Canal 集群横向扩容、按库拆分同步任务、回放端批量提交（攒批 100 条/100ms 提交一次）、新库关闭非必要二级索引减少回放开销。切换前用「双位点对比」确认延迟归零。

**Q4：切换后发现新库有问题，怎么最快回滚？**
A：路由回滚——把灰度比例调回 0，所有流量回旧库；前提是旧库还活着且数据完整（所以切换后要保留新→旧的反向同步）。配置回滚是最快、最安全的兜底。

**Q5：分库分表迁移和普通迁移有什么不同？**
A：多了「数据路由」这一层：存量数据要按分片键重新分布、全量导入要按分片并行、增量回放要按分片键路由到对应分片、双写要验证路由规则、对账要按分片进行。复杂度主要在路由正确性上。

## 八、总结

| 阶段 | 核心动作 | 风险 | 完成标志 |
| --- | --- | --- | --- |
| 全量同步 | 快照导出 + 并行导入 | 耗时长、锁表 | 全量对账一致 |
| 增量同步 | binlog 实时回放 | 丢消息、延迟 | 延迟归零 |
| 双写过渡 | 应用层旁路双写 + 补偿 | 数据不一致 | 稳定运行 1~2 周无失败 |
| 灰度切换 | 先读后写、比例灰度 | 切换瞬间丢写 | 100% 流量稳定 |

**一句话总结**：数据库平滑迁移 = 全量打底 + 增量追平 + 双写验证 + 灰度切换，核心是**任何一步都可验证、可回滚**。面试时按「四阶段」讲流程，再补上「Canal 位点」「对账校验和」「回滚三板斧」这些细节，就是一份满分方案。

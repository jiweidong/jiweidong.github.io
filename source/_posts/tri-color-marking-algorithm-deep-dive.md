# 【JVM 底层】三色标记算法深度解析：从 CMS 到 G1 的并发标记、漏标与写屏障

## 面试官：CMS 和 G1 的并发标记阶段是怎么实现的？为什么需要写屏障？

"三色标记"是 JVM 面试从 30K 到 50K 的分水岭。懂的人能讲清楚"为什么并发标记会漏标、SATB 和增量更新怎么解决、写屏障在干什么"。本文从可达性分析讲起，把并发标记的底层逻辑完整拆开。

## 一、为什么需要并发标记？

### 1. 可达性分析：GC Roots 出发的图遍历

JVM 判定对象存活靠**可达性分析**：从 GC Roots（栈帧局部变量、静态变量、JNI 引用、常量池引用等）出发，沿着引用链遍历，**所有不可达的对象就是垃圾**。

```java
Object a = new Object();   // a 是 GC Root
Object b = a;              // b 通过 a 可达，存活
Object c = new Object();   // 没有引用指向 c，垃圾
```

### 2. 标记期间不能乱动：STW 的由来

如果标记过程中**引用关系还在变化**（应用线程在跑），标记结果可能失真。所以早期的标记（如 Serial/Parallel 的 mark 阶段）必须**暂停所有业务线程**——这就是 **Stop The World（STW）**。

但 STW 时间 = 堆大小 × 遍历成本，堆越大暂停越长。CMS 和 G1 的追求是**"标记的同时让业务线程继续跑"**，于是有了并发标记——以及它带来的难题。

## 二、三色标记算法

把遍历过程中的对象染成三种颜色：

| 颜色 | 含义 | 状态 |
|------|------|------|
| **白色** | 未被访问 | 可能是垃圾（标记结束时仍为白色 = 垃圾） |
| **灰色** | 自身已被访问，但其引用到的对象还没全部扫描 | 正在处理中（工作队列） |
| **黑色** | 自身和它的所有引用都已扫描完 | 确定存活 |

```java
// 伪代码：三色标记的 BFS/DFS
// 初始：所有对象白色，GC Roots 入灰色队列
while (!grayQueue.isEmpty()) {
    Object cur = grayQueue.poll();          // 取出一个灰色
    for (Object ref : referencesOf(cur)) {  // 扫描它的引用
        if (colorOf(ref) == WHITE) {
            colorOf(ref) = GRAY;            // 染灰，入队
            grayQueue.offer(ref);
        }
    }
    colorOf(cur) = BLACK;                   // 扫描完，染黑
}
// 结束后：所有白色对象 = 垃圾，回收
```

**串行标记时这个算法完美**：遍历期间引用不变，白→灰→黑单向流动，最后白色全是垃圾。

## 三、并发标记的灾难：多标与漏标

业务线程和 GC 线程并发跑，引用关系随时在变，会出现两种错误：

### 1. 多标（浮动垃圾）——无害

**本来要死的对象，被并发期间新引用救活了，或者被标成黑色。** 比如：

```
业务线程执行：b.field = a;   // 把已扫描过的 a 赋给 b
之前：a 被标为黑色（它的引用已扫完），但现在 a 又引用了新对象 c
```

结果：c 是垃圾却因为是"黑色 a 的引用"被漏扫，**被当成存活**——这就是"多标"，产生**浮动垃圾**，留到下一轮 GC 清理。**无害**，只是浪费一点内存。

### 2. 漏标——致命！活对象被当垃圾回收

**本来活着的对象被标成白色，直接被回收** → 程序崩溃。漏标需要同时满足两个条件：

```
条件一：黑色对象 X 新增了指向白色对象 W 的引用   （X -> W 新建立）
条件二：灰色对象 Y 原本指向 W 的引用被删除了       （Y -> W 被切断）
```

分析：GC 线程已经扫完 X（黑色，不会再扫 X 的引用），而 Y 还没来得及扫到 W 时引用被删了。结果 **W 永远没被扫到，保持白色 = 被当垃圾回收**。而 W 其实是业务线程刚让 X 引用的活对象！**这就是必须解决的"漏标"问题。**

## 四、解决方案：两种写屏障

要防漏标，就要破坏上面两个条件中的任意一个：

### 方案 A：增量更新（Incremental Update）——CMS 的选择

**破坏条件一**：当黑色对象 X **新增引用**指向白色对象 W 时，把 X **重新标回灰色**（或记录这个引用），下一轮继续扫描 X。

```c
// 伪代码：增量更新写屏障（赋值时触发）
void write_barrier(Obj *field, Obj *new_value) {
    if (is_black(field->owner) && is_white(new_value)) {
        gray(field->owner);          // 黑色变灰，重新扫描
    }
    *field = new_value;
}
```

**代价**：灰色对象会反复变多（重新扫描），标记时间变长；且记录引用需要额外的记忆集结构。

### 方案 B：原始快照 SATB（Snapshot At The Beginning）——G1 的选择

**破坏条件二**：记录"被删除的引用"（快照思想）。**标记开始时**对引用关系拍一张快照，**凡是标记开始时是存活（灰色）对象引用的对象，都按快照继续标记**——即使后来引用被删，也当它存活，下一轮再回收。

```c
// 伪代码：SATB 写屏障（删除引用时触发）
void write_barrier(Obj *field, Obj *old_value) {
    if (is_gray(field->owner) && is_white(old_value)) {
        enqueue_satb(old_value);     // 把"将死的旧引用目标"记入 SATB 队列
    }
    *field = new_value;              // 实际赋值
}
// GC 线程：扫描 SATB 队列里的对象，把它们当作"快照时存活"，继续标记
```

**代价**：SATB 队列要记录所有被删除的引用，**会产生更多浮动垃圾**（快照时存活、实际已死的对象被多保留一轮）。但好处是**不需要重新扫描黑色对象**，标记效率高、停顿更可预测。

### 对比总结

| 维度 | 增量更新（CMS） | SATB 原始快照（G1） |
|------|----------------|---------------------|
| 防漏标思路 | 破坏条件一：黑色变灰重扫 | 破坏条件二：记录旧引用按快照标记 |
| 副作用 | 灰色对象反复变多，标记慢 | 浮动垃圾更多 |
| 写屏障时机 | 赋值**新引用**时 | **删除旧引用**时 |
| 停顿特性 | 重扫阶段（remark）要 STW | 无重扫，停顿更稳 |
| 典型使用者 | CMS | G1、ZGC |

## 五、写屏障到底是什么？

"写屏障"不是内存屏障（memory barrier），**它是一段在"引用字段赋值"时被插入执行的代码**（类似 AOP 切面），由 JIT 编译器在编译赋值指令时自动插入：

```java
// 源码
a.field = b;

// JIT 编译后实际执行（示意）
write_barrier(a.field, b);   // 增量更新/SATB 的钩子
a.field = b;
```

**每个引用赋值都过一遍写屏障**，所以写屏障的性能至关重要——这也是 JVM 用"位图 + 卡表"这类紧凑结构来记录引用变化的原因。

**延伸：卡表（Card Table）与记忆集（Remembered Set）**
跨代/跨区域引用（老年代对象引用新生代对象）怎么找？JVM 把堆分成 512 字节一张的"卡"，**老年代对象引用新生代对象时，通过写屏障把对应卡标记为 dirty**。GC 时只需扫描 dirty 卡对应的对象，**不用全堆扫描**。G1 在此基础上为每个 Region 维护 RSet，记录"谁引用了本 Region 的对象"，实现局部回收。

## 六、CMS 与 G1 的并发标记流程对比

### CMS 的 4 个阶段（并发标记相关）

```
1. 初始标记（STW）：只标 GC Roots 直接引用的对象，极快
2. 并发标记（并发）：三色标记遍历全堆
3. 重新标记（STW）：用增量更新修正并发期间的漏标（黑色变灰重扫）
4. 并发清除（并发）：清理浮动垃圾
```

### G1 的并发标记（借助 SATB）

```
1. 初始标记（STW）：标 GC Roots + 处理 SATB 队列
2. 并发标记（并发）：三色标记 + 不断处理 SATB 队列中的"旧引用快照"
3. 最终标记（STW）：处理 SATB 队列剩余内容
4. 清理（STW + 并发）：统计存活对象，筛选回收价值高的 Region
```

**关键差异**：CMS 靠"重新标记 + 增量更新"修正，G1 靠"SATB 快照"全程不重扫——所以 **G1 的停顿时间更可预测**，这也是 G1 取代 CMS 成为默认收集器的底层原因之一。

## 七、面试高频追问

**Q1：什么是浮动垃圾？**
并发标记期间产生的、实际已死但被误标为存活的对象（多标的结果），只能等下一轮 GC 回收。SATB 比增量更新产生更多浮动垃圾。

**Q2：漏标的两个必要条件？**
① 黑色对象新增引用指向白色对象；② 灰色对象删除了指向该白色对象的引用。两者**同时发生**才漏标。

**Q3：为什么 G1 用 SATB 而 CMS 用增量更新？**
G1 面向大堆和可预测停顿，SATB 免去重新扫描黑色对象，标记阶段更稳定；代价是浮动垃圾多、占用内存记录快照。CMS 追求低延迟但可接受 remark 停顿，增量更新实现简单、浮动垃圾少。

**Q4：ZGC 呢？**
ZGC 用**染色指针（Colored Pointer）**——引用指针本身携带颜色标记（Marked0/Marked1/Remapped），配合读屏障（Load Barrier）在**读取引用时**修正，实现了几乎不随堆大小增长的停顿（<1ms）。它连"标记"都放进了指针里，是另一个维度的方案。

**Q5：写屏障会影响性能吗？**
会，每次引用赋值都有开销。所以 JVM 做了极致优化：卡表用字节数组 + 位图、写屏障用汇编级别的最短指令序列。这也是"并发收集器吞吐略低于并行收集器"的原因之一。

## 八、总结

**一条主线记住**：并发标记的难点 = **业务线程边跑边改引用** → 可能漏标活对象 → **增量更新**（CMS：黑变灰重扫）和 **SATB 快照**（G1：记录旧引用）两种写屏障来解决 → 写屏障 = 赋值时的钩子代码 → 顺带实现卡表/RSet 记录跨代引用。**问到底层，一切都是"用一点空间和时间开销，换掉全量 STW"。**

# 【AI 转型】AI 应用开发职级能力模型：P5 到 P8 的能力矩阵、晋升证据链与定级实战

## 前言

一个很扎心的现象：

> 有人把 LangChain、Spring AI、RAG、MCP 全都学了一遍，Demo 写了十几个，去面 AI 应用开发岗，被定到了"初级"，薪资还不如他做 Java 后端时高。

原因不是技术不够，而是**他把"能力"当成了"职级"**。

- **能力**回答的是"你会不会做"；
- **职级**回答的是"在多复杂的问题上、以多大的确定性、带动了多少人做成"。

这两个东西是两个维度。你可以会用 RAG（能力），但如果你的 RAG 只在自己的 Demo 里跑过 200 篇文档，那你证明的是"会"，不是"能扛生产"。

这篇给出一个可以直接用来对照的**职级能力模型**：4 个职级 × 10 项能力，每格写清"能做到什么程度"，再配上晋升证据链与 Java 转岗定级的实操。

---

## 一、先分清两个坐标系

| 维度 | 能力模型 | 职级模型 |
|---|---|---|
| 回答的问题 | 我会什么 | 我在多大范围内、以多高确定性交付结果 |
| 评价依据 | 知识 + 技能 | 影响力半径 + 结果 + 沉淀 |
| 是否可速成 | 可以（几周） | 不可以（需要真实项目与时间） |
| 在面试中的作用 | 决定"要不要" | 决定"给几级、给多少钱" |

**职级的本质是"影响力半径"**：

```
P5：把一个明确任务做好          → 半径 = 任务
P6：把一个模块/项目从头做到上线  → 半径 = 项目
P7：把一个系统/领域做稳做优      → 半径 = 系统 + 小团队
P8：定义一个方向并让别人也能做成 → 半径 = 组织 + 业务
```

在这条主轴上，AI 能力只是"内容"，不改变"半径"的判定方式。很多人转岗失败，是因为**只换了内容，没有扩大半径**。

---

## 二、四级职级定义（AI 应用开发）

### P5 · AI 应用开发工程师（执行者）

**典型画像**：能独立完成一个明确的开发任务，代码质量合格，遇到问题会查文档、会问人。

| 项目 | 要求 |
|---|---|
| 交付 | 在他人设计好的框架内完成模块开发，PR 可一次通过率 > 70% |
| 技术 | 熟练调用 LLM API、写清 Prompt、能用 Spring AI 做基本 RAG |
| 调试 | 能定位"为什么答错了"到"检索没召回 / Prompt 没说清"这一层 |
| 边界 | 需要有人给方案，遇到架构选择要请示 |

**红线能力**：**能把一个 AI 功能跑通并且可复现**（不是"在我机器上能跑"）。

### P6 · 资深 AI 应用开发工程师（独立负责人）

**典型画像**：拿到一个业务目标，能自己拆解、选型、落地、上线、兜住线上问题。

| 项目 | 要求 |
|---|---|
| 交付 | 独立负责一个 AI 功能/子系统从 0 到 1，含排期、联调、上线、复盘 |
| 技术 | 能设计 RAG 全链路（切分/Embedding/召回/重排）、能设计 Agent 工具集与状态机 |
| 质量 | 建立最小评测集（50–200 条），能说清"这次改动让准确率从 71% 到 82%" |
| 成本 | 能算出单次请求成本，做过至少一次成本优化（缓存/小模型/上下文裁剪） |
| 稳定性 | 有降级、限流、超时、重试的实际设计，能处理 429 与模型抖动 |
| 影响 | 能带 1–2 个初级同学，能输出可复用的组件或规范 |

**红线能力**：**能对一个 AI 功能的线上质量负责**——包括"它答错了你怎么知道"。

### P7 · AI 应用架构师 / 技术专家（系统负责人）

**典型画像**：负责一条 AI 产品线或一个平台，能定义技术方案，能在多个约束（成本、延迟、质量、合规）之间做取舍。

| 项目 | 要求 |
|---|---|
| 交付 | 主导跨团队的系统设计，方案被采纳并落地 |
| 技术 | 能设计多模型网关、Agent 运行时、评测平台、知识库治理体系 |
| 取舍 | 能说清"为什么这里用长上下文不用 RAG""为什么这个场景不上 Agent" |
| 治理 | 建立成本账本、可观测体系、灰度与回滚机制、Prompt 版本管理 |
| 影响 | 定规范、定标准，影响 5 人以上团队的技术选择 |
| 前瞻 | 对模型能力演进有判断，能提前布局（如 MCP 生态、上下文工程） |

**红线能力**：**能做"不做什么"的决策**，并为决策的后果负责。

### P8 · 领域专家 / 技术负责人（方向定义者）

**典型画像**：定义公司在这个方向上的技术路线，能组织资源打硬仗，对外有影响力。

| 项目 | 要求 |
|---|---|
| 方向 | 定义 1–2 年的技术路线，能说服业务与老板投入 |
| 组织 | 搭建团队能力梯队，建立招聘与培养标准 |
| 业务 | 技术决策直接关联业务指标（收入/成本/留存） |
| 外部 | 有行业可见度（开源、专利、标准、技术分享） |
| 风险 | 能预判合规、安全、供应链风险并提前建防线 |

**红线能力**：**在没有标准答案的地方给出可执行的方向**。

## 三、能力项 × 职级矩阵（10 项）

这是本文最实用的部分：拿自己的实际经历，逐格对照。

| 能力项 | P5 | P6 | P7 | P8 |
|---|---|---|---|---|
| **1. LLM 调用与 Prompt** | 会写结构化 Prompt，懂 few-shot | 建立 Prompt 模板库 + 版本管理 + 灰度 | 设计 Prompt 治理体系与评测闭环 | 定义 Prompt 工程方法论 |
| **2. RAG 体系** | 能接向量库、跑通问答 | 会切分策略、混合检索、重排、评测 | 设计多租户知识库、ACL、增量更新 | 定义企业知识资产战略 |
| **3. Agent 架构** | 会用框架跑 ReAct | 能设计工具集、记忆、状态机、断点续跑 | 设计多智能体协作与工作流编排平台 | 定义 Agent 产品形态与边界 |
| **4. 评测与质量** | 会人工抽检 | 建评测集 + LLM-as-Judge + 回归门禁 | 建评测平台，指标与业务对齐 | 定义质量标准和行业基准 |
| **5. 性能与成本** | 知道 token 要省钱 | 会算单位成本，做缓存/裁剪/路由 | 设计成本模型与容量规划 | 成本结构成为商业模型一部分 |
| **6. 安全与合规** | 知道别把密钥写进代码 | 做输入隔离、输出护栏、权限校验 | 建安全基线、审计、红队机制 | 应对监管与合规审查 |
| **7. 数据与向量库** | 会 CRUD、会建索引 | 懂 HNSW/量化、分段与召回率权衡 | 设计数据管道与存储选型 | 定义数据资产治理 |
| **8. Java 后端基本功** | 会 Spring Boot、会用连接池 | 懂并发、JVM、MySQL 调优 | 设计高并发高可用架构 | 定义技术栈演进 |
| **9. 系统设计** | 能按模板画图 | 能做容量估算与故障域划分 | 能做多方案取舍与演进规划 | 定义架构原则 |
| **10. 影响与沉淀** | 写清文档 | 带 1–2 人、输出组件 | 定规范、跨团队推动 | 建团队、建标准、对外输出 |

**用法**：不要看"最高那一列"，看**你能连续稳定做到的最后一列**。中间有断档（比如 RAG 到 P7 但评测只有 P5），定级时按**最低的关键项**算——这就是为什么很多人"技术很猛但定级不高"。

## 四、晋升证据链：怎么证明"我到了下一级"

### 4.1 一个可复用的四段式

| 段落 | 内容 | 反例 |
|---|---|---|
| **问题** | 业务/技术问题 + 量化现状 | "我们做了个智能客服" |
| **判断** | 你为什么选这个方案，排除了什么 | "因为大家都用 RAG" |
| **动作** | 你个人做了什么（区分"我"和"我们"） | "团队完成了…" |
| **结果** | 量化指标 + 影响半径 | "效果不错，用户很满意" |

### 4.2 结果必须量化，四类指标

| 类型 | 例子 | 常见陷阱 |
|---|---|---|
| 质量 | 准确率 71%→86%，幻觉率 12%→3% | 用"感觉更好了"代替指标 |
| 成本 | 单次请求 ¥0.021→¥0.007，月省 4.2 万 | 只算 token 单价，不算重试与失败成本 |
| 效率 | 人工处理 30 分钟/单 → 3 分钟/单 | 没算人工复核成本 |
| 稳定性 | P99 从 8s→1.2s，429 率 6%→0.3% | 只报平均值 |

**最强证据是"对照"**：改前/改后、A 方案/B 方案、有评测/无评测。晋升评委最喜欢的句式是："上线前我们建了 200 条黄金集，准确率 A 方案 71%、B 方案 86%，选 B，线上抽检 91%。"

### 4.3 影响半径的三层证明

```
个人层：我写的代码/组件（PR、仓库、文档）
团队层：别人用我的东西（引用数、接入方数量、培训场次）
组织层：流程/标准因我而变（规范文档、评审机制、招聘标准）
```

P6 至少要有"团队层"，P7 至少要有"组织层"。这一条卡掉了大量"技术很强但影响力为零"的候选人。

## 五、Java 后端转 AI：定级怎么算

### 5.1 三种转岗路径与定级预期

| 路径 | 说明 | 定级预期 |
|---|---|---|
| **平级转**（同公司内部转岗） | 用现有信任 + 补齐 AI 能力 | 通常保级，6–12 个月后有机会晋升 |
| **跳槽转**（换公司做 AI 岗） | 需要证明 AI 生产经验 | 常见"降半级"或"同级但薪资持平" |
| **AI 加持不转岗**（在原岗做 AI 功能） | 阻力最小、证据最真实 | 最容易拿到"同级 + 高绩效" |

**最推荐的其实是第三条**：在你现在的公司，把一个真实业务问题用 AI 解决掉，拿到量化结果。这比任何课程证书都有说服力，而且不用承担转岗降级的风险。

### 5.2 能力迁移对照表

| Java 后端能力 | 迁移到 AI 应用开发后的价值 | 需要补的缺口 |
|---|---|---|
| 高并发/线程池/连接池 | 直接复用：LLM 调用就是慢 IO，池化思维一模一样 | 流式响应下的连接生命周期管理 |
| JVM 调优/GC | 中价值：向量化与本地推理仍吃内存 | 推理框架的显存/内存模型 |
| MySQL/索引/事务 | 高价值：元数据、会话、评测数据都要落库 | 向量库与混合检索 |
| 微服务/网关/限流熔断 | **最高价值**：LLM 网关就是网关 | 按 token 计量、429 语义 |
| 可观测性（Trace/Metrics） | 高价值：AI 应用最缺这个 | LLM 特有的 span（prompt/completion/usage） |
| 设计模式/架构 | 高价值：Agent 编排本质是状态机 + 策略 | Agent 范式（ReAct/Plan-Execute） |
| 单元测试/CI | 高价值：评测集就是 AI 的单元测试 | LLM-as-Judge、非确定性断言 |

一句话：**你的后端功底不是"要洗掉的包袱"，而是 AI 应用岗最稀缺的部分**——因为这个岗位 70% 的难度在工程，30% 在模型。

### 5.3 面试官怎么看你"没有 AI 生产经验"

他们真正担心的不是"你没用过 GPT-4"，而是这四件事：

1. 你不知道**怎么判断效果好坏**（没有评测意识）；
2. 你没处理过**非确定性**（把 LLM 当确定性函数用）；
3. 你不懂**成本失控**的后果（没见过账单）；
4. 你没做过**降级兜底**（模型挂了业务就挂了）。

对应的破局方式：**用一个真实项目把这四点全覆盖**。哪怕是你自己搭的、服务 50 个用户的小系统，只要你有评测集、有成本账、有降级方案、有线上数据，它就等价于"生产经验"。

## 六、定级面试的真实流程

| 轮次 | 考察点 | 通过标准 |
|---|---|---|
| 简历筛 | 有没有"AI + 量化结果" | 出现具体指标与个人贡献 |
| 技术面（1–2 轮） | 编码 + AI 基础 | 能写能跑，能解释 RAG/Agent 原理 |
| 项目深挖 | 你的项目到底多深 | 追问 5 层还能答（为什么这么切分？换方案会怎样？） |
| 系统设计 | 设计一个 AI 系统 | 能覆盖质量/成本/延迟/降级四个维度 |
| 定级面 / 交叉面 | 影响力与判断力 | 能说清"为什么不做某些事" |
| HC 校准 | 与其他候选人横向比 | 证据链完整度 |

**项目深挖最容易翻车的三个追问**：

1. "你的召回率是多少？怎么测的？" —— 答不出评测方法 = 直接掉级。
2. "如果模型换成便宜 10 倍的，你的方案要怎么改？" —— 考的是权衡能力。
3. "线上答错了，你怎么发现？多久发现？" —— 考的是工程闭环。

## 七、90 天举证计划（面向"想晋升/想转岗"）

| 周次 | 目标 | 产出（证据） |
|---|---|---|
| W1–W2 | 选定一个真实业务问题 | 问题定义文档 + 现状量化（基线指标） |
| W3–W4 | 建最小评测集 | 100–200 条黄金集 + 评分标准（含 LLM-as-Judge 脚本） |
| W5–W6 | 跑通基线方案 | 可运行的服务 + 基线准确率/成本/延迟三张表 |
| W7–W8 | 做一轮优化并对照 | A/B 对照报告（准确率、成本、P99 各一组数字） |
| W9–W10 | 上线与兜底 | 灰度方案、降级开关、告警规则、429 处理 |
| W11 | 沉淀 | 组件/文档/规范，至少 1 个其他团队接入 |
| W12 | 复盘与包装 | 四段式述职材料 + 一页架构图 + 数据看板 |

这套节奏的关键是 **W3–W4 的评测集**。没有它，后面所有"优化"都无法证明有效，你的述职就只能停留在"我做了个功能"——那是 P5 的语言。

## 八、定级失败的 7 个常见原因

1. **只讲技术不讲结果**——"我用了 RAG + 重排"，但说不清提升了什么。
2. **指标是拍的**——准确率没有评测集支撑，一问就露。
3. **区分不了"我"和"我们"**——评委无法判断你的个人贡献。
4. **没有失败案例**——只讲成功，说明你没真正踩过坑，深度可疑。
5. **成本意识为零**——AI 岗的必修课，答不出单位成本基本定不到 P6。
6. **把框架当能力**——会用 LangChain4j 不等于会设计 Agent，框架会换，设计能力不会。
7. **影响半径为 0**——东西做得再好，没有第二个人用，就只能定 P5。

## 九、面试高频追问（自我认知类）

**Q1：你怎么衡量一个 Agent 做得好不好？**

三层：**结果层**（任务完成率、答案准确率）、**过程层**（工具调用成功率、平均步数、无效循环率）、**工程层**（P99 延迟、单任务成本、失败可恢复率）。只有结果层会导致"为了准确率无限加步数"，成本爆炸。

**Q2：你的项目影响半径有多大？**

按"个人 → 团队 → 组织"回答，并给数字：接入方数量、日调用量、被引用次数、因你而改的规范。不要只说"我们团队"。

**Q3：如果让你重做一遍，你会改什么？**

这是考"判断力"的题。好答案会指向**架构决策**（比如"当初应该先建评测集再写代码""不该上 Agent，规则引擎就够了"），而不是"我会多写点测试"。

**Q4：AI 领域变化这么快，你怎么保证不过时？**

给出机制而不是口号：跟踪哪些源（论文/官方 changelog/开源仓库）、怎么验证（一周一个小 spike）、怎么沉淀（写成内部文档/组件）。**能说出"我上个月验证了 X，结论是不适合我们，因为 Y"的人，比说"我一直在学习"的人可信 10 倍。**

**Q5：你觉得自己现在是什么级别？为什么？**

用本文的矩阵回答："按 10 项能力，我在 RAG/Agent/工程化上稳定在 P6，评测体系到了 P6 上限但还没到 P7（没有跨团队评测平台），影响半径目前是团队层（3 个接入方），所以我认为是 P6 偏上。"

## 十、总结

回到开头那个"学完一堆课却被定到初级"的人：他的问题不是学得少，而是**没有把能力翻译成职级语言**。

三句话收尾：

1. **职级看半径，不看技能清单**。同样的 RAG，服务 200 篇文档和服务 200 万篇多租户文档，是两个级别。
2. **证据链的核心是"对照 + 量化 + 个人贡献"**。没有评测集的优化，在评委眼里等于没发生。
3. **Java 背景是你的资产**。AI 应用岗 70% 的难度在工程（并发、稳定性、可观测、成本），这恰好是你已经训练过的东西——你要补的是评测意识、非确定性思维和上下文工程。

如果你正在准备转岗或晋升，建议从今天开始只做一件事：**找一个真实问题，建一个评测集，跑出第一组对照数字。** 这一个动作，比再刷十篇教程更能改变你的定级结果。

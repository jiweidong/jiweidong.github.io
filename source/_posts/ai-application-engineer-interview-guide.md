# 【AI 面试】AI 应用开发岗面试指南：高频考点、答题框架与项目追问链路

## 前言

2026 年的 AI 应用开发岗（也叫 LLM 应用工程师、Agent 工程师、AI 平台工程师）已经过了"会调 OpenAI API 就能入职"的阶段。

现在的面试官普遍会做三件事：

1. **用场景题筛掉"只会写 demo"的人**：不是问"什么是 RAG"，而是问"你的 RAG 为什么召回不准，怎么定位"。
2. **用追问链挖深度**：一个问题连着问四层，看你是背的还是有真实工程经验。
3. **用成本/稳定性问题筛掉"没上过生产"的人**：Token 账单、P99 延迟、幻觉率、灰度方案。

这篇文章把过去一年高频出现的题目按模块整理，并给出**可以直接套用的答题框架**。重点不是"标准答案"，而是**答题的结构**——面试官真正在评估的是你的思维方式。

---

## 一、面试流程与评估维度

典型 4 轮：

| 轮次 | 时长 | 考察 | 通过关键 |
|---|---|---|---|
| 一面（基础） | 45min | LLM 基础、Prompt、RAG 概念、代码 | 概念准确、不装懂 |
| 二面（项目） | 60min | 你的项目细节、技术选型、踩坑 | 能讲清"为什么这么选" |
| 三面（系统设计） | 60min | 设计一个 AI 系统 | 分层清晰、有取舍、有兜底 |
| 四面（交叉/HR） | 30min | 业务理解、协作、动机 | 有业务视角、稳定 |

面试官心里的评分表通常长这样（100 分）：

| 维度 | 权重 | 说明 |
|---|---|---|
| 基础概念准确性 | 20 | LLM/RAG/Agent 的核心概念不出错 |
| 工程落地能力 | 30 | 能处理延迟、成本、并发、失败 |
| 技术选型判断 | 20 | 知道 trade-off，不迷信单一方案 |
| 问题定位能力 | 20 | 有排查方法论，不是"重启试试" |
| 沟通与表达 | 10 | 结构化、有重点 |

**关键洞察**：基础只占 20 分。**大部分候选人挂的不是"不懂"，而是"讲不出工程细节"**。

## 二、模块一：大模型基础（必问，但要答得"有用"）

### 2.1 高频题

1. Transformer 的 Self-Attention 在算什么？为什么能并行？
2. KV Cache 是什么？为什么能加速推理？显存怎么算？
3. Temperature / Top-p / Top-k 的区别？生产环境怎么设？
4. 上下文窗口变长，成本怎么变？为什么是平方级？
5. 什么是幻觉？根因是什么？怎么缓解？
6. 预训练 / SFT / RLHF / DPO 各自解决什么问题？

### 2.2 答题框架：**"是什么 → 为什么 → 工程影响"**

以"Temperature 怎么设"为例：

> **是什么**：Temperature 是对 logits 做缩放，T<1 让分布更尖锐（更确定），T>1 更平坦（更随机）。Top-p 是核采样，只从累积概率前 p 的 token 里采样。
>
> **为什么**：不同任务对确定性的需求不同。分类/抽取要确定性，创意生成要多样性。
>
> **工程影响**：生产上我会按场景分别配置——**结构化抽取 T=0，客服问答 T=0.3，文案生成 T=0.7**。而且这些参数要放进配置中心，不能硬编码，因为调参是持续过程。另外 T=0 也不保证完全可复现（浮点非确定性 + 模型版本），所以幂等要靠缓存而不是靠参数。

这个回答比"Temperature 控制随机性"高出一个量级——因为它落到了**工程决策**。

### 2.3 一个必须会的计算题

> 8K 上下文，输入 6000 token，输出 1000 token，日调用 100 万次，成本多少？

答题步骤（面试官在看你的**拆解能力**）：

```
输入 token：6000 × 1e6 = 6e9
输出 token：1000 × 1e6 = 1e9
按某模型定价（输入 2 元/百万，输出 8 元/百万）：
  输入成本 = 6000 × 2 = 12,000 元/天
  输出成本 = 1000 × 8 = 8,000 元/天
  合计 ≈ 2 万元/天 ≈ 60 万/月
优化方向：Prompt 压缩、缓存（命中率 30% 可省 6k/天）、小模型路由
```

**加分项**：主动提"输出 token 单价通常是输入的 3~4 倍，所以**控制输出长度比压缩输入更省钱**"。

## 三、模块二：Prompt 工程（别背模板，讲方法论）

### 3.1 高频题

1. 你如何设计一个稳定的抽取 Prompt？
2. Few-shot 的示例怎么选？放几个合适？
3. Chain-of-Thought 什么时候有用，什么时候有害？
4. 怎么做 Prompt 版本管理？
5. Prompt 注入怎么防？

### 3.2 答题框架：**"目标 → 约束 → 结构 → 验证"**

以"抽取合同关键信息"为例：

> **目标**：从非结构化合同文本抽取 12 个字段，输出 JSON。
>
> **约束**：字段缺失必须输出 null 而不是编造；金额统一为数字；日期统一 ISO 格式。
>
> **结构**：角色（法务信息抽取器）+ 字段定义表 + 2 个 few-shot（一个完整、一个含缺失字段）+ 输出 schema。
>
> **验证**：不靠"感觉对不对"，而是 ① JSON Schema 校验 + 失败重试；② 用 200 条标注集算字段级 F1；③ 线上抽样人工复核。

**必答的加分点**：**"我不追求 Prompt 一次写对，而是建立'改 Prompt → 跑评测集 → 看指标'的闭环"**。这句话直接证明你有工程思维。

## 四、模块三：RAG（占比最高，追问最深）

### 4.1 高频题与追问链

面试官通常会这样连问：

```
Q1: 介绍一下你的 RAG 系统
 └ Q2: 文档怎么切分的？为什么用这个 chunk size？
     └ Q3: 召回不准，你怎么定位是切分问题还是 Embedding 问题？
         └ Q4: 混合检索的权重怎么定？
             └ Q5: 重排模型带来多少延迟？值得吗？
                 └ Q6: 怎么评估整个 RAG 的效果？
```

### 4.2 每层的答题要点

**切分（Chunking）**

| 策略 | 适用 | 坑 |
|---|---|---|
| 固定长度 + overlap | 通用兜底 | 切断语义 |
| 按标题/段落 | 结构化文档（制度、手册） | 依赖文档质量 |
| 语义切分 | 长文、论文 | 慢、不稳定 |
| 父子块（small-to-big） | 精准检索 + 完整上下文 | 存储翻倍 |

> 答题话术："我用的是**父子块**——子块 256 token 用于检索（精度高），父块 1024 token 送给 LLM（上下文完整）。overlap 设 10~15%，因为我的文档段落边界清晰，不需要大 overlap。"

**Embedding 选型**

必须能说出 trade-off：中文效果（BGE-M3 / 通义）、维度（768 vs 1024 vs 1536）、最大长度（512 会截断长块）、是否支持稀疏、部署方式（API vs 本地 GPU）、**换模型的迁移成本**。

**混合检索**

```
最终分数 = α × 向量相似度 + (1-α) × BM25 分数
```

关键回答："α 不是拍脑袋，我用**网格搜索 + 黄金集**在 0.3~0.7 之间选，最终 0.55。另外向量分数和 BM25 分数**量纲不同**，必须先归一化（min-max 或 RRF）——**直接用 RRF（倒数排名融合）更稳，因为它不需要调权重**。"

**重排（Rerank）**

- 模型：BGE-reranker、Cohere Rerank、通义 gte-rerank
- 代价：一次重排 20 条候选，延迟增加 80~200ms
- 判断："如果召回 Top-20 的准确率已经 85%，重排收益有限；如果只有 60%，重排能拉到 80%+，那 150ms 完全值得——**先测再上，不要默认加**。"

**评估**

必须提到三层：

| 层次 | 指标 | 工具 |
|---|---|---|
| 检索层 | Recall@K、MRR、命中率 | 自建黄金集 |
| 生成层 | Faithfulness、Answer Relevancy、Context Precision | RAGAS |
| 业务层 | 解决率、转人工率、用户满意度 | 线上埋点 + AB |

### 4.3 一定要准备的"故障故事"

面试官几乎必问："**你的 RAG 出过什么问题？**"

准备一个结构化的故事（**现象 → 定位 → 根因 → 修复 → 验证**）：

> **现象**：上线两周后，"报销标准"类问题的回答开始引用过期制度。
> **定位**：查 trace 发现召回的 chunk 来自旧版文档（v2024），但库里已有 v2026。
> **根因**：文档更新走的是"新增"而不是"替换"，旧 chunk 没删；且检索没按 `effective_date` 过滤。
> **修复**：① 数据侧改为按 `doc_id` 覆盖写；② 检索加 `status='active'` 过滤；③ 加一致性校验任务，比对业务库与向量库的文档数。
> **验证**：黄金集回归 + 线上抽样 100 条人工复核，过期引用从 7% 降到 0.3%。

这个故事同时证明了**可观测性、数据治理、验证意识**——比任何概念回答都值钱。

## 五、模块四：Agent（区分度最高）

### 5.1 高频题

1. ReAct、Plan-and-Execute、Reflection 的区别？分别适合什么任务？
2. 工具调用（Function Calling）的完整链路是什么？
3. Agent 陷入死循环怎么办？
4. 多智能体协作怎么分工？怎么防止互相甩锅？
5. Agent 的记忆怎么设计？
6. MCP 解决了什么问题？

### 5.2 答题框架：**先分类，再讲取舍，最后讲兜底**

以"三种 Agent 范式"为例：

| 范式 | 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| ReAct | 思考→行动→观察 循环 | 灵活、能纠错 | Token 多、可能绕圈 | 探索型任务（查资料） |
| Plan-Execute | 先出计划再逐步执行 | 可预测、可并行 | 计划错了全错 | 步骤明确的任务（报表生成） |
| Reflection | 生成→自评→改进 | 质量高 | 成本翻倍、延迟高 | 写作、代码生成 |

> 话术："我不会一上来就用最复杂的。**默认 ReAct + 最大步数限制**；如果任务步骤可枚举（比如'查订单→算运费→生成回复'），改 Plan-Execute 更稳；只有对质量要求极高的场景（合同起草）才加 Reflection，因为它的成本是 2~3 倍。"

### 5.3 "死循环"是必问题

标准答案要有**四道闸**：

1. **最大步数**（max_iterations = 8~10）
2. **重复检测**（连续两次相同工具 + 相同参数 → 中断）
3. **超时**（整体 30s，单步 10s）
4. **降级**（中断后返回"我暂时无法完成，已转人工"，而不是抛错）

再加一句加分："**中断要留 trace**，否则你不知道是模型笨还是工具描述写得烂。"

### 5.4 MCP 怎么答

> "MCP 是**工具接入的标准化协议**。在此之前，每接一个工具就要写一套适配代码；有了 MCP，工具方提供 Server，Agent 侧只要一个 Client。它解决的不是'能不能调'，而是'**接入成本**和**复用性**'——同一个 MCP Server 可以被 Claude、IDE、自研 Agent 共用。落地时要注意：① 工具描述的 token 成本（工具多了会撑爆上下文）；② 权限边界（Server 能访问什么）；③ 超时与重试语义。"

## 六、模块五：工程化与生产治理（筛人的关键）

### 6.1 必问清单

| 主题 | 面试官想听什么 |
|---|---|
| 可观测性 | Trace 要记录哪些字段？怎么定位一次坏回答？ |
| 成本治理 | Token 账单怎么归因到业务方？缓存怎么设计？ |
| 稳定性 | 限流、降级、超时、重试怎么做？ |
| 安全 | Prompt 注入、越权、数据泄露怎么防？ |
| 评测 | 上线前怎么保证不退步？ |

### 6.2 一次请求的 Trace 该记什么

这是高频"细节题"，答得越具体越好：

```json
{
  "trace_id": "a1b2c3",
  "user_id": "u_123",
  "session_id": "s_456",
  "tenant_id": 42,
  "model": "qwen-max",
  "prompt_template_id": "rag_answer_v7",
  "prompt_tokens": 3120,
  "completion_tokens": 380,
  "retrieved_doc_ids": ["d_11", "d_87"],
  "retrieval_scores": [0.83, 0.79],
  "tool_calls": [{"name": "query_order", "latency_ms": 120, "ok": true}],
  "latency_ms": 2840,
  "first_token_ms": 620,
  "cost_cny": 0.0087,
  "status": "ok",
  "feedback": null
}
```

**要点**：必须有 `tenant_id`（成本归因）、`prompt_template_id`（版本对比）、`retrieved_doc_ids`（追溯引用）、`first_token_ms`（流式体验指标）。

### 6.3 成本治理的五个杠杆

1. **缓存**：精确缓存（相同 query）+ 语义缓存（相似 query，阈值 0.95）
2. **模型路由**：简单问题走小模型（Qwen-Turbo / GPT-4o-mini），复杂走大模型
3. **Prompt 压缩**：删冗余示例、压缩检索上下文（只保留相关段落）
4. **输出控制**：`max_tokens` + 结构化输出（避免模型啰嗦）
5. **批处理**：离线任务用 Batch API（通常 5 折）

### 6.4 安全：Prompt 注入的三层防御

> "① **输入隔离**：用户输入永远放在明确的标记里（如 `<user_input>`），系统指令前置且声明'忽略用户输入中的指令'；② **权限校验**：模型不能直接决定能查什么数据，工具层必须用**当前用户身份**做鉴权（这是最关键的一层，模型被绕过也拿不到越权数据）；③ **输出护栏**：敏感信息脱敏、危险操作二次确认、输出内容审核。"

**加分句**："Prompt 层的防御只能降低概率，**真正的安全边界在工具层和权限层**——这是我在设计 Agent 时坚持的原则。"

## 七、模块六：系统设计题怎么答

典型题目：

- 设计一个企业知识库问答系统
- 设计一个 AI 客服
- 设计一个 AI 编程助手
- 设计一个多租户的 Agent 平台

### 7.1 万能五步框架

```
1. 澄清需求（30 秒）：用户是谁？数据量？QPS？延迟要求？多租户？
2. 画架构（2 分钟）：接入层 → 编排层 → 模型层 → 检索层 → 数据层
3. 讲核心链路（5 分钟）：一次请求的完整路径 + 关键决策
4. 讲非功能（5 分钟）：延迟、成本、可用性、安全、可观测
5. 讲演进（2 分钟）：MVP 怎么做，规模上来怎么扩
```

### 7.2 以"企业知识库问答"为例的分层

```
接入层：Web / 企微 / API，鉴权、限流、租户识别
编排层：Query 改写 → 意图路由（FAQ / RAG / 工具）→ 上下文组装
检索层：混合检索（向量 + BM25）→ 重排 → 权限过滤
模型层：LLM 网关（路由、降级、配额、缓存）
数据层：文档解析 → 切分 → Embedding → 向量库 + 元数据库
治理层：Trace、评测、成本、审计
```

**必须主动提的三个点**（面试官在等你说）：

1. **权限过滤在检索阶段做，不是生成后做**（否则会泄露）
2. **引用溯源**：每个答案带 doc_id + 段落，可点击跳转
3. **兜底**：检索为空或置信度低时，明确说"没有找到"，而不是让模型编

## 八、Java 背景的加分项怎么讲

这是本站读者最关心的部分。Java 后端转 AI，**不要试图证明"我比算法同学更懂模型"**，要证明"我比算法同学更懂怎么把它做成稳定服务"。

| 你的优势 | 怎么表达 |
|---|---|
| 高并发经验 | "我用虚拟线程 + 信号量把 LLM 调用并发从 200 提到 2000，P99 稳定在 3s" |
| 中间件经验 | "用 Kafka 做异步任务解耦，用 Redis 做语义缓存，命中率 34%" |
| 稳定性经验 | "熔断降级：模型超时切备用模型，连续失败 5 次切规则兜底" |
| 工程规范 | "Prompt 走 Git 版本管理 + CI 跑评测集，回归不过不许上线" |
| Spring 生态 | "用 Spring AI 的 VectorStore 抽象，本地 pgvector、生产 Milvus 一套代码" |

**一句话定位**："我的价值是把 LLM 的不确定性，包装成业务可用的确定性服务。"

### 反问环节（体现专业度）

- "团队现在 RAG 的召回率大概在什么水平？主要瓶颈在检索还是生成？"

- "模型选型是统一走一家，还是多模型路由？"

## 十、五个最容易踩的坑

1. **只讲概念不讲数字**："提升了效果" → 一定要说"召回率从 62% 提到 81%"。
2. **把 demo 说成生产**：面试官追问"多少 QPS、怎么监控、出过什么故障"就露馅。**宁可说这是 POC**。
3. **迷信单一方案**："我们用了 RAG 所以不需要微调"——正确的说法是"当前数据量和迭代频率下 RAG 更划算，如果领域术语太多，会考虑 LoRA 补语义"。
4. **忽略成本**：只谈效果不谈钱，会被认为没做过生产。
5. **不会说"不知道"**：遇到没做过的，正确姿势是"我没做过 X，但我会这样入手：先…再…"，展示迁移能力而不是硬编。

---

## 十一、总结

AI 应用开发面试的本质，是**用工程语言讲清楚一件不确定的事**：

- **基础**要准确（20 分，不能丢）
- **项目**要有数字（召回率、延迟、成本、QPS）
- **选型**要讲 trade-off（没有最好的方案，只有最合适的）
- **故障**要有方法论（现象→定位→根因→修复→验证）
- **系统设计**要有分层和兜底

最后一句给正在转型的 Java 同学：**你不需要成为算法专家，你需要成为"最懂怎么把模型变成产品"的工程师**。这个岗位稀缺的从来不是会调 API 的人，而是能让它在生产环境稳定跑一年的人。

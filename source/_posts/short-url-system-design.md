# 【系统设计】短链接系统架构设计：从发号器到跳转的完整方案

## 面试官：设计一个短链接系统，说下你的思路？

短链接是系统设计面试的"经典题库题"（和秒杀、支付、消息推送并列）。它麻雀虽小五脏俱全：**发号算法、存储设计、缓存、高并发跳转、数据统计**全都涉及。而且它真实存在于你身边的每个场景——微博分享、营销短信、二维码里那一串 `t.cn/xxxxx`。

本文给出一个可以直接"背"进面试的完整设计方案。

---

## 一、需求分析

### 功能需求
1. **生成**：输入长链接，返回短链接（如 `https://s.dg.com/Ab3xY9`）；
2. **跳转**：访问短链接，302 重定向到长链接；
3. **统计**：每个短链接的访问次数、来源、时间分布（加分项）；
4. **管理**：可自定义短码、可设置过期时间（加分项）。

### 非功能需求（关键！）
- **高并发**：跳转是读多写少，QPS 可能极高（营销活动时秒级上万）；
- **高可用**：跳转失败 = 用户进不了页面，可用性要求 99.99%；
- **低延迟**：跳转链路要快，缓存命中率要足够高。

### 容量估算（背下来，面试很加分）
- 每天新增短链接 1000 万 → 每年约 36.5 亿条；
- 短码长度：用 62 进制（a-zA-Z0-9），6 位可表示 `62^6 ≈ 568 亿`，7 位 `62^7 ≈ 3.5 万亿`。**6 位短码足够用**；
- 存储：每条记录约 200B，一年数据约 70GB，单库 MySQL 完全扛得住（加上索引约 100GB+）。

## 二、总体架构

```
                     ┌──────────────┐
   用户生成短链接 ──▶ │   发号服务    │ ──▶ 全局发号器（DB/Redis）
                     └──────────────┘        │
                                            ▼
                     ┌──────────────┐   ┌──────────┐
   用户访问短链接 ──▶ │   跳转服务    │ ─▶│  Redis   │ 缓存短码→长链接
                     └──────────────┘   └──────────┘
                           │ 未命中         │ 命中即 302
                           ▼                │
                     ┌──────────────┐       │
                     │    MySQL     │ ◀─────┘  (读DB回源并回填缓存)
                     │ (短码→长链接) │
                     └──────────────┘
                           │ 异步
                           ▼
                     ┌──────────────┐
                     │  统计服务(MQ) │ 访问日志异步落库
                     └──────────────┘
```

核心链路就两条：**写路径（生成）** 和 **读路径（跳转）**。

---

## 三、核心难点 1：短码生成（发号器设计）

这是短链接系统最核心的设计决策，有四种主流方案：

### 方案 A：自增 ID + 62 进制转换（推荐）
用数据库自增 ID（或发号器）生成一个全局唯一的十进制数，再转成 62 进制字符串作为短码。

```java
public String toBase62(long num) {
    char[] chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();
    StringBuilder sb = new StringBuilder();
    while (num > 0) {
        sb.append(chars[(int) (num % 62)]);
        num /= 62;
    }
    return sb.reverse().toString();
}
```

优点：**无碰撞、短码可控、可反解出 ID**（短码转回数字即可定位记录）。缺点：依赖发号器的高可用。

**发号器实现**：
- 单表自增：`INSERT ... 返回自增 ID`，简单但 DB 是瓶颈；
- 号段模式：一次取一批（如 10000 个号），内存里发完再取——**发号与业务解耦，吞吐极高**（美团 Leaf 就是这个思路）；
- Redis INCR：`INCR short_id`，快但要注意持久化丢失问题（可配合 DB 兜底）。

### 方案 B：随机生成 + 去重校验
随机生成 6 位短码，查重，冲突则重试。缺点：冲突率高（数据量大时），每次都要查 DB，不推荐作为主方案。

### 方案 C：MD5/哈希截取
对长链接 MD5，取前 6~8 位。缺点：**碰撞概率高**，且相同长链接可能生成不同短码（除非加缓存去重）。一般只用于"无需唯一"的场景。

### 方案 D：预生成短码池
提前批量生成短码存入池中，生成时从池中取。适用于"短码可预期、离线批量"的场景，实时性差一些。

**面试推荐话术**："主方案用 **DB 号段模式发号 + 62 进制编码**，保证唯一性和高性能；同时用 **长链接 MD5 做唯一索引**，相同长链接复用同一个短码（省存储、防重复）"。

## 四、核心难点 2：存储设计

### 表结构

```sql
CREATE TABLE short_url (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    short_code  VARCHAR(10)  NOT NULL COMMENT '短码（62进制）',
    long_url    VARCHAR(2048) NOT NULL COMMENT '原始长链接',
    url_md5     CHAR(32)     NOT NULL COMMENT '长链接MD5，用于去重',
    user_id     BIGINT       DEFAULT NULL,
    expire_time DATETIME     DEFAULT NULL COMMENT '过期时间',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_short_code (short_code),
    UNIQUE KEY uk_url_md5 (url_md5)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：
- `short_code` 唯一索引：跳转查询走主键级索引，**单条记录查询 O(1)**；
- `url_md5` 唯一索引：长链接去重（相同长链接直接复用短码）；
- 过期数据：定时任务 + 按 `expire_time` 分批删除（或标记失效）。

### 缓存设计（读路径性能关键）

```java
// 跳转服务伪代码：Cache Aside 模式
public String getLongUrl(String shortCode) {
    // 1. 查缓存
    String longUrl = redis.get("short:" + shortCode);
    if (longUrl != null) return longUrl;
    // 2. 缓存未命中，查 DB
    ShortUrl url = mapper.selectByShortCode(shortCode);
    if (url == null) {
        // 3. 防止缓存穿透：空值也缓存，设置短过期
        redis.set("short:" + shortCode, "", 60);
        return null;
    }
    // 4. 回填缓存（热点数据 TTL 可设置较长）
    redis.set("short:" + shortCode, url.getLongUrl(), 7 * 24 * 3600);
    return url.getLongUrl();
}
```

**缓存三兄弟防护**（面试必答）：
- **穿透**：不存在的短码直接打 DB → 空值缓存 + **布隆过滤器**（生成短码时写入过滤器，跳转前先查过滤器）；
- **击穿**：某个热点短码缓存失效瞬间大量请求打 DB → 互斥锁重建缓存（`SETNX`）；
- **雪崩**：大量短码同时过期 → TTL 加随机抖动（如 7 天 ± 随机 1~2 天）。

## 五、核心难点 3：跳转（301 还是 302？）

这是短链接系统的一个经典细节题：

| 状态码 | 含义 | 浏览器行为 | 适用 |
|--------|------|-----------|------|
| 301 | 永久重定向 | 浏览器**缓存**跳转结果，后续直接访问长链接 | 不关心统计（跳转不再经过短链服务） |
| 302 | 临时重定向 | 每次都请求短链服务再跳转 | **需要统计每次点击** |

**答案**：需要统计点击量的短链接系统必须用 **302**。用 301 的话，第二次访问浏览器直接跳过短链服务，统计就丢了。面试时能说出"301 省一次请求但丢统计，302 多一次请求但统计完整，我们选 302"就稳了。

跳转响应：

```http
HTTP/1.1 302 Found
Location: https://www.example.com/very/long/url/...
```

## 六、数据统计（加分项）

访问日志异步化：跳转服务只做"写一条日志到 MQ"，不阻塞主流程。

```
短链访问 → 跳转服务（302）→ 同时发消息到 Kafka/RabbitMQ
                              → 消费者聚合 → 落库/写入 ClickHouse
                              → 定时汇总：PV/UV、来源、地域、时间分布
```

UV 去重可以用 Redis HyperLogLog（`PFADD`/`PFCOUNT`），内存占用极小（12KB 存 2^64 个去重值）。

---

## 七、高可用与扩展

1. **跳转服务无状态化**：多实例水平扩展，前面挂 LB；
2. **Redis 集群**：缓存分片，热点短码加本地缓存（Caffeine）兜底；
3. **发号器高可用**：号段模式 + 多 DB 节点（每个节点不同步长，如 A 节点发 1,3,5，B 节点发 2,4,6，避免重复）；
4. **冷热分离**：近期数据在 MySQL，历史数据归档到冷存储（Tablestore/HDFS）；
5. **安全防护**：短码暴力遍历 → 布隆过滤器 + 限流；恶意长链接（钓鱼）→ 加白名单校验。

## 八、面试官连环追问

**Q1：短码会不会重复？**
不会。用发号器生成的 ID 全局唯一，62 进制转换是一一映射，天然无碰撞。随机方案才有碰撞问题。

**Q2：6 位短码够用吗？**
`62^6 ≈ 568 亿`，按每天 1000 万新增可以用 15 年+。不够了扩到 7 位即可（`62^7 ≈ 3.5 万亿`），**扩容只需改编码长度，无需迁移数据**（旧的 6 位短码仍有效，新短码变长）。

**Q3：Redis 挂了怎么办？**
跳转服务降级直查 MySQL（DB 单条主键查询本身很快，QPS 几千没问题）；缓存重建时注意防击穿。**Redis 是加速层不是可靠性依赖，DB 才是最终兜底**。

**Q4：相同长链接会生成不同短码吗？**
取决于设计。加了 `url_md5` 唯一索引后，相同长链接复用同一短码——省存储、省发号。但注意：不同用户分享同一链接想要独立统计时，就不能复用（此时去掉 md5 唯一约束）。

**Q5：怎么防止短码被恶意刷量（攻击统计）？**
限制单 IP 访问频率（限流）、短码加校验位、非公开短码加访问鉴权（如短信验证码场景）。

---

## 九、总结

短链接系统的设计套路一句话概括：**发号器保唯一，62 进制压缩长度，MySQL 存映射，Redis 扛读流量，302 保统计，MQ 异步做分析**。

| 模块 | 核心方案 |
|------|----------|
| 短码生成 | DB 号段发号 + 62 进制编码 |
| 存储 | MySQL（short_code / url_md5 双唯一索引） |
| 读加速 | Redis Cache Aside + 布隆过滤器 |
| 跳转 | 302（保留统计） |
| 统计 | MQ 异步 + HLL 去重 UV |
| 高可用 | 无状态服务 + 发号器多节点 + 冷热分离 |

面试时按"需求 → 容量 → 架构图 → 发号 → 存储缓存 → 跳转细节 → 统计 → 高可用"的顺序完整输出，这道系统设计题就是你的加分题。

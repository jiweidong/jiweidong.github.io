# 【MySQL 原理】MySQL 优化器深度解析：从统计信息、基数估算到执行计划选择的决策逻辑

## 面试官：为什么同样的 SQL，有时候走索引有时候全表扫描？优化器是怎么做决定的？

很多人会把 SQL 慢归咎于「没建索引」，但很多时候索引建了、SQL 却没走 —— 因为 **MySQL 优化器基于成本模型做选择，而成本估算依赖统计信息**。理解优化器，是理解 EXPLAIN 里 `rows`、`type`、`key` 这些字段背后逻辑的钥匙。

## 一、一条 SQL 的完整旅程

```
SQL 语句
  → 连接器（鉴权、建立连接）
  → 分析器（词法/语法分析，生成语法树）
  → 优化器（决定执行计划：走哪个索引、表连接顺序）
  → 执行器（按计划调用存储引擎 API，返回结果）
```

**优化器是「决策者」**：它的输入是语法树 + 统计信息，输出是执行计划。它可能做出错误决策，理解它才能干预它。

## 二、优化器的工作内容

1. **选择索引**：多个候选索引（主键、普通索引、联合索引）选哪个？可能全表扫描更优；
2. **决定表连接顺序**：多表 JOIN 时，谁是驱动表、谁是被驱动表；
3. **选择执行算法**：嵌套循环（NLJ）、块嵌套循环（BNL）、Hash Join（8.0.18+）；
4. **子查询优化**：转 semi-join、物化等；
5. **其他重写**：条件化简、常量传播、`ORDER BY` 利用索引排序、`DISTINCT` 优化等。

## 三、成本模型：优化器的一切决策都看「钱」

MySQL 优化器为每个候选执行计划估算一个**总成本**，选成本最小的。成本由两部分组成：

```
总成本 = IO 成本（读取数据页） + CPU 成本（比较、计算）
```

具体数字（`mysql.server_cost` / `mysql.engine_cost` 表可查可改）：

| 成本项 | 默认值 | 含义 |
|--------|--------|------|
| row_evaluate_cost | 0.2 | 每行比较/计算成本 |
| io_block_read_cost | 1.0 | 读取一个数据页的成本 |
| memory_block_read_cost | 0.25 | 从内存缓冲池读一页（便宜） |
| 索引扫描成本 | 低 | 扫描索引页比扫描数据页便宜 |

**关键点**：优化器不知道真实数据分布，它只能**估算**。估算的依据是统计信息，而统计信息不一定准 —— 这就是一切「优化器选错」的根源。

## 四、统计信息与基数（Cardinality）

### 4.1 什么是基数？

`Cardinality` = 索引中**不同值的个数**。基数是估算「扫描多少行」的核心输入：

- 基数 ≈ 行数 → 索引区分度低（比如性别字段只有 2 个值），优化器倾向于不用这个索引；
- 基数远小于行数 → 区分度高，适合建索引。

EXPLAIN 里的 `rows` 字段，就是优化器基于基数估算出的「预计扫描行数」——注意是**估算值，不是真实值**。

### 4.2 InnoDB 怎么算基数？

InnoDB 不可能扫描全表去数不同值，它用**采样**：

- `innodb_stats_persistent=ON`（8.0 默认）：采样 20 个（`innodb_stats_persistent_sample_pages`）B+ 树**叶子节点**，统计每个叶子页上不同值的个数，再推算整体基数；
- 采样有随机性 → **统计信息天然可能不准**，数据分布变化后还会过期；
- 什么时候更新统计信息：`ANALYZE TABLE`、表数据量变化超过 1/16 或 20 亿行阈值时自动触发（`innodb_stats_auto_recalc`）。

### 4.3 统计信息不准会怎样？

```
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
-- type: ref, rows: 50000  （实际只有 50 行）
```

基数被高估 1000 倍 → 优化器以为扫 5 万行很贵 → 可能放弃这个索引。**解法**：

```sql
ANALYZE TABLE orders;          -- 手动刷新统计信息（生产可执行，开销小）
SHOW INDEX FROM orders;        -- 查看 Cardinality 字段
```

## 五、经典案例：优化器为什么选错索引？

### 案例：两列查询，一列区分度高

```sql
-- 索引 idx_a(a)，idx_b(b)，两张索引的基数都正常
SELECT * FROM t WHERE a > 100 AND b = 5;
```

优化器会分别估算「走 idx_a 扫多少行」和「走 idx_b 扫多少行」，选成本低的。但如果 `b=5` 的数据恰好**集中在某个数据页**（局部性极好），估算 1000 行、实际只读 1 页，真实成本远低于估算 —— 优化器就「选错了」。

### 案例：深分页的索引选择陷阱

```sql
SELECT * FROM t ORDER BY create_time LIMIT 100000, 10;
```

优化器可能因为 `ORDER BY create_time` 直接选 create_time 索引做索引排序，但 LIMIT 偏移 10 万意味着要**扫描并丢弃 10 万行** —— 这时候全表扫描 + filesort 可能反而更快。经典解法是**延迟关联**：

```sql
SELECT t.* FROM t
JOIN (SELECT id FROM t ORDER BY create_time LIMIT 100000, 10) tmp
ON t.id = tmp.id;
```

先只查主键（走索引、不回表），再按主键回表取整行。

## 六、索引失效场景的优化器视角

很多「索引失效」其实不是失效，而是**优化器认为走索引不划算**：

| 场景 | 真正原因 | 优化器视角 |
|------|---------|-----------|
| 隐式类型转换 | 索引列是字符串，条件传数字 | 函数作用于索引列 → 无法走索引（8.0 有转换但仍有开销） |
| 对索引列做函数/运算 | `WHERE DATE(create_time)='2026-08-31'` | 索引列被函数包裹 → 无法二分定位 |
| `LIKE '%xxx'` | 前导通配符 | 无法利用 B+ 树有序性 |
| 联合索引不满足最左前缀 | 跳过第一列 | B+ 树第一层就无法定位 |
| 优化器放弃 | 估算全表扫描更便宜 | **`rows` 估算小 + 回表成本高** → 走全表 |

> 注意最后一个：有时候 `EXPLAIN` 显示 `type=ALL` 但 SQL 并不慢，就是优化器判断全表扫描更快（小表、或用不上索引排序）。**别一看全表扫描就加索引，先看 rows 估算和实际耗时**。

## 七、干预优化器的手段

### 7.1 直方图（8.0 新特性，强烈推荐）

基数只能描述「有多少个不同值」，描述不了**分布**。比如性别字段基数=2，但 99% 是男 —— 优化器不知道。直方图解决这个问题：

```sql
ANALYZE TABLE t UPDATE HISTOGRAM ON gender, status WITH 100 BUCKETS;
SHOW HISTOGRAM ON t\G
```

直方图记录了字段的**值分布**，让优化器能精确估算「等值条件命中多少行」。8.0 里遇到「字段基数低但分布极不均匀导致选错索引」，先建直方图，比 force index 优雅得多。

### 7.2 其他手段（按优先级）

1. **刷新统计信息**：`ANALYZE TABLE`（先做这个，最安全）；
2. **直方图**：`ANALYZE TABLE ... UPDATE HISTOGRAM ON ...`；
3. **改写 SQL**：延迟关联、拆 SQL、加等值条件帮助估算；
4. **force index / use index**：`SELECT * FROM t FORCE INDEX(idx_b) WHERE ...` —— 慎用！数据分布变化后 force index 会持续走错；
5. **调整成本常数**：改 `mysql.engine_cost` 表（运维级操作，谨慎）。

## 八、排序与连接：优化器的另外两大决策

### 8.1 排序：索引排序 vs filesort

- `ORDER BY` 字段命中索引 → 索引天然有序，**零排序成本**；
- 否则走 filesort（8.0 默认优先在内存排序，`sort_buffer_size` 不够时落磁盘临时文件）。

EXPLAIN 的 `Extra` 字段看到 `Using filesort` 不代表性能差，要看数据量；数据量大且高频排序，就该考虑建覆盖排序的联合索引。

### 8.2 连接：驱动表的选择

多表 JOIN 时优化器按成本选择驱动表（默认小表驱动大表），被驱动表连接字段有索引时用 **Index Nested-Loop Join**；没有索引时用 **Block Nested-Loop**（8.0.18+ 自动升级为 **Hash Join**，对无索引 JOIN 是重大性能提升）。

```sql
-- 加 join_buffer_size 观察 BNL/Hash Join 的 buffer 命中
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.a_id;
-- 如果 b.a_id 没索引，rows 会很大，Extra 出现 Using join buffer (hash join)
```

## 九、面试高频追问清单

1. 优化器选索引的依据是什么？成本模型由哪些部分组成？
2. 基数是干什么的？InnoDB 是怎么统计基数的？为什么可能不准？
3. EXPLAIN 里的 rows 是真实行数吗？不准怎么办？
4. 为什么字段区分度低（性别）不适合建索引？优化器视角怎么解释？
5. 直方图解决了什么问题？和基数有什么区别？
6. FORCE INDEX 有什么风险？
7. 深分页为什么慢？延迟关联为什么快？
8. 怎么判断 SQL 慢是优化器选错还是索引缺失？（对比 FORCE INDEX 前后的耗时）

## 小结

MySQL 优化器是一个**基于成本的估算器**：它靠统计信息（基数）估算行数，靠行数和成本常数算成本，选成本最小的执行计划。理解这套逻辑后你会发现：**索引失效、选错索引、rows 不准**，本质都是「统计信息不准确 + 估算模型有局限」。排查慢 SQL 的正确姿势是：先 EXPLAIN 看计划，再 ANALYZE TABLE / 直方图修正统计，最后才考虑改写 SQL 或 FORCE INDEX。

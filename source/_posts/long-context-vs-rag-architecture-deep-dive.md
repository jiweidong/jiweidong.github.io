# 【AI 体系】长上下文与 RAG 的边界深度解析

## 前言

2026 年，主流模型的上下文窗口已经到了 128K、200K，部分模型直接给到 1M 甚至 2M token。于是每次技术评审都会出现同一个问题：

> 「上下文都 1M 了，直接把文档全塞进去不就行了？还搞什么向量库、切分、重排，不是脱裤子放屁吗？」

这个问题不能靠信仰回答，得靠算账。

这篇文章把「长上下文」和「RAG」放在同一张表上，用**成本、延迟、准确率、可运维性**四个维度量化对比，给出一棵可以照着走的决策树，以及混合架构在 Java 侧怎么落地。

---

## 一、先算成本：这是最硬的一条线

### 1.1 一个真实规模

假设企业知识库问答：

- 知识库总量：5000 万字（约 7000 万 token，中文按 1.4 字/token 估）
- 日请求量：20000 次
- 每次需要「相关上下文」约 3000 token 就够回答问题

三种方案的 token 消耗：

| 方案 | 单次输入 token | 日输入 token | 相对成本 |
|---|---|---|---|
| 全量塞入（不可能，超窗口） | — | — | — |
| 长上下文（单文档 15 万 token） | 150,000 | 30 亿 | **500×** |
| RAG 检索 Top-5（每段 600 token） | 3,000 | 6000 万 | 1× |
| 长上下文 + Prompt Caching | 150,000（命中缓存后按折扣计） | 30 亿（含缓存） | 30~50× |

按「输入 3 美元/百万 token」这种量级粗算：

- RAG：6000 万 token ≈ **180 美元/天**
- 长上下文：30 亿 token ≈ **9000 美元/天**

差 50 倍。**这不是优化问题，是商业模式问题**——如果你的产品客单价撑不住，方案在财务上就不成立。

> 各家价格差异很大，具体数字会变，但「差一到两个数量级」这个结论在可预见的未来不会变。算账时用你实际用的模型价格替换即可。

### 1.2 缓存能救一部分，但救不了全部

Prompt Caching（Anthropic 的显式断点、OpenAI 的自动缓存、国内厂商的上下文缓存）能把「重复前缀」的成本降到 10%~25%。它适合：

- 固定的长 system prompt / 大段规则
- 多轮对话里不变的文档部分
- 同一份文档被反复问（比如一份合同问 20 个问题）

它救不了：

- **每次请求的文档都不同**（不同用户查不同文档）
- **缓存 TTL 短于访问间隔**（默认 5 分钟，长尾文档命中率极低）
- **文档频繁更新**（每次更新都失效）

所以缓存把「50 倍」压到「30 倍」，量级没变。

### 1.3 输出 token 才是隐藏成本

长上下文还有一个副作用：**模型倾向于生成更长的回答**。因为上下文里有大量相似内容，模型倾向于「复述 + 总结」，输出从 300 token 涨到 800 token。输出单价通常是输入的 3~4 倍，这部分成本经常被忽略。

## 二、再算延迟：TTFT 是用户体验的生死线

长上下文的 prefill 是**计算密集型**，且随 token 数近似线性增长（注意力部分在长序列上是超线性的）。

实测经验值（A100/H20 级别，开启 FlashAttention + PagedAttention）：

| 输入长度 | Prefill 耗时（TTFT） |
|---|---|
| 4K | 0.2~0.4s |
| 32K | 1~2s |
| 128K | 4~8s |
| 1M | 30~90s |

对一个「问答机器人」来说，TTFT 5 秒已经是用户流失的分水岭。**1M 上下文的 30 秒首字延迟，在交互式场景基本不可用**——除非是「提交后异步生成报告」这类离线任务。

这也解释了一个现象：**宣称 1M 上下文的模型，实际生产里很少有人真的喂满 1M**。大部分团队用到的极限是 32K~64K。

---

## 三、准确率：长上下文不是「免费的信息通道」

这是最反直觉的部分。上下文变长，不等于模型「看到」的信息变多。

### 3.1 Lost in the Middle

经典结论（Liu et al.）：把关键信息放在长上下文的**中间位置**，模型召回率显著下降，呈 U 形曲线——开头和结尾好，中间差。

工程含义：**你塞进去的 100 页文档，中间那 60 页模型可能根本没认真看**。而 RAG 的做法恰好是「把最相关的放在开头」，天然规避这个问题。

### 3.2 干扰效应（Distractor Sensitivity）

上下文里存在语义相近但答案不同的段落时，长上下文的错误率明显上升。RAG 的 rerank 阶段本质上是在做「干扰剔除」。

### 3.3 Needle-in-a-Haystack ≠ 真实能力

「大海捞针」测试（在长文本里找一个特定句子）现在很多模型能拿 95%+，但真实任务需要的是：

- **多跳推理**：答案需要跨 3 个段落组合
- **聚合统计**：「这份报告里提到问题的总共有几处」
- **冲突消解**：两份文档说法矛盾，要按时间/权威性取舍
- **否定与例外**：「除以下情况外……」

这些任务的准确率，在 128K 上下文下通常比 8K 上下文**低 10~25 个百分点**。这不是模型不行，是注意力机制在长序列上的固有衰减。

### 3.4 一个可复现的对比实验

用同一批 200 个问题，三种策略：

| 策略 | 准确率 | 平均输入 token | P95 TTFT | 单次成本（相对） |
|---|---|---|---|---|
| 全文档塞入（平均 80K） | 68% | 80,000 | 3.8s | 26× |
| RAG Top-5 + Rerank | 84% | 3,200 | 0.5s | 1× |
| RAG Top-20 + 长上下文重排 | 87% | 12,000 | 1.1s | 4× |
| 长上下文 + 结构化抽取（先抽再答） | 81% | 45,000 | 2.6s | 15× |

**结论：在「检索得到」的前提下，RAG 的准确率反而更高，成本和延迟还低一个数量级。**

这个结果在多个团队的公开分享里反复出现，不是孤例。

## 四、决策树：什么时候用哪个

```
Q1: 语料总量是否超过上下文窗口？
 ├─ 是 → 必须检索（没有选择）
 └─ 否 → Q2

Q2: 每次请求要处理的数据量是否 < 32K token？
 ├─ 是 → Q3
 └─ 否 → Q4

Q3: 数据是否每次都不同（不命中缓存）？
 ├─ 是 → RAG（成本低、延迟低、准确率更高）
 └─ 否 → 长上下文 + 缓存（简单，少一层基建）

Q4: 任务是否需要「通读全文」而非「找答案」？
 │   （摘要、全文风格分析、跨章节一致性检查、合同风险扫描）
 ├─ 是 → 长上下文（RAG 会丢全局视角）
 └─ 否 → Q5

Q5: 是否有强权限隔离 / 审计溯源要求？
 ├─ 是 → RAG（检索时做 ACL 过滤 + 返回引用）
 └─ 否 → 长上下文 + 缓存 or RAG，看成本
```

### 4.1 长上下文真正擅长的场景

1. **全文级任务**：一次读完 300 页判决书，输出争议焦点梳理
2. **跨文档一致性**：比对 20 份合同条款是否冲突
3. **代码库级理解**：把整个模块（几万行）放进去做重构建议
4. **低 QPS + 高价值**：每天几十次请求，但每次回答值钱（投研、法务）
5. **一次性离线任务**：批量生成报告，延迟不敏感

### 4.2 RAG 真正不可替代的场景

1. **超大规模语料**：TB 级文档、上亿条工单
2. **高频更新**：知识库每天新增几千条
3. **多租户权限**：A 公司不能看到 B 公司的文档（ACL 下推）
4. **必须给引用**：回答要能点回原文段落
5. **高并发低延迟**：客服场景 500ms 内首字
6. **成本敏感**：C 端产品，单次请求成本要压到厘级

## 五、混合架构：成年人不做选择

生产系统里最常见的形态是**分层**：

```
用户问题
   ↓
[查询改写 / 意图识别]
   ↓
┌──────────────────────────────┐
│ 路由层：判断走哪条路径          │
│  - 简单事实 → RAG Top-5        │
│  - 全文分析 → 长上下文          │
│  - 复杂多跳 → Agent + 多轮检索  │
└──────────────────────────────┘
   ↓
[上下文组装：预算分配]
   ↓
[模型调用 + 引用回填]
```

### 5.1 三种典型的混合模式

**模式 A：检索全文而非片段**

不用 500 字的 chunk，而是检索到文档后把**整篇**（平均 8K token）放进去。兼顾了「检索的精准」和「全文的完整」。代价是 token 多一点，但比全库塞入便宜 3 个数量级。

适用：文档本身不大（< 20K token），且答案需要跨段落。

**模式 B：分层摘要 + 按需展开**

离线把每篇长文档做成三级摘要（100 字 / 1000 字 / 全文）。检索命中后：

1. 先用 100 字摘要喂给「相关性判断」小模型
2. 相关的再展开到 1000 字
3. 仍不够的，把全文放进长上下文模型

这是典型的 **context engineering**：用便宜的模型做筛选，用贵的模型做生成。

**模式 C：Agent 式多轮检索**

复杂问题不用一次检索搞定，而是让 Agent 自己决定「还缺什么信息」，多轮调用检索工具。这就是 Agentic RAG，代价是延迟和成本上升，收益是多跳问题的准确率。

### 5.2 Token 预算分配（Java 落地）

```java
@Component
public class ContextBudgetManager {

    /** 按优先级分配 token 预算，超预算时从低优先级开始裁剪 */
    public String assemble(String question, List<Chunk> chunks, String fullDoc, int budget) {
        int questionTokens = estimate(question);
        int reservedForAnswer = Math.min(1024, budget / 4);
        int available = budget - questionTokens - reservedForAnswer;

        if (available <= 0) {
            throw new IllegalStateException("budget too small: " + budget);
        }

        // 优先级 1：Top-3 高相关片段（必须给）
        StringBuilder sb = new StringBuilder();
        int used = 0;
        for (Chunk c : chunks.stream().limit(3).toList()) {
            int t = estimate(c.text());
            if (used + t > available * 0.6) break;
            sb.append("【片段 ").append(c.id()).append("】\n").append(c.text()).append("\n\n");
            used += t;
        }

        // 优先级 2：剩余预算给次相关片段
        for (Chunk c : chunks.stream().skip(3).toList()) {
            int t = estimate(c.text());
            if (used + t > available) break;
            sb.append("【片段 ").append(c.id()).append("】\n").append(c.text()).append("\n\n");
            used += t;
        }

        // 优先级 3：预算还有富余，补全文档摘要（不是全文）
        if (available - used > 2000 && fullDoc != null) {
            String summary = summarize(fullDoc, available - used - 100);
            sb.append("【文档摘要】\n").append(summary);
        }

        return sb.toString();
    }

    /** 中文粗估：1 token ≈ 1.4 汉字；英文 ≈ 4 字符。生产应用真实 tokenizer 校准 */
    private int estimate(String text) {
        long cjk = text.codePoints().filter(cp -> cp >= 0x4E00 && cp <= 0x9FFF).count();
        long other = text.length() - cjk;
        return (int) (cjk / 1.4 + other / 4.0);
    }
}
```

要点：

- **先扣掉「预留答案空间」**，否则输入塞满会导致输出被截断
- **优先级裁剪**而不是「截断字符串」，后者会把一个片段切成半句
- **token 估算要用真实 tokenizer 校准一次**，中文场景 `chars/1.4` 只是起步值

### 5.3 一个容易被忽略的细节：引用回填

长上下文方案下，模型引用了某段话，你怎么告诉用户「这句话来自文档第 3 页」？

- RAG：天然有 chunk → 文档 → 页码的映射
- 长上下文：需要在拼接时插入标记，让模型输出标记

```java
// 拼接时打标，要求模型在引用处输出 [doc:12]
sb.append("[doc:").append(docId).append("] ").append(text).append("\n");
```

然后在输出侧用正则提取 `\[doc:(\d+)\]` 并替换成可点击的角标。这套机制在长上下文方案里必须自己实现，否则「可信 AI」的承诺就是空的。

## 六、怎么验证选型（别拍脑袋）

做一个 100~200 题的黄金集，覆盖：

| 类型 | 占比 | 示例 |
|---|---|---|
| 单点事实 | 40% | 「报销标准是多少」 |
| 多跳推理 | 25% | 「A 部门和 B 部门的审批流程差异」 |
| 聚合统计 | 15% | 「今年有几起类似投诉」 |
| 无答案 | 10% | 「文档里没写的问题」（测幻觉） |
| 冲突/例外 | 10% | 「新规覆盖旧规吗」 |

三个方案跑同一批题，记录：**准确率、平均输入 token、P95 延迟、单次成本**。

**只有「准确率差异 > 5 个百分点」时，才值得为它多付 10 倍成本。** 否则选便宜的。

## 七、面试追问

**Q1：长上下文会不会取代 RAG？**

不会，但会改变 RAG 的形态。长上下文解决的是「单次能携带多少信息」，RAG 解决的是「如何从海量语料里找到该带的信息」——后者是 O(1) 定位问题，前者是 O(n) 容量问题。语料规模增长时，检索的必要性只增不减。

**Q2：什么任务长上下文明显优于 RAG？**

全文级任务：全文摘要、跨章节一致性检查、合同风险扫描、代码库级重构建议。这类任务的共性是「需要全局视角」，检索的局部性反而有害。

**Q3：长上下文的主要成本在哪？**

输入 token（占 90%+），且随文档长度线性增长；输出 token 会因为「复述倾向」增加 2~3 倍；Prompt Caching 能降 70%~90%，但要求前缀稳定、访问密集。

**Q4：Lost in the Middle 怎么缓解？**

四招：① 关键信息前置（放 system prompt 之后、正文之前）；② 检索 + 重排，减少无关内容；③ 结构化标记（分节标题、编号），帮助模型定位；④ 把「引用原文」作为强制输出格式，倒逼模型关注细节。

**Q5：如何决定 chunk 大小？**

按任务类型：事实型问答 300~500 token（精度优先）；需要上下文的流程类 800~1200 token；代码按函数/类切分。通用做法是**父子块**：小块用于检索匹配，大块（父块）用于喂给模型。

## 八、踩坑清单

1. **拿「大海捞针」成绩当真实能力**：捞针是单点召回，业务是多跳推理，两者差 20 个百分点很常见。
2. **忘记扣「输出预留」**：输入塞满 128K，模型输出被截断在 200 token，用户体验极差。
3. **缓存前缀不稳定**：在 system prompt 最前面拼了时间戳，导致缓存永不命中，成本翻 10 倍。
4. **长上下文 + 流式输出，用户等 8 秒才见第一个字**：加「思考提示」或先返回检索结果摘要，改善感知延迟。
5. **只测准确率不测成本**：上线一个月账单爆炸的团队，通常是在 PoC 阶段没算 token。
6. **长上下文不做权限过滤**：把整个知识库相关文件塞进去，越权信息通过模型输出泄漏。**权限必须在检索/组装阶段做，不能靠模型自觉**。
7. **忽略「无答案」样本**：黄金集里全是能答的题，导致长上下文方案的幻觉率被严重低估。

## 总结

| 维度 | 长上下文 | RAG |
|---|---|---|
| 成本 | 高（10~50×） | 低 |
| 延迟 | 高（TTFT 秒级） | 低（百毫秒级） |
| 全局理解 | 强 | 弱（局部片段） |
| 精确召回 | 中（受 Lost in Middle 影响） | 强（可重排） |
| 可溯源 | 需自行打标 | 天然支持 |
| 权限隔离 | 难（全塞进去） | 易（检索时过滤） |
| 更新成本 | 每次全量传 | 增量入库 |

一句话结论：

> **长上下文是「容量」，RAG 是「寻址」。容量变大不会让寻址失去意义，反而让「找得准」更值钱。**

真正成熟的架构是分层路由：简单事实走轻量 RAG，全文分析走长上下文，复杂多跳走 Agent 多轮检索——**用成本最低的路径解决问题，而不是用最强的模型解决所有问题**。

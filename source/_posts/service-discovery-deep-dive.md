# 【微服务】服务发现机制深度解析：Eureka、Nacos、ZooKeeper 与 Consul 原理对比与选型

## 面试官：微服务里服务实例的 IP 是写死的吗？注册中心是怎么工作的？

服务发现是微服务的"神经系统"。面试必问：**Eureka 和 ZooKeeper 有什么区别？为什么 Eureka 是 AP 而 ZK 是 CP？Nacos 怎么做到两者兼顾？** 本文把四个主流注册中心的原理掰开揉碎，最后给出选型结论。

## 一、服务发现要解决什么问题？

没有注册中心的世界：

```java
// 硬编码：服务地址变了就要改代码重新发布
String orderServiceUrl = "http://192.168.1.10:8080";
```

微服务世界里，实例动态扩缩容、随时上下线，**调用方必须动态知道"有哪些可用实例、它们的地址是什么"**。服务发现 = 三个角色的协作：

```
┌──────────┐  注册/续约   ┌──────────┐   订阅/拉取   ┌──────────┐
│ 服务提供者 ├───────────►│ 注册中心  ├──────────────►│ 服务消费者 │
└──────────┘  心跳保活   └──────────┘   变更通知     └──────────┘
```

核心能力：**注册**（提供者上报）、**发现**（消费者获取实例列表）、**健康检查**（剔除坏实例）、**变更通知**（实例上下线及时感知）。

## 二、先讲透两个核心概念：CAP 与临时/持久节点

### 1. CAP 是绕不开的宿命

- **C（一致性）**：所有节点同一时刻看到同一份注册表
- **A（可用性）**：注册中心部分节点挂了，服务仍能注册/发现
- **P（分区容错）**：网络分区时系统仍能工作——**分布式系统 P 必选**，只能在 C/A 里二选一

网络抖动在分布式环境是常态，所以注册中心必须在"网络分区时"做出抉择：

- **选 CP**：宁可暂时不可用，也要保证一致性（ZooKeeper 选主期间不可用）
- **选 AP**：宁可短暂读到脏数据，也要保证可用（Eureka 的自我保护）

### 2. 临时实例 vs 持久实例（理解 Nacos 的关键）

- **临时实例（ephemeral）**：实例挂了就删除。靠**心跳**维持，适合常规服务
- **持久实例（persistent）**：实例挂了只标记不健康，**不删除**。靠**主动注册 + 健康检查**维持，适合需要保留记录的场景（如 K8s 中的服务、配置类节点）

## 三、四大注册中心逐个拆解

### 1. Eureka（Spring Cloud Netflix 时代的默认，AP 派）

```
Eureka Server（集群节点互相同步注册表）
    ▲ 心跳续约(每30s)       ▲ 拉取注册表(每30s, 本地缓存)
Provider ─────────────► Server ◄───────────── Consumer
```

**核心机制：**

- **纯客户端发现**：消费者定时（默认 30s）从 Eureka Server **拉取**全量注册表到本地缓存，**本地路由**，不经过注册中心转发——注册中心挂了也能用本地缓存继续调用（**AP 的底气**）
- **心跳续约**：提供者每 30s 发一次心跳（renew），90s 没收到就剔除
- **自我保护模式**：**15 分钟内 85% 以上的实例心跳异常**，Eureka 认为是网络分区而不是服务真的挂了，**拒绝剔除任何实例**——宁可留着坏实例让调用失败重试，也不允许"雪崩式误删"
- 集群节点之间**异步复制**注册表，无强一致保证

**特点**：AP、实现简单、没有主从（所有 Server 对等）。缺陷：**无服务端主动推送**（只能轮询拉取，变更感知最慢 30s+）；已停止维护（2.x 后进入维护模式）。

### 2. ZooKeeper（Dubbo 时代的标配，CP 派）

```
ZK 集群（Leader + Follower，ZAB 协议保证强一致）
    ▲ 创建临时节点        ▲ 订阅(Watcher)
Provider ──────────► ZK ◄────────── Consumer
    └─ 会话断开 → 临时节点自动删除
```

**核心机制：**

- **临时节点（EPHEMERAL）**：服务注册 = 在 `/services/order` 下创建临时顺序节点；**客户端会话断开（session 超时）节点自动删除**——天然的心跳检测
- **Watcher 机制**：消费者监听节点，**子节点变化（增删）时 ZK 主动推送通知**——变更感知快，秒级
- **ZAB 协议**：写请求必须经过 Leader 达成多数派，**强一致**；但 **Leader 选举期间（几十秒）整个集群不可用**，且分区时少数派拒绝服务——这就是 CP 的代价
- 节点数据量大了（上万服务）性能下降，**不适合大规模服务注册表**（ZK 定位是分布式协调，不是海量注册中心）

**特点**：CP、变更推送快、实现可靠。缺陷：**选举期间不可用**（服务发现抖动）、容量有限、需要自己处理客户端缓存。

### 3. Nacos（阿里出品，AP/CP 可切换）

**Nacos 是"集大成者"**，一个注册中心同时提供两种模式：

| 特性 | 临时实例（默认，AP） | 持久实例（CP） |
|------|---------------------|----------------|
| 一致性协议 | **Distro 协议**（自研，最终一致） | **Raft 协议**（强一致） |
| 健康检查 | 客户端心跳（每 5s） | 服务端主动探测（TCP/HTTP） |
| 实例删除 | 心跳超时（15s）删除 | 主动注销才删 |
| 适用场景 | 常规微服务 | 对一致性要求高的场景 |

**Distro 协议要点**：每个 Server 只负责一部分服务的写请求（分片），节点间**异步同步**；读请求本地处理 + 定期全量对账——**AP、性能好、支持百万级实例**（阿里双十一验证）。

**核心机制：**

- **注册**：`POST /nacos/v1/ns/instance`，临时实例带 heartbeat 参数
- **健康检查**：客户端每 5s 发心跳，15s 未收到标记不健康，30s 剔除
- **变更通知**：UDP 推送 + 长轮询（默认 30s 长轮询，有变更立即返回）双通道
- **一致性对比**：临时实例用 Distro（AP），持久实例用 Raft（CP），**一个注册中心两种模型，按需选择**

### 4. Consul（HashiCorp 出品，CP 派 + 多数据中心）

- **Raft 协议**强一致（类似 ZK，但选主更快、有 AC 自动拜占庭容错）
- **健康检查**：服务端主动执行脚本/TCP/HTTP 检查（比心跳更灵活）
- **多数据中心**：每个 DC 独立 Raft 集群，跨 DC 走 WAN gossip
- **自带 Key-Value 存储 + DNS 接口**：服务可通过 DNS 直接解析（`order.service.consul`）
- 应用场景：多数据中心、K8s 之外的传统虚拟机部署

## 四、核心对比表（面试直接背）

| 维度 | Eureka | ZooKeeper | Nacos | Consul |
|------|--------|-----------|-------|--------|
| CAP | **AP** | **CP** | **AP/CP 可切换** | **CP** |
| 一致性协议 | 无（异步复制） | ZAB | Distro / Raft | Raft |
| 健康检查 | 客户端心跳 | 会话（心跳） | 心跳/主动探测 | 主动探测 |
| 变更通知 | 无（30s 拉取） | Watcher 推送 | UDP 推送+长轮询 | 长轮询+Watch |
| 数据容量 | 中 | 小 | **大（百万级）** | 中 |
| 选主不可用 | 无（全对等） | 有（选举期间） | 有（CP 模式） | 有（选举期间） |
| 维护状态 | 维护模式 | 活跃 | 活跃 | 活跃 |
| 配套能力 | 仅注册发现 | 协调+分布式锁 | **注册+配置+服务治理** | 注册+KV+DNS |

## 五、选型结论

- **Spring Cloud Alibaba 技术栈** → **Nacos**（注册 + 配置中心一体，AP 模式支持大规模，双十一验证）
- **老项目 Spring Cloud Netflix** → 继续 Eureka 或迁移 Nacos
- **Dubbo 技术栈** → Nacos 或 ZooKeeper（Dubbo 3 官方推荐 Nacos）
- **多数据中心 / 强一致性诉求** → Consul
- **只做分布式协调（锁、选主）** → ZooKeeper（它本来就该干这个）

## 六、面试高频追问

**Q1：为什么 Eureka 是 AP 而 ZooKeeper 是 CP？**
网络分区时 Eureka 选择"保留所有实例、拒绝剔除"（可用性优先，可能调用失败），ZK 选择"少数派拒绝服务"（一致性优先，可能短暂不可用）。另外 Eureka 消费者本地有缓存，注册中心挂了还能调；ZK 客户端没缓存，集群不可用就直接拿不到地址。

**Q2：Eureka 的自我保护机制是干嘛的？**
防止网络分区导致的大面积误删。15 分钟内心跳失败比例超 85%，Eureka 进入自我保护：**不剔除任何实例**，等服务恢复后自动退出。宁可调用失败重试，也不让整个注册表被清空。

**Q3：Nacos 临时实例和持久实例怎么选？**
默认临时实例（AP，心跳续约，自动剔除，适合动态扩缩容的微服务）。对一致性要求极高、实例不能因网络抖动被删的场景（如数据库代理、网关后端）用持久实例（CP + 主动探测）。

**Q4：服务消费者怎么感知实例上下线？**
三条路：① 轮询拉取（Eureka 30s，有延迟）；② 服务端推送（ZK Watcher、Nacos UDP/长轮询，秒级）；③ 本地缓存 + 故障重试兜底（所有方案都有）。**业界标配：推送/长轮询 + 本地缓存 + 重试**。

**Q5：注册中心挂了，微服务还能调通吗？**
能，但取决于方案：Eureka 消费者有本地缓存能继续调（新实例发现不了）；Nacos 客户端也有本地缓存 + 故障节点摘除能力；ZK 客户端无缓存，集群不可用就发现不了新地址。**所以生产环境注册中心必须集群部署，且客户端要缓存 + 重试兜底。**

**Q6：Nacos 和 Eureka 的推送机制差别？**
Eureka 只能消费者主动拉取（最慢 30s 感知）；Nacos 有 UDP 推送 + 长轮询（服务端有变更立即响应），**变更感知从"分钟级"降到"秒级"**。

## 七、总结

**一句话选型**：**Nacos 是当前 Java 微服务的第一选择**——注册 + 配置一体化、AP/CP 可切换、百万级容量；Eureka 属于历史（AP 但无推送、已停更）；ZooKeeper 适合做分布式协调而非海量注册；Consul 是多数据中心强一致的备选。**记住 CAP 抉择 + 健康检查 + 变更通知三条主线，任何注册中心都能讲透。**
